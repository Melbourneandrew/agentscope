## Overview

Agentscope manages harness integrations as explicit, reversible installations. A harness is a coding-agent runtime, not the model provider behind it.

## Terminology

- **Owned integration:** a configuration block installed and identifiable as Agentscope-managed.
- **Product harness roster:** Codex, Claude Code, Cursor, Gemini CLI, OpenCode, Pi, OpenClaw, and Hermes; this is the complete first-party product target, not a claim that every release supports every listed harness.
- **Release-supported harness:** a harness, version, and execution mode backed by the release support manifest for the release making the claim.

## Requirements

### REQ-HAR-001: Reversible installation

As a coding-agent user, I want to install and remove an integration safely, so that I retain control of my harness configuration.

- **AC-HAR-001.1:** When I run `agentscope install <harness>`, the system shall detect supported versions and create only an owned, reversible integration.
- **AC-HAR-001.2:** When I run `agentscope uninstall <harness>`, the system shall remove only its owned integration block.

### REQ-HAR-002: Conflict-aware ownership

As a user, I want duplicate observability hooks detected, so that I do not accidentally export duplicate or inconsistently redacted traces.

- **AC-HAR-002.1:** When an overlapping vendor integration is detected, the system shall report the conflict and require an explicit migration before replacement.

### REQ-HAR-003: First-party harness coverage

As a coding-agent user, I want consistent setup behavior across supported harnesses, so that choosing a harness does not weaken Agentscope's safety guarantees.

- **AC-HAR-003.1:** When Agentscope advertises its product harness roster, the system shall include first-party integrations for Codex, Claude Code, Cursor, Gemini CLI, OpenCode, Pi, OpenClaw, and Hermes.
- **AC-HAR-003.2:** When any release-supported harness is installed, inspected, upgraded, or removed, the system shall apply the same ownership, fail-open, redaction, and diagnostic guarantees while preserving harness-specific semantics.
- **AC-HAR-003.3:** When any release advertises a harness as supported, the system shall limit the claim to the harness versions and execution modes backed by that release's support manifest.
- **AC-HAR-003.4:** When a harness in the product harness roster is not backed by a release's support manifest, the system shall omit that harness from that release's support claims without removing it from the product harness roster.
