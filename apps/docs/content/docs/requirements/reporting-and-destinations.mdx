title: Reporting and Destinations
description: User requirements for reliable trace delivery to supported destinations.

## Overview

Agentscope begins with Langfuse and must grow to additional observability destinations without changing how agent harnesses capture work.

## Terminology

- **Delivery identity:** a stable per-item identity that lets a destination deduplicate repeated delivery when supported; it does not guarantee exactly-once delivery.
- **Reporter receipt:** a content-free terminal statement about one connection attempt; it is accepted only when returned before the shared hook deadline.
- **Outcome unknown:** the conservative connection-attempt state used whenever full-batch acceptance or definite non-commit cannot be established, including lost acknowledgements and every partial-batch response even when individual provider items are attributable.
- **Connection attempt:** at most one hook-time Reporter invocation for one selected connection and one bounded redacted batch.
- **Langfuse reporting connection:** a Reporter connection that sends normalized redacted trace data to a Langfuse OTLP endpoint.

## Requirements

### REQ-REP-001: Bounded fail-open delivery

As a user, I want capture to attempt delivery without slowing or changing my agent session, so that observability remains non-disruptive.

- **AC-REP-001.1:** When a reporter accepts a redacted batch before the hook deadline, the system shall record that connection's terminal outcome and return without creating a Core-owned delivery copy.
- **AC-REP-001.2:** When a reporter cannot accept a batch before the hook deadline, the system shall discard that connection's batch without creating a retry payload.
- **AC-REP-001.3:** When any reporting attempt fails, times out, or has an unknown outcome, the system shall retain only bounded non-content health evidence and fail open to the harness.

### REQ-REP-002: Destination extensibility

As an Agentscope contributor, I want a stable reporter contract, so that I can add a first-party destination without modifying harness adapters.

- **AC-REP-002.1:** When a reporter receives a batch, the system shall supply normalized and redacted trace data independent of native harness format.

### REQ-REP-003: Independent multi-destination outcomes

As a user, I want each selected destination attempted independently, so that one unavailable destination does not prevent another from receiving the trace.

- **AC-REP-003.1:** When routing selects multiple named connections, the system shall attempt each selected connection within the same absolute hook deadline.
- **AC-REP-003.2:** When one selected connection reaches a terminal outcome, the system shall record exactly one terminal outcome for that connection independently of every other selected connection.
- **AC-REP-003.3:** When a connection's acknowledgement is lost after a possible remote commit, the system shall classify the outcome as unknown rather than rejected.
- **AC-REP-003.4:** When the same logical trace boundary is routed to multiple destinations or regrouped into different transport batches, the system shall preserve the same per-item delivery identity.

### REQ-REP-004: Standard Langfuse reporting transport

As a Langfuse user, I want Agentscope reporting to use the standard observability transport, so that trace delivery does not depend on a separate proprietary reporting API.

- **AC-REP-004.1:** When a Langfuse reporting connection sends a redacted trace batch, the system shall send it exclusively through OTLP and shall not invoke any separate Langfuse API for reporting.
- **AC-REP-004.2:** When Langfuse reporting is unavailable, the system shall apply the same bounded fail-open and per-connection outcome requirements as every other Reporter.
