## Capability Summary

The workspace separates the user-facing CLI application from shared runtime services and first-party harness and Trace Destination integrations, so each concern can evolve and be verified without becoming a runtime extension system.

## Architecture Decision Records

### ADR-001: Treat the CLI as an application

**Decision:** `apps/cli` is the `@agentscope/cli` publishable application and owns command parsing, user interaction, exit codes, and release-facing executable packaging. It depends on `packages/core` and first-party integrations but contains no reusable domain implementation.

**Context:** The CLI is the product entry point, while trace collection, configuration, delivery, and integration logic must also be executable from hooks and test infrastructure.

**Consequences:** Hook installation binds to an Agentscope-owned launcher rather than searching hook-time `PATH`. CLI commands delegate to Core services; no harness-native parsing, destination transport, or credential storage implementation is duplicated in `apps/cli`. Release builds bundle all private Agentscope TypeScript workspace code into the CLI artifact. Non-bundleable third-party/native modules remain ordinary public runtime dependencies unless [NPM Publishing ADR-002](/docs/blueprints/operations/npm-publishing) and the owning destination Blueprint jointly authorize one install-script-free vendored native closure with exact build-material, notice, loader, artifact, and native-evidence gates.

### ADR-002: Keep Core shared and integration-neutral

**Decision:** `packages/protocol` owns the canonical OTLP/OpenInference contract, documented `agentscope.*` attributes, schema validation, and protocol migrations. `packages/destinations/core` owns destination-family ports and portable reporter/retriever DTOs. `packages/core` owns redaction, configuration and credential references, routing, bounded hook-time delivery, retrieval safety, and sanitized diagnostics. None contains harness-specific configuration mutation or destination protocol mapping.

**Context:** A single owner is required for data governance and delivery semantics across every harness and Trace Destination.

**Consequences:** Protocol may depend only on standards and deliberately approved low-level libraries. Destination family Core depends only on Protocol and approved schema libraries; application Core may depend on Protocol and destination family Core, but never on a concrete destination. Concrete integrations depend inward on their family Core and Protocol. The CLI alone composes application Core with concrete first-party integrations.

### ADR-003: Group first-party integrations by product concern

**Decision:** First-party integrations live under `packages/harnesses/` and `packages/destinations/`. `packages/harnesses/core` and `packages/destinations/core` contain only shared internal ports, DTOs, and contract-test fixtures for their respective families. A harness package owns one harness; a destination entry owns a mandatory `reporter/` module and, when the destination supports it, an optional `retriever/` module.

**Context:** This makes the contributor-facing structure reflect the two independent directions of the system: harness-native evidence enters through adapters and redacted canonical data leaves through destinations.

**Consequences:** The target layout is:

```text
apps/
  cli/
  docs/
packages/
  protocol/
  core/
  harnesses/
    core/
    codex/
    claude-code/
    gemini-cli/
    opencode/
    pi/
    openclaw/
    hermes/
  destinations/
    core/
    langfuse/
      reporter/
      retriever/              # present only when supported
    local-sqlite/
      reporter/
      retriever/
  testkit/
tests/
  integration/
  integration-live/
```

The shared family packages are not public runtime plugin SDKs. The existing Cursor harness and console destination directories are disposable scaffolds and are removed rather than carried into the target structure. Adding a harness or destination remains a reviewed first-party pull request; the contracts exist to prevent copy/paste and preserve consistent behavior. The CLI is the composition root and may import first-party package public exports to assemble the supported registry; application Core may import only the destination-family ports, never a concrete destination implementation.

### ADR-004: Keep test layers in their natural ownership location

**Decision:** Unit and contract tests are colocated with the application or package that owns the behavior. Root `tests/integration/` owns hermetic multi-package executable scenarios, and `tests/integration-live/` owns protected external smoke scenarios.

**Context:** Colocation keeps fast feedback and coverage with the code being changed. A root scenario suite is the appropriate owner for Docker topology, candidate CLI packaging, real harnesses, and cross-package assertions.

**Consequences:** A package may import shared fixtures from `packages/testkit`, but package tests do not reach into other package internals. Integration scenarios consume public/internal package contracts only and do not become a second home for unit coverage. Docker Compose and image definitions belong under `tests/integration/`, not a generic root `infra/` directory, until the product has deployable infrastructure.
