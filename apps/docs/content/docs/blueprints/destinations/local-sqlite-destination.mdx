## Capability Summary

The local SQLite destination gives a user an opt-in durable trace repository and retrieval capability without requiring Langfuse or another remote observability service.

## Architecture Decision Records

### ADR-001: Make local SQLite a separate opt-in destination

**Decision:** A first-party Local SQLite Trace Destination provides both reporter and retriever behavior. It is disabled by default and exists only after `agentscope destination configure local-sqlite` succeeds with explicit user confirmation.

**Context:** Default AgentScope capture is intentionally non-durable: a failed hook-time report is discarded. A local database materially changes privacy, disk, retention, and backup expectations and must be a user-selected destination rather than hidden runtime state.

**Consequences:** Once configured, Local SQLite receives the same redacted Protocol graph as every other destination. It has no credentials by default. Its retention and data controls are destination settings, not Core diagnostics. Encryption at rest is not required; the destination creates user-restricted files and documents that host filesystem and disk-encryption policy remains the user's responsibility.

### ADR-002: Treat remote SQLite-compatible services as distinct destinations

**Decision:** Local SQLite is a filesystem destination. Any remote SQLite-compatible service such as libSQL/Turso is a separate Trace Destination type with its own endpoint, credential slots, network behavior, and availability contract.

**Context:** A network filesystem SQLite file is not a safe substitute for a database service: locking, durability, latency, and failure semantics differ substantially from a local database.

**Consequences:** A shared internal SQLite schema/migration utility may be reused, but `local-sqlite` and a remote service do not share a configuration type or pretend to have identical reliability properties.

### ADR-003: Configure and migrate deliberately

**Decision:** Local SQLite uses `better-sqlite3` and one contiguous, append-only inventory of reviewed `NNNN-name.sql` resources and SHA-256 digests. A build-time SQLite-aware tokenizer/parser admits only `CREATE TABLE`, non-virtual `CREATE INDEX`, bounded `ALTER TABLE` add/rename, `DROP INDEX`, and bounded `INSERT`/`UPDATE`/`DELETE` against the closed schema; it rejects transaction control, `PRAGMA`, `VACUUM`, `ATTACH`/`DETACH`, virtual tables, triggers, writable-schema operations, extension loading, and every unrecognized construct, and proves each resource ends at a statement boundary. DML may touch only migration metadata or newly introduced derived index/projection tables; it cannot update or delete a durable trace/delivery row or change payload bytes, Protocol compatibility identity, delivery identity, canonical TraceId, canonical start time, or retention-admission time. Before commit the runner verifies the exact multiset of immutable row identities and payload digests equals its pre-migration snapshot, rebuilds every branch/model/session/tag and other portable derived projection from those immutable payloads through the current Protocol compatibility compiler, and proves the candidate projection multiset exactly equals that bounded recomputation. Runtime executes statements individually inside its own `BEGIN EXCLUSIVE`, verifies the connection remains in that transaction after every statement, and commits only after the complete candidate ledger, row-preservation invariant, and semantic projection invariant validate. New-database provisioning and explicit upgrade take the exclusive database lifecycle fence with a bounded busy timeout. The closed `schema_migrations` ledger records version, name, digest, and order; database metadata separately records the destination format and exact Protocol compatibility identity stored by the rows. Missing, edited, reordered, skipped, or unknown committed evidence rejects upgrade. A failed transaction rolls back completely; the lifecycle intent records only that the exact immutable target inventory did not commit, and explicit resume may safely retry that same inventory after proving the database remains at the prior ledger.

**Context:** Creating a database is a material mutation and must not occur merely because `agentscope init` discovered local capability. Database layout and Protocol semantics evolve independently, and a general migration framework would add authority without owning either one.

**Consequences:** Init may propose the destination but never enables it by default. The destination ships no ORM, source compiler, or ad hoc repair path. SQL migrations change storage and indexes but never rewrite immutable Protocol payloads. Recovery accepts only the exact prior or complete candidate ledger; every other state requires reconciliation. Backup/restore verification binds both the migration ledger and Protocol compatibility metadata.

### ADR-004: Separate SQL layout from durable Protocol payload versions

**Decision:** Every row stores the immutable Protocol payload, its exact Protocol compatibility-profile identity, and stable delivery identity. The Protocol package's manifest-bound compatibility compiler is the sole reader authority; Local SQLite stores and indexes the identity but owns no reader or compatibility window and does not rewrite canonical payloads during SQL migrations.

**Context:** Database layout and canonical trace semantics evolve independently; rewriting historic trace payloads can destroy downgrade and recovery options.

**Consequences:** SQL migrations change storage structures only. Retrieval and restore submit the stored identity and payload to the current Protocol compatibility compiler and refuse an unreadable or unsupported identity with a stable diagnostic rather than guessing its meaning.

### ADR-005: Bound concurrency, retention, and destructive lifecycle

**Decision:** Writes use WAL and a unique delivery constraint. Hook-time native database work runs in one short-lived, bounded-IPC child process owned by the hook. The same-process branded absolute deadline remains only in the parent; the child receives a validated integer work budget ending at `hard deadline - native teardown reserve`. The non-configurable reserve and minimum useful child budget are support-manifest values proven on each native baseline, and configuration rejects a routing duration below their sum. Insufficient runtime budget consumed by earlier stages returns `unavailable` before spawn. Each admitted baseline supplies an OS-backed parent-death/job containment primitive that terminates the child if the parent or authenticated IPC channel dies; support tests prove containment and joined teardown for both ordinary cutoff and abrupt parent death. At the child cutoff the parent forces termination and joins within the certified reserve; failure to certify or achieve joined teardown makes that Local SQLite baseline unsupported, and no native handle or child survives hook return. Before any mutating SQLite call, the child sends a bounded ready-to-attempt message and waits. The parent durably transitions the in-process attempt state to possible-commit before returning one exact one-use permission; without it the child cannot enter SQLite. Cutoff before permission is granted has proven noncommit and returns `unavailable`; every cutoff, crash, lost acknowledgement, or global expiry after permission is granted returns `outcome-unknown`, whether or not the child reports that SQLite entry completed. SQLite's busy timeout never exceeds the derived child budget. Every connection stores positive age, trace-count, and immutable Protocol-payload-byte limits; defaults are 30 days, 100,000 traces, and 1 GiB, and versioned settings ceilings are 365 days, 1,000,000 traces, and 10 GiB. Age is measured only from the frozen Core-minted UTC admission timestamp in the Reporter attempt context and stored immutably with each accepted trace, never from caller/provider canonical time or a concrete package clock. The database stores a nondecreasing last-trusted cutoff. Within one boot, Core binds UTC to its monotonic clock; across restart, a backward wall time never lowers the cutoff or re-exposes an expired trace. A forward or otherwise unprovable discontinuity beyond the manifest-bound tolerance preserves physical rows, suppresses irreversible cleanup, makes portable search/get return their existing plain `unavailable` result, and records `destination-retention` through Reporter evidence until an explicit plan-first clock rebaseline is confirmed; uncertainty never widens the visible retention window. Each operation fixes one trusted cutoff at entry. A row expires only when its admission timestamp is strictly earlier than `trusted operation time - configured age`; equality remains retained. Search/get logically exclude expired rows without mutation. Doctor reports the configured policy and fixed unavailable status for cutoff, clock-continuity, row-count, and byte-count facts that require transactional table or WAL access; it never substitutes stale header evidence. Reporting, explicit retention maintenance, upgrade, backup, and restore-candidate preparation are the only retention-mutating operations and finish transactional cleanup before success; an idle database may retain expired physical pages until one of them runs. Backup cleans before taking its snapshot. Eviction is oldest-first by admission timestamp, canonical TraceId, then delivery identity, all ascending. A Reporter first resolves every batch identity against the pre-cleanup transaction snapshot. A conflicting payload or compatibility identity rolls back the complete batch and returns proven-noncommit `rejected`. Byte-identical nonexpired evidence is protected from that transaction's eviction, collapses as accepted, and preserves its original admission timestamp; byte-identical evidence already expired returns proven-noncommit `rejected` plus `destination-retention`, is never reinserted, and never receives a fresh timestamp. A concurrent uniqueness loser rereads and applies the same rules before settlement. Only after this classification does the transaction insert new rows and apply cleanup; it returns `accepted` only when every batch identity remains durably present. A batch that cannot coexist returns `rejected` plus `destination-capacity` with proven noncommit. Cleanup uses the same permission boundary and receipt rules. Boundary tests fix the timestamp granularity and prove equality retained, one unit older excluded, and cleanup matches retrieval; duplicate tests cover sequential and concurrent identical, conflicting, and expired deliveries.

**Context:** Concurrent hooks, migrations, full disks, corruption, and user removal intent fail independently.

**Consequences:** Payload-byte accounting uses exact stored immutable Protocol bytes rather than implementation-dependent SQLite file size. Database pages use full auto-vacuum from initial creation and WAL checkpoint policy is bounded separately; Doctor reports only configured policy and bounded nonmutating physical evidence, and reports database-derived retention/capacity facts unavailable rather than opening SQLite or guessing from page/freelist, WAL, or header state. Retention never rewrites a payload or silently raises a limit. Local SQLite maps its closed native dispositions only to destination-family Core's generic `destination-busy`, `destination-full`, `destination-corrupt`, `destination-migrating`, `destination-retention`, and `destination-capacity` receipt reasons; Application Core then maps those receipts into Operational State as Reporter ADR-002 defines.

### ADR-006: Implement the canonical Retriever with indexed keyset queries

**Decision:** The Local SQLite Retriever implements the same `search` and `get` contract as every retrieval-capable destination. Its schema maintains indexes for canonical trace ID, start time, harness, branch, model, session, and normalized tags. Search uses snapshot-consistent keyset pagination ordered by start time descending and canonical trace ID; get reads the immutable Protocol payload through the supported reader and current redaction boundary.

**Context:** Local SQLite is the reference destination for exact portable semantics and should not gain a second, SQL-specific CLI surface.

**Consequences:** `agentscope traces search --destination <local-connection>` and `traces get` behave identically to Langfuse at the CLI boundary. Raw SQL, database paths, and row identifiers are never accepted as portable trace references. Migration and query plans are covered by destination-specific tests in addition to the shared Retriever contract suite.

### ADR-007: Gate the bundled native dependency per exact platform baseline

**Decision:** The Local SQLite package exports one complete local destination descriptor and lifecycle handler for the packed application's immutable product registry. Descriptor registration is platform-independent and makes `local-sqlite` discoverable. Native loading remains entirely inside package-owned factories closed over the exact manifest and owned loader; it does not widen a destination-family factory or lifecycle DTO and never accepts caller callbacks, paths, handles, or an arbitrary database object. Configure preflight derives the current full platform and native projection, verifies the exact candidate manifest and binary, and returns the fixed native-unavailable result before configuration, directory, database, credential, or lifecycle mutation when any authority is absent or inconsistent. Public release support is admitted only by the external evidence gate in [CLI Installation ADR-003](/docs/blueprints/operations/cli-installation).

Local SQLite uses one release-material-manifest-pinned `better-sqlite3` registry artifact as an audited build input, not as a dependency of either the workspace or published CLI. The material manifest binds its exact package name, version, registry identity, npm integrity, source revision, compressed byte length, archive format, and expected regular-file inventory. An Agentscope-owned acquirer downloads that tarball as inert bounded bytes and verifies its exact length and integrity before decoding. Its closed archive compiler performs no filesystem write until it has consumed the exact archive and proven one end marker with no trailing or concatenated data; manifest-fixed entry-count, path-depth, segment/path-byte, per-file, total-expanded-byte, and compression-ratio ceilings; and exact agreement with the expected regular-file names, sizes, and digests. It rejects empty or absolute names, dot or dot-dot segments, NUL/control bytes, backslashes, drive/UNC forms, repeated separators, noncanonical UTF-8/NFC, case or Unicode filesystem aliases, duplicates, sparse encodings, links, devices, directories as payload entries, PAX/GNU name indirections, and every unknown header or extra/missing entry.

Only after complete admission does the acquirer create one fresh current-user-only private staging directory outside the workspace and materialize each in-memory/stream-owned payload to its manifest-owned canonical target rather than an archive-supplied target. It creates bounded parent directories itself and uses containment-bound directory handles, no-follow traversal, and exclusive-create regular-file writes; then it rechecks every size/digest and hands the builder an unforgeable closed staging authority only after the exact inventory is complete. Failure cleans only objects authenticated under that fresh root and exposes no partial directory to the builder. The acquirer never invokes a package manager, resolves a dependency graph, loads extracted code, or executes any declared or inferred lifecycle hook. Clean workspace installation from an empty package store proves `better-sqlite3` and its dependency graph are absent.

Each native-binary tuple then has one manifest-fixed binary origin. That tuple is narrower than a full supported-platform tuple and binds only the binary's Node ABI contract and admitted Node-major set, operating-system family and minimum release, architecture, and Linux libc family plus minimum version. An upstream prebuild is admissible only when registry provenance binds it to the exact source revision, native build workflow, runner image, compiler/toolchain, SQLite amalgamation and options, every resolved compiled dependency including the exact `node-addon-api` revision, and the produced binary digest. When any material is range-resolved, mutable, absent, or unattested, that upstream binary is inadmissible. The alternative is an Agentscope-owned native build on the native-binary tuple's runner. Its separate exact material lock enumerates every source/header/tool artifact and transitive input by registry/source identity, integrity, source revision, license, and bounded inventory. The same inert-byte acquirer fetches each entry independently; no material dependency graph is installed, and any unlisted transitive request fails.

The build runs in one disposable, credential-free sandbox rather than the trusted release/publish process. Before any source-controlled or upstream build code can run, a separate acquisition job closes all inputs and the sandbox starts with network and host-socket access denied; no OIDC, registry, repository, signing, cloud, package-manager, or user credential; an empty synthetic home and temporary directory; one exact allowlisted environment; no inherited workspace, Git, package-manager, compiler-plugin, shell-profile, or user/system configuration discovery; read-only material, owned build-entry, toolchain, SDK, and system-root mounts; and one fresh bounded writable output root. The reviewed entry may interpret only the manifest-named upstream build metadata inside that sandbox, starts one bounded owned process tree through absolute executables, and cannot download, add a material, escape the output root, retain a process, or address another filesystem namespace. Wall time, CPU, memory, process count, output files, bytes, and logs are hard-capped; timeout, signal, sandbox violation, unknown subprocess, unexpected output, or teardown failure discards the complete job. Hostile upstream build-action, compiler-plugin/config discovery, environment, network, subprocess, path/output-escape, and resource-limit fixtures must fail without observing a host secret or external side effect.

The sandbox emits only the expected unsigned binary and content-free build record. A separate aggregation job that executes no build output reconstructs provenance and the complete software bill of materials from the closed input/job records, verifies the binary format/architecture/import surface plus exact path/size/digest, and admits the inert bytes to later native execution tests.

Every pre-admission load of either an upstream or owned binary—including the owned-loader smoke and complete packed-CLI lifecycle matrix—runs on its exact native baseline inside a fresh sacrificial VM or equivalently certified OS containment boundary. The guest receives no repository, artifact-store, cloud, OIDC, signing, registry, user, or package-manager credential; has network and host/metadata socket access denied; mounts the immutable candidate and test program read-only; sees no release checkout or writable artifact authority; and uses only an allowlisted environment plus fresh bounded synthetic home, temp, database, backup, and output roots. The supervisor outside the guest owns the monotonic deadline, process/job containment, immutable candidate digest, test oracle, output caps, and forced teardown. It independently proves no child, handle, mutable disk, VM, or external side effect survives, destroys the guest after every result, and exports only one bounded content-free evidence record bound to the immutable candidate, image, filesystem, test-manifest, and support-tuple digests. The guest cannot publish or replace the tested candidate, and the nonexecuting aggregator accepts evidence only from the exact externally observed run. Hostile native egress, host/repository mutation, child/handle retention, output overflow, candidate replacement, and forged/partial guest-evidence fixtures fail the gate.

Signing and publication authority exists only after those tests in a fresh job that shares no writable filesystem or runner state with acquisition, build, or execution jobs and cannot execute source, build metadata, or the native candidate. A release cannot mix origins silently; the support manifest records the chosen origin, build and execution sandbox profiles, and complete material ledger for every tuple.

The artifact assembler copies a closed allowlist consisting of the reviewed CommonJS runtime, all licenses and notices required by the runtime and incorporated binary materials, the generated provenance/SBOM records, and the checksum-bound admitted upstream or owned-build binaries into an Agentscope-owned internal CLI directory. It never copies `binding.gyp`, C/C++ or vendored SQLite sources, package scripts, dependency metadata, a `build` directory, or unmanifested, package-manager, or install-time generated native output. The published manifest names no `better-sqlite3` dependency and defines no install-time lifecycle script, so an ordinary clean end-user `npm install` has no native compilation path.

The generated support manifest binds the exact upstream artifact integrity and source revision, binary-origin and build-material ledger, license/notice inventory, provenance and SBOM digests, every copied relative path, regular-file type, byte size and SHA-256 digest, the owned loader contract, and each native-binary tuple's exact binary. Every admitted full platform tuple separately retains its credential-backend, filesystem, lifecycle, and other evidence and maps through one total unambiguous native projection to exactly one native-binary tuple. Multiple full platform tuples may reference one binary only when their native projection is identical; an incompatible or ambiguous projection, multiple binaries for one native-binary tuple, or one binary entry claimed by distinct native-binary tuples is invalid. The loader validates the current native projection and loads only that native-binary tuple's manifest-named file through an explicit absolute path. It never uses upstream platform auto-detection, searches `node_modules`, accepts an environment or caller path, or falls back to `build/Debug`, `build/Release`, source compilation, download, or another binary. Missing, extra, nonregular, unloadable, provenance-incomplete, notice-incomplete, or checksum-mismatched evidence makes Local SQLite unavailable before credential, configuration, database, or lifecycle mutation.

An early native smoke may verify the owned loader and WAL reopen, but support admission requires the exact packed CLI on a pinned native image and claimed filesystem class to complete configuration, Reporter deadline/failure behavior, retention, search/get, Doctor, migration/upgrade, backup/restore, unconfigure, retained-data deletion, CLI upgrade, and uninstall without a source toolchain. Evidence admits only the stated baseline; widening a release or libc floor requires an explicit compatibility policy and additional boundary evidence.

**Context:** The package revision examined for this decision, `better-sqlite3@13.0.3` with npm integrity `sha512-RbOBxmLBG8uvFUc15X9+9SFemKcQ0WBuISBVkpuiaUB2qblC8UWlHEjdWVoZ8AdhSwmoEgsiXKfopX0CQxaACQ==`, declares Node 22 or newer and bundles macOS, Windows, glibc Linux, and musl Linux binaries for x64 and arm64. A clean install under the pinned workspace package manager otherwise attempts a native `node-gyp rebuild` despite those bundled files. Its published native source consumes the separately MIT-licensed header-only `node-addon-api`, while the package declares only a version range; the upstream workflow's install step does not by itself preserve an exact resolved compiled-input ledger. Therefore package integrity and npm publication provenance alone do not admit these prebuilds. The eight-file upstream binary inventory is input evidence, not an Agentscope support claim, and inclusion in the CLI is not support admission.

**Consequences:** The generated support documentation distinguishes base CLI support from this optional capability. The production tarball verifier proves the exact internal native closure, complete third-party notice and SBOM inventory, absence of dependency/install-script/build-source authority, ordinary clean installation with scripts enabled on a runner that has no compiler toolchain, and zero filesystem or subprocess evidence of compilation or download. Build-input tests start with an empty package store, prove no native material appears in workspace dependency metadata or `node_modules`, and use scripted direct/transitive, traversal, absolute/dot-dot, duplicate-last-wins, separator/case/Unicode alias, PAX/GNU indirection, link/device, sparse, truncation/trailing, compressed/expanded exact-limit and limit-plus-one fixtures to prove acquisition is bounded and never executes or automatically resolves package code. The verifier rejects every undeclared tuple/file, provenance, material, notice, or sandbox substitution; native execution happens only in the disposable test boundary and returns only its externally bound record. Dependency updates are explicit material-lock, source-provenance, build-material, license/notice, allowlist, manifest, artifact, sandbox-profile, and native-matrix changes. Build tools and an upstream package's bundled inventory cannot widen runtime support.

### ADR-008: Bind configuration and the database through one recoverable lifecycle

**Decision:** Version 1 owns `<agentscope-home>/destinations/local-sqlite/<connection-identity-digest>/traces.sqlite`; the digest is derived only from destination type and stable opaque connection identity, never mutable settings. Settings accept no path, URI, attach target, VFS, or remote endpoint. The concrete package projects physical evidence through the registered local-resource lifecycle capability; Application Core validates it and mints the one-use plan and exact Configuration authority without importing the package. Before plan presentation and again at apply/recovery, the capability re-resolves every existing ancestor, rejects final links and identity drift, proves containment and a supported local fixed-filesystem class, and binds that physical identity into the plan. The exact lifecycle capability version, contract fingerprint, and recovery-handler identity are bound into every plan, intent, recovery claim, shared lease, retained ownership receipt, backup receipt, and database metadata record. A release retains exact readers/recovery handlers while any advertised artifact can exist. Before a full handler is retired, an adjacent explicit migration must convert every authenticated artifact under the old handler; a permanent minimal tombstone-safe handler remains able to authenticate and delete the exact old database/backup family without interpreting payloads. Unknown identities remain inspection-only `reconciliation-required` and cannot be treated as current. A durable content-free lifecycle intent and recovery claim reciprocally fence Configuration Management CAS and every database open. Configure stages and migrates an owned candidate, commits the exact connection through authorized CAS, atomically activates and verifies the candidate, then clears the fence. Unconfigure creates a durable retained-database ownership receipt before removing the connection; the receipt preserves stable connection identity, deterministic path digest, file identity, format/ledger identity, lifecycle identity and generation but no path or trace content. Deletion first advances active and last-known-good configuration beyond the connection, then uses that receipt under the fence. Every crash prefix has only exact resume, rollback, cleanup, or reconciliation behavior.

**Context:** Configuration and SQLite are independent commit domains. Without a shared intent, a crash can leave either an orphan database or a configured missing file; without a retained receipt, unconfiguration destroys later deletion authority.

**Consequences:** Directory creation is umask-independent (`0700` and `0600` files, or current-user-only Windows ACLs). Reporter, Retriever, migration, backup, and restore use the same lease gate. A shared opener reads the fixed exclusive fence, validates a bounded inventory containing only exact live leases and no cleanup claim, exclusively creates and fsyncs a process/start-identity, lifecycle-identity, and lifecycle-generation lease, then recompiles that inventory and rereads the fence before opening. It admits other exact live shared leases, but any fence, cleanup claim, malformed or mismatched record, dead or indeterminate owner, missing own lease, or inventory race makes it retire only its exact lease and refuse to open. For hook reporting, the parent owns that exact lease and a fresh child nonce; before attempt permission it atomically amends and fsyncs the lease with the child's independently verified process/start identity. It grants the child only the matching bounded authority, joins the child on every settlement/cutoff/crash, revalidates the lease inode and complete owner tuple, and removes the lease through the shared-owner cleanup protocol before returning. That cleanup does not acquire the exclusive fence: the exact lease record is its durable authority. It exclusively creates and fsyncs `lease-cleanup-<lease-id>.json` as a hard link to that record, proves both names and the owner tuple, retires and fsyncs the public lease name, then removes the cleanup claim last. The only admitted per-lease states are `lease-only`, exact same-inode `lease+cleanup-claim`, `cleanup-claim-only`, and `absent`; any different pair is reconciliation-required. The live exact owner may resume the first three states with its in-process lease authority. An ordinary exclusive operation publishes and fsyncs its fixed fence, recompiles the complete inventory, and refuses to proceed while any lease or cleanup claim remains. Dead-lease recovery instead publishes and fsyncs a connection-scoped recovery fence whose immutable record binds its process/start owner plus the canonical ordered vector of every admitted dead-owner lease record, original per-lease state, and physical identity from the Core-minted plan. Before any recovery mutation, the handler opens and revalidates that exact fence inode, acquires one nonblocking operating-system advisory exclusive lock on the retained descriptor, and holds it through final fence removal. The first owner must match the record; a later owner may resume only after acquiring the automatically released lock and independently proving the recorded owner dead. A held lock is `busy`, so two live recoverers never advance the vector concurrently. The platform's descriptor-lock, process-death release, inherited-handle, and alias behavior is part of the fingerprinted native/full-platform support evidence; a platform without that proven primitive cannot admit Local lifecycle recovery. The first bounded rescan must reproduce the bound vector exactly and rejects any live or indeterminate lease owner, malformed or mismatched state, or unplanned lease/claim. Under that one fence it drains the vector in canonical lease-ID order: it creates the cleanup claim only from `lease-only`, resumes `lease+cleanup-claim` or `cleanup-claim-only`, never creates a second recovery-claim class, and removes the fence last. On restart, the fence authorizes only an exact suffix of its vector: every completed canonical prefix member must be absent, every later member must retain its bound identity and original state, and the first remaining member may additionally occupy only a later same-inode state in the admitted monotonic chain. Any gap, reordered survivor, changed identity, unexpected entry, or non-prefix absence is reconciliation-required. An empty suffix means cleanup completed and authorizes only final fence removal. Interruption therefore has one authenticated residual state, and two or more crashed cleanup claims cannot block one another permanently. Parent-death containment terminates the child. Child crash cannot strand an undiscoverable live lease once the parent joins. Each connection permits at most 64 exact 256-byte lease records and at most one same-ID cleanup claim per lease in one closed fixed-length filename namespace. The complete lifecycle inventory permits at most 192 entries and 96 KiB: at most 128 lease/cleanup-claim entries plus the existing 64-entry and 64-KiB nonlease metadata budget. Full, malformed, duplicate, extra, oversized, or over-budget inventory blocks every new open with `reconciliation-required` rather than truncating or partially scanning. Doctor never creates a lease, advances a cleanup claim, or opens SQLite. It performs only bounded no-follow reads, a nonblocking probe of the exact recovery-fence descriptor lock that it immediately releases when acquired, and final identity/inventory revalidation. Failure to prove one stable inspection is `unavailable`; otherwise malformed, mismatched, duplicate, unowned, unknown-handler, or noncanonical evidence is `reconciliation-required`; otherwise any exact live or indeterminate lease owner or held recovery lock is `busy`; otherwise one or more admitted dead-owner states is `recovery-required`; the remaining empty admitted inventory is `clean`. Migration, backup, restore, and deletion hold the exclusive fence; Reporter and Retriever use shared leases. Fence recovery and fixed-to-claim handoff follow Configuration Management's monotonic read order and ADR-010's namespace-mutation boundary. Deletion closes the database through SQLite so persistent WAL is recovered safely, revalidates the complete manifest-owned database family and physical namespace, and removes only authenticated artifacts without recursive directory deletion. Doctor reports the bounded inventory but never repairs or deletes it automatically.

### ADR-009: Backup and restore through verified candidates

**Decision:** Backup and restore use only an owned `<connection-namespace>/backups/<backup-identity>.sqlite` inventory; version 1 accepts no external path. One connection admits at most eight published backups and at most 32 total backup-directory entries. Every published snapshot, candidate, and rollback preimage is individually no larger than the support manifest's fixed maximum snapshot bytes `M`; published snapshot files additionally have aggregate bytes no greater than checked `8 × M`; receipts and other bounded metadata have a separate 64 KiB aggregate/scan ceiling; one active transaction may additionally own at most one candidate and one rollback preimage. Sizes and sums use exact nonnegative filesystem integers with checked multiplication/addition; overflow, sparse/huge evidence, `M + 1`, or aggregate `8 × M + 1` is over-budget. Transient transaction roles do not count as published snapshots, but the complete namespace ceiling is the checked sum of the published, metadata, and two transient-role ceilings, so every admitted crash prefix remains valid. Every listing and collision proof is bounded by those counts and bytes; malformed, extra, oversized, or over-budget evidence is reconciliation-required, while a valid inventory that lacks capacity rejects a new backup before mutation with `destination-capacity`. Core generates each backup identity from a fresh nonzero 128-bit random value encoded as exactly 32 lowercase hexadecimal characters; callers can select only an identity returned by the durable receipt. Before I/O, physical collision checks use the platform filesystem identity rather than spelling and cover every case/Unicode alias among the bounded backups, receipts, active SQLite artifacts, lifecycle records, candidates, and rollback preimages. Backup is an explicit plan-first operation that completes authorized retention cleanup, uses SQLite's online backup API to write one exclusive-created user-restricted candidate, verifies integrity plus exact schema, migration, destination-format, and stored Protocol compatibility identities, then atomically publishes it with the receipt and never overwrites an existing identity. Restore selects one authenticated receipt and runs under the exclusive lifecycle fence. It opens the backup read-only without following a link, revalidates every physical ancestor and role collision, copies through the backup API into an owned same-directory candidate, verifies it through the current Protocol compiler, transactionally applies the current trusted cutoff and count/byte retention limits to that candidate, revalidates all invariants, atomically replaces the active database while retaining the rollback preimage, and removes that preimage only after reopen verification. The lifecycle intent authenticates each stage and makes every crash prefix resumable or reversible. Tests pin `M`, `M + 1`, aggregate equality and overflow, sparse/huge stats, and every candidate/preimage crash prefix.

**Context:** Copying the main file of an open WAL database can omit committed state, while restoring in place can destroy the last compatible database before validation.

**Consequences:** The complete active, backup, and lifecycle namespace uses the same plan-bound physical identity, supported filesystem classification, no-follow apply-time recheck, exclusive-create, flush, atomic rename, directory-sync, and collision closure. Active-database deletion does not delete backups; deleting a backup is a separate confirmed receipt-bound operation. Restore cannot change connection identity, path, retention settings, or configuration. Unsupported Protocol/schema identities, corruption, links, busy leases, and failed replacement are content-free failures that preserve the active database. Tests cover concurrent reporting, WAL state, interruption at every durable prefix, mode/ACL preservation, incompatible readers, and exact rollback.

### ADR-010: Preserve inode authority across namespace mutation

**Decision:** Every interactive operation that removes, publishes, or replaces a Local SQLite name runs under the exclusive lifecycle fence and a durable operation intent, and pins each exact source and last-compatible destination inode with a same-filesystem hard-link claim or rollback preimage before changing a public name. Shared-lease release is the sole narrow exception: ADR-008's exact lease record and lease-cleanup claim are its durable authority and preserve shared-to-exclusive ordering without acquiring the fence it is releasing. Each protocol fsyncs its claims and containing directory, performs only descriptor-relative no-follow namespace operations, and immediately recompiles the complete bounded public-and-claim inventory. Success requires the exact authority-recorded inode mapping. An interruption or any other observed mapping retains every authenticated record and claim and returns `reconciliation-required` or `outcome-unknown` as appropriate. Recovery operates only from those durable authorities and either establishes the exact candidate mapping, restores the exact last-compatible mapping, or leaves all still-identifiable inodes preserved for explicit reconciliation.

The supported concurrency authority covers every Agentscope process through the fixed lifecycle fence, leases, and claims. Portable unprivileged local-filesystem APIs do not offer a conditional operation equivalent to “unlink or rename this name only if it still identifies inode X.” An out-of-band actor running as the same operating-system principal can therefore change a directory entry between the kernel's last identity observation and a pathname-based namespace syscall. Such interference is external filesystem corruption and is outside the supported concurrency boundary. A pathname syscall may already have moved or removed the substituted entry before a post-operation proof detects the mismatch; when the mismatch is observable, it cannot count as success or authorize any further access or cleanup. Agentscope does not claim zero transient namespace movement or conditional deletion against that actor. A platform may advertise a stronger boundary only when its support manifest names the exact primitive and immutable-candidate evidence proves the stronger result.

**Context:** A check followed by `unlink`, `rename`, or exchange is not an inode-conditional transaction. Pretending otherwise makes exact-file deletion and rollback claims unimplementable on the supported POSIX baseline. Treating every mismatch as ordinary failure is also unsafe because the namespace may already have changed before the mismatch became observable.

**Consequences:** Under the supported Agentscope-controlled lifecycle namespace, user-confirmed deletion destroys only the inode authenticated by the retained ownership receipt and operation claims. Restore always pins the last compatible database bytes until the candidate mapping is proven after reopen. Claim names, maximum counts, byte ceilings, and every public/claim/preimage mapping are part of the fingerprinted artifact grammar and Doctor inventory. This decision lands before any Local SQLite full-platform tuple or lifecycle artifact is eligible for publication or support admission, so it replaces the pre-admission lifecycle-v1 grammar and fingerprint rather than migrating an advertised predecessor. The first admitted artifact remains capability version 1 with this exact grammar; artifacts from earlier proposed or development-only candidates have no release authority and are inspection-only `reconciliation-required`. After that first admission, every grammar change requires a successor capability and fingerprint, an adjacent transform where migration is possible, retained exact historical recovery or tombstone handling, and predecessor upgrade evidence. Tests cover each pre-claim, post-claim, namespace-syscall, post-syscall, directory-sync, reopen, and cleanup interruption prefix. Out-of-band substitution tests prove every observable mismatch stops before further I/O or cleanup, retains every still-identifiable artifact, and reports reconciliation rather than a successful delete or restore; they do not claim that an unprivileged pathname syscall can retroactively undo an undetectable same-principal replacement.
