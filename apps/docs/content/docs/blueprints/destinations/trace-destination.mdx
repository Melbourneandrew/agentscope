title: Trace Destination
description: ADRs for connecting harness data to destination capabilities.

## Capability Summary

A Trace Destination is the configured local or remote trace repository or service that receives captured canonical traces through one mandatory reporter and may expose them through an optional retriever. A native trace source remains the local harness artifact from which an adapter captures evidence.

## Architecture Decision Records

### ADR-001: Make Trace Destination the user-configured connection

**Decision:** A Trace Destination owns one local or remote destination's non-secret configuration, mandatory reporting capability, and optional retrieval capability. Core owns selection and routing across named Trace Destinations.

**Context:** Users configure a logical service connection, not an unconnected reporter implementation; cross-connection selection needs one authoritative policy owner.

**Consequences:** `agentscope destination configure langfuse` creates a named destination connection reusable by many harnesses.

### ADR-002: Keep extraction outside Trace Destination

**Decision:** Harness adapters produce transient captures; Core converts them into branded redacted canonical batches. Trace Destinations accept only that branded type and never parse harness artifacts.

**Context:** This keeps a destination reusable across harnesses and makes reporter integration testable independently.

### ADR-003: Let first-party destinations declare their own validated shape

**Decision:** Each first-party destination package exports an internal `DestinationDescriptor`: one stable package-form destination type identity, one positive integer settings version, a strict Zod schema and defaults for non-secret connection settings, declared credential slots, a mandatory synchronous reporter factory, a local-or-remote transport declaration, and a documentation reference. The application layer owns opaque connection identities and the outer configuration document. Retriever capability extends this descriptor when the Retriever contract lands. A local destination may additionally declare one versioned first-party local-resource lifecycle capability through the destination-family contract; its closed operation inventory, settings schema, durable-artifact grammar, receipt-reason inventory, and recovery-handler identity produce one exact capability fingerprint. Application Core owns its process-branded plan and Configuration Management authority, while the registered concrete package owns only its bounded filesystem/database preparation, inspection, activation, and recovery operations. This capability is neither an untyped callback nor a public plugin seam.

**Context:** Langfuse, local SQLite, and remote database services need different settings, but destination-specific CLI commands would make the command tree inconsistent and force users and agents to learn unrelated surfaces.

**Consequences:** `agentscope destination configure <type>` is one generic command. It resolves the first-party descriptor, accepts its documented flags or non-interactive input, validates the shape with Zod, reconstructs fresh bounded JSON-safe settings, writes atomically, and stores credential references—not secret values. Descriptor compilation accepts only declarative Zod behavior represented exactly by a bounded strict JSON Schema; custom refinements, transforms, preprocessing, coercion, defaults, and other callback-backed semantics are rejected. First-party modules materialize every Zod object shape before descriptor handoff; compilation rejects shape accessors and executes no caller callback. Runtime parsing uses a privately rebuilt and sealed validator compiled from that machine-readable schema, never the caller-owned Zod object. Defaults pass through the detached validator. Unknown, stripped, expanded, credential-shaped, asynchronous, or non-JSON schema results fail with a fixed diagnostic. Settings versions are unrelated to package, Protocol, envelope, or lifecycle-capability versions; a future settings or lifecycle migration must be an explicit adjacent transform and is never run implicitly at hook time. Every durable local-resource artifact binds its exact capability fingerprint, and Application Core dispatches only to a retained exact recovery handler or returns reconciliation-required. A local lifecycle implementation receives only the exact connection, validated settings, resolved Agentscope home, deadline, and one-use lifecycle/Configuration authority needed for the selected operation; it cannot mint a plan, select another connection, or write configuration directly. A descriptor is normal reviewed first-party code, not a runtime plugin ABI.

### ADR-004: Separate family contracts from destination implementations

**Decision:** `packages/destinations/core` owns the destination-family contracts introduced by each delivery slice: `DestinationDescriptor`, `Reporter`, later `Retriever`, portable request/result DTOs, capability declarations, fixed error taxonomy, and contract-test entry points. It depends only on Protocol and deliberately approved low-level schema libraries. `packages/core` depends on those ports to perform configuration resolution, credential binding, routing, retrieval safety, and deadline orchestration; it never imports a concrete destination.

**Context:** Putting the contracts in a concrete destination would leak provider concepts inward. Making destination family Core depend on application Core would create a dependency cycle once Core orchestrates retrievers.

**Consequences:** Concrete destination packages depend on destination family Core and Protocol. The CLI is the composition root that registers concrete descriptors with Core. These internal contracts make first-party implementations consistent but are neither a public SDK nor a runtime plugin ABI.

### ADR-005: Keep destination data and credentials out of configuration

**Decision:** The configuration document contains non-secret connection settings and credential references only. A local destination owns its opted-in data beneath `<agentscope-home>/destinations/<type>/<connection-identity-digest>/`; its Blueprint defines the closed file family and lifecycle within that namespace. Remote credentials resolve through an OS credential store or explicit CI environment reference.

**Context:** Configuration must remain safe to inspect, back up, and migrate. A local data file and a remote token have different retention and access-control properties.

**Consequences:** Agentscope home never contains a Langfuse key or remote database secret. It contains a local trace payload only when a user explicitly configures and selects a durable local destination.

### ADR-006: Apply one remote endpoint security baseline

**Decision:** A remote descriptor projects one endpoint candidate from already validated non-secret settings. Destination-family Core first resolves an opaque prepared connection containing that canonical validated endpoint; only then may Application Core bind its executor, resolve the declared credential slots, and construct the reporter. HTTPS is required, while plain HTTP is allowed only for literal `127.0.0.0/8` or `::1` loopback behind an explicit insecure setting. User information, query strings, fragments, opaque schemes, and port zero are rejected. The reporter receives an opaque credential accessor plus an origin-bound transport capability. Authority to prepare connections, mint deadlines, bind executors, and invoke reporters is exposed only through the Core-restricted orchestration subpath; concrete destinations cannot mint it. Authenticated redirects must be handled manually and remain on the bound origin.

**Context:** Secure storage does not protect a credential or redacted trace from a malicious endpoint, typo, plaintext transport, or origin-changing redirect.

**Consequences:** The prepared-connection phase accepts no credentials or executor, so origin validation necessarily precedes both credential resolution and reporter construction. The bound transport rejects an expired deadline or aborted signal immediately before executor invocation, accepts only same-origin relative requests, forbids authority-changing headers, snapshots bounded bytes, and returns bounded content without exposing provider bodies through receipt or diagnostic types. A destination may narrow the rules. Doctor reports insecure, redirecting, and origin-mismatched configuration without resolving or printing the secret. Mock services use the explicit loopback-insecure path or HTTPS test certificates.
