## Capability Summary

Hook installation writes the minimal owned integration that allows a harness to invoke Agentscope capture.

## Architecture Decision Records

### ADR-001: Use a conflict-safe installation transaction

**Decision:** Adapters generate an identifiable Agentscope-owned block through Harness Core's versioned launcher metadata and classify each inspected target as unchanged, owned replacement/removal, overlapping replacement, conflict, or unsupported. Harness Core accepts only canonical absolute path spellings, resolves every existing ancestor before deriving a physical path identity, rejects a final symbolic link, and applies conservative case-folded identity on Windows plus convergent canonical Unicode caseless identity in decomposed form on Darwin so one filesystem entry cannot acquire two transaction namespaces. It reads at most sixteen regular-file targets through no-follow handles under a 1 MiB per-target ceiling, supplies fresh byte copies to the first-party planner, and returns an opaque process-branded one-use plan. Applying that plan rechecks every preimage SHA-256 digest and mode before mutation. Core exclusively creates one canonical owned transaction manifest containing only the transaction identity, target paths, exact before/after existence, digests and modes, deterministic same-directory stage/backup names, and commit state. It derives artifact and ownership names from that physical, platform-aware target identity and rejects any collision among the manifest, manifest temporary, targets, stages, backups, ownership candidates, markers, and claims before admitting either a new plan or recovery manifest. Recovery re-resolves the complete stored namespace and rejects an identity change before interpreting transaction state. Staged outputs and unavoidable recovery backups are then written exclusive, explicitly chmod-bound independent of process umask, flushed, and directory-synced. A recovered `prepared` manifest must prove every required stage and backup exists with its exact digest and mode before ownership publication or the `committing` transition. Before target mutation, the transaction hard-links its exact transaction-owned candidate into one deterministic per-target turnover claim, then publishes and directory-syncs the matching ownership marker. The turnover claim serializes marker replacement; a claim or marker whose referenced manifest still exists blocks every other manifest. A completed marker may be replaced only while the next exact claim is held and only after its prior manifest is absent. The claim is removed before the completing manifest; if cleanup stops in that interval, the exact committed manifest and marker may reconstruct only their matching claim and finish cleanup. The manifest enters `committing` before any target rename, and only that state plus the exact claim and marker may recognize an already-committed postimage. Each target is atomically renamed only after a second precondition and staged-artifact digest-and-mode check. The manifest itself is durably replaced as the state changes, and every final target is read back and digest-and-mode verified before directory-synced cleanup.

**Context:** Vendor-owned files can contain credentials and can change concurrently. A snapshot alone does not make rollback safe.

**Consequences:** A crash after manifest creation is recoverable without storing target bytes inside the manifest. Resume infers each target from its exact preimage/committed digest and mode and finishes only compatible work. A `prepared` manifest may continue only from its exact preimage; it cannot adopt a matching postimage produced by another transaction. Cancelling a `prepared` manifest never inspects or mutates a target because that durable state proves no target rename began; it removes only artifacts and exact ownership records belonging to that manifest. Resume and rollback of later states require every exact per-target ownership marker, and terminal cleanup may reacquire a missing matching claim only from that marker plus its still-present canonical manifest. Rollback walks targets in reverse and restores or removes a target only when its current digest and mode still equal the transaction's committed value; an already-restored preimage is left untouched, while any third value reports conflict for explicit resolution. The latest completed ownership marker remains as a bounded non-content receipt until a later transaction atomically claims that target; transaction candidates, stages, backups, and manifests use only deterministic paths rederived from transaction and target identity and are directory-synced during creation and cleanup. Preimages remain in memory where possible; unavoidable same-directory recovery backups preserve source permissions, are excluded from diagnostics, and are removed after verified commit or rollback. Paths, hashes, configuration bytes, native errors, and callback values never enter returned result DTOs. Formats that cannot classify ownership or provide this replacement/recovery contract are unsupported for mutation.

### ADR-002: Detect conflicts before modifying hooks

**Decision:** An adapter reports overlapping Agentscope/vendor hooks with the distinct `replace-overlap` decision. Harness Core treats that decision as conflict for install and uninstall plans and permits it only when the caller selected the explicit migration operation. Ordinary owned replacement and removal never imply migration authority.

**Consequences:** Dry-run is the default diagnostic path; failure rolls back only verified unchanged Agentscope-owned targets. Install, resume, rollback, uninstall, and Doctor share this state machine.

### ADR-003: Verify installation in fresh machine-like environments

**Decision:** The integration matrix installs the packed CLI and each harness adapter into a fresh isolated container before exercising its owned hook.

**Context:** A developer's globally installed binary or preexisting harness configuration can hide missing package assets, installation assumptions, or upgrade regressions.

### ADR-004: Bind hooks to an owned launcher and versioned contract

**Decision:** Installation writes the exact stable launcher path owned by [CLI Installation ADR-002](/docs/blueprints/operations/cli-installation) with separately encoded arguments; it never invokes through a shell or searches hook-time `PATH`. Harness Core contract version 1 fixes the complete argument vector to `capture-hook-v1`, `--contract-version`, `1`, `--harness`, and one exact first-party harness registry identity, in that order with no extra token. It derives a stable `agentscope-hook-v1-sha256-*` ownership identity from the absolute launcher path, contract version, and exact argument vector. Each format-specific owned block records that metadata and calls the internal machine-facing capture entry point.

Contract version 1 transports per-invocation context evidence only on standard input as one EOF-framed opaque byte sequence. The launcher and Core copy it exactly once as a fresh immutable value, accept from zero through 65,536 bytes, read at most 65,537 bytes to prove the bound, and require EOF. They do not interpret it as command arguments, environment, a path, JSON, text, or a durable artifact. The exact first-party adapter selected by `--harness` owns native decoding under its descriptor and compatibility range. Empty, malformed for that adapter, truncated, oversized, accessor-backed test input, read failure, abort, or expiry produces only the fixed fail-open lifecycle result. The stream is never logged, echoed, persisted, included in ownership identity, or forwarded to a destination except through the ordinary transient capture, redaction, and branded routing lifecycle.

**Context:** Persisted harness configuration outlives individual installs, and GUI/non-login environments may resolve a bare command differently.

**Consequences:** The launcher conveys its verified machine-home authority directly to the bundled hook entry point; it never trusts a project-inherited `AGENTSCOPE_HOME`. The internal command writes no stdout or stderr, returns success to the harness after every handled outcome, and exposes no human or structured CLI presentation contract. An operating-system failure to start the launcher is ignored by the installed harness-owned block. Unknown, duplicate, reordered, missing, or additional arguments suppress capture without fallback parsing, version guessing, or mutation. Doctor verifies launcher ownership, location, release identity, home authority, and contract compatibility. Installation upgrades compatible launchers transactionally; unsupported hook or launcher versions remain untouched pending explicit migration. Tests cover exact argument encoding, stdin boundaries and EOF, malformed and oversized evidence, environment redirection, relocation, upgrade, downgrade, deadline, zero-output fail-open capture, and uninstall.
