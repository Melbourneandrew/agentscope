## Capability Summary

Hook installation writes the minimal owned integration that allows a harness to invoke Agentscope capture.

## Architecture Decision Records

### ADR-001: Use a conflict-safe installation transaction

**Decision:** Adapters generate an identifiable Agentscope-owned block through Harness Core's versioned launcher metadata and classify each inspected target as unchanged, owned replacement/removal, overlapping replacement, conflict, or unsupported. Harness Core reads at most sixteen absolute regular-file targets through no-follow handles under a 1 MiB per-target ceiling, supplies fresh byte copies to the first-party planner, and returns an opaque process-branded one-use plan. Applying that plan rechecks every preimage SHA-256 digest and mode before mutation. Core exclusively creates one canonical owned transaction manifest containing only the transaction identity, target paths, exact before/after existence, digests and modes, deterministic same-directory stage/backup names, and commit state. It rejects any collision among the manifest, manifest temporary, targets, stages, backups, ownership candidates, markers, and claims before admitting either a new plan or recovery manifest. Staged outputs and unavoidable recovery backups are then written exclusive, explicitly chmod-bound independent of process umask, flushed, and directory-synced. Before target mutation, the transaction hard-links its exact transaction-owned candidate into one deterministic per-target turnover claim, then publishes and directory-syncs the matching ownership marker. The turnover claim serializes marker replacement; a claim or marker whose referenced manifest still exists blocks every other manifest. A completed marker may be replaced only while the next exact claim is held and only after its prior manifest is absent. The claim is removed before the completing manifest; if cleanup stops in that interval, the exact committed manifest and marker may reconstruct only their matching claim and finish cleanup. The manifest enters `committing` before any target rename, and only that state plus the exact claim and marker may recognize an already-committed postimage. Each target is atomically renamed only after a second precondition and staged-artifact digest-and-mode check. The manifest itself is durably replaced as the state changes, and every final target is read back and digest-and-mode verified before directory-synced cleanup.

**Context:** Vendor-owned files can contain credentials and can change concurrently. A snapshot alone does not make rollback safe.

**Consequences:** A crash after manifest creation is recoverable without storing target bytes inside the manifest. Resume infers each target from its exact preimage/committed digest and mode and finishes only compatible work. A `prepared` manifest may continue only from its exact preimage; it cannot adopt a matching postimage produced by another transaction. Cancelling a `prepared` manifest never inspects or mutates a target because that durable state proves no target rename began; it removes only artifacts and exact ownership records belonging to that manifest. Resume and rollback of later states require every exact per-target ownership marker, and terminal cleanup may reacquire a missing matching claim only from that marker plus its still-present canonical manifest. Rollback walks targets in reverse and restores or removes a target only when its current digest and mode still equal the transaction's committed value; an already-restored preimage is left untouched, while any third value reports conflict for explicit resolution. The latest completed ownership marker remains as a bounded non-content receipt until a later transaction atomically claims that target; transaction candidates, stages, backups, and manifests use only deterministic paths rederived from transaction and target identity and are directory-synced during creation and cleanup. Preimages remain in memory where possible; unavoidable same-directory recovery backups preserve source permissions, are excluded from diagnostics, and are removed after verified commit or rollback. Paths, hashes, configuration bytes, native errors, and callback values never enter returned result DTOs. Formats that cannot classify ownership or provide this replacement/recovery contract are unsupported for mutation.

### ADR-002: Detect conflicts before modifying hooks

**Decision:** An adapter reports overlapping Agentscope/vendor hooks with the distinct `replace-overlap` decision. Harness Core treats that decision as conflict for install and uninstall plans and permits it only when the caller selected the explicit migration operation. Ordinary owned replacement and removal never imply migration authority.

**Consequences:** Dry-run is the default diagnostic path; failure rolls back only verified unchanged Agentscope-owned targets. Install, resume, rollback, uninstall, and Doctor share this state machine.

### ADR-003: Verify installation in fresh machine-like environments

**Decision:** The integration matrix installs the packed CLI and each harness adapter into a fresh isolated container before exercising its owned hook.

**Context:** A developer's globally installed binary or preexisting harness configuration can hide missing package assets, installation assumptions, or upgrade regressions.

### ADR-004: Bind hooks to an owned launcher and versioned contract

**Decision:** Installation writes an Agentscope-owned absolute launcher or verified shim with separately encoded arguments; it never invokes through a shell or searches hook-time `PATH`. Harness Core contract version 1 fixes the command token `capture-hook-v1`, the `--contract-version 1` pair, and one exact first-party `--harness` registry identity. It derives a stable `agentscope-hook-v1-sha256-*` ownership identity from the absolute executable path, contract version, and exact argument vector. Each format-specific owned block records that metadata and calls the versioned machine-facing capture entry point; bounded per-invocation context evidence remains a separately copied runtime value and is not part of the installed ownership identity.

**Context:** Persisted harness configuration outlives individual installs, and GUI/non-login environments may resolve a bare command differently.

**Consequences:** The launcher resolves the machine-default Agentscope home through the owned Configuration Management contract and conveys that approved authority to the hook entry point; it never trusts a project-inherited `AGENTSCOPE_HOME`. Doctor verifies launcher ownership, location, home authority, and contract compatibility. Installation upgrades owned blocks transactionally; unsupported versions remain untouched pending explicit migration. Tests cover argument encoding, environment redirection, relocation, upgrade, downgrade, capture, and uninstall.
