## Capability Summary

This Blueprint realizes [Configuration Directory](/docs/requirements/configuration-directory) for a TypeScript CLI.

## Architecture Decision Records

### ADR-001: Resolve one cross-platform machine-local root

**Decision:** Resolve the default home with Node's `os.homedir()` and `path.join(home, ".agentscope")`: `~/.agentscope` on macOS/Linux and `%USERPROFILE%\\.agentscope` on Windows. Installed hooks and ordinary commands ignore ambient `AGENTSCOPE_HOME`. The variable replaces the complete resolved home only when an owned invocation explicitly declares the closed `ci`, `portable`, or `test` override authority; launcher/install composition conveys the already resolved home rather than inheriting a project process environment.

**Context:** Users and hook processes need a predictable support surface without Unix-only path assumptions; hermetic tests need one clean override.

**Consequences:** Every CLI command, hook, Core service, and harness adapter receives the same injected home resolver. No package derives its own path from `$HOME`, `~`, a shell expansion, a project-local environment file, or a platform-specific environment variable. Tests prove that an ambient override cannot redirect an installed-style resolution and that each explicit override authority is opt-in.

### ADR-002: Use one fenced compare-and-swap mutation service

**Decision:** Configuration Management solely owns a fenced compare-and-swap mutation service. Core accepts only a branded, current, mutation-safe snapshot whose generation is exactly one greater than the caller's expected generation. It canonical-serializes that snapshot, records the expected and candidate byte digests in an exclusively created immutable lock, fsyncs the lock directory, writes and fsyncs same-directory candidate and backup stages, atomically replaces the bounded last-known-good backup, revalidates the active generation and exact prior digest, then atomically replaces the fixed active config path and fsyncs its directory.

**Context:** Atomic rename prevents torn writes but does not prevent two valid writers from overwriting each other. One small configuration document does not need a second active-version pointer.

**Consequences:** Every mutating command uses this transaction service. Lock records contain a random transaction identity, process ID, process-start identity, exact prior/candidate generations and digests, and transaction-owned stage names; they contain no configuration or credential content. A writer rechecks its exact lock immediately before active replacement. A live or indeterminate owner is never repaired. After the owner is independently proven dead, one recovery creates a fixed same-filesystem hard-link claim with exclusive-create semantics, fsyncs it, revalidates both names and the owner, removes the original fixed name, and performs cleanup only through the claimed inode. Writers check the claim both before and after creating their fixed lock, and abandon only their exact lock if a claim appeared. Competing recoverers, a substituted fixed lock, or delayed cleanup therefore cannot unlink a replacement writer. Any recovery claim is conservatively reported as `reconciliation-required`, blocks writers, and is never guessed active or stale, whether or not the original fixed name remains. Recovery accepts only an active document whose canonical bytes exactly match either the prior or committed candidate evidence and otherwise refuses repair. The active document is always canonical UTF-8 JSON with a bounded byte size; noncanonical, duplicate-key-bearing, malformed, symlinked, or oversized input is never copied into the backup. Hooks ignore lock contents, perform no migration or mutation, and return a fixed fail-open unavailable result when the active snapshot cannot be safely read. Interactive callers apply an exact adjacent pure migration registry before proposing a CAS candidate; future versions and incomplete migrations refuse downgrade. Doctor reuses the same parser and dead-owner evidence evaluation for a non-mutating inspection, and its explicit repair delegates to this exact recovery operation; backup restoration, interrupted-claim reconciliation, and any broader repair remain separate explicit recovery commands.

### ADR-003: Resolve every effective value once with provenance

**Decision:** Core resolves one immutable hook-start snapshot with deterministic precedence: descriptor defaults, validated persisted non-secret settings, then narrowly allowlisted command-scoped overrides. The owned launcher authority supplies its verified machine home, exact adapter identity, configuration generation and canonical configured-duration copy, plus the one-shot bounded stdin evidence loader defined by Hook Installation ADR-004. The launcher creates the hook deadline from that bounded duration before ownership verification or invoking the loader. Core freezes the copied evidence with configuration and effective policy and requires the persisted generation and duration to equal the launcher authority. The registered pure context projection and Core-owned workspace/Git resolver then complete the same snapshot before adapter capture execution. Environment variables supply credential values only through persisted explicit references unless a setting explicitly permits otherwise. Every effective non-secret value carries sanitized source provenance.

**Context:** Init, hooks, Doctor, and interactive commands must not resolve the same connection differently or allow project-local environment to redirect machine-owned routing.

**Consequences:** Every entry point receives the same snapshot. A hook never rereads configuration, process cwd, policy material, or Git state after capture starts. An invalid or unavailable configuration/policy or a generation/duration mismatch produces only the fixed pre-brand diagnostic and fail-open suppression defined by Canonical Trace Format ADR-002. A user-approved duration change first durably creates and fsyncs one bounded non-content reconciliation intent naming the exact prior/candidate configuration generations and durations plus the canonical set of affected launcher ownership identities. Configuration writers and hook installers check the fixed intent and its recovery claim before and after acquiring their own locks; only the exact Core-minted reconciliation authority may cross both fences. A shortening replaces every owned launcher/block before committing the shorter configuration; a lengthening commits configuration before replacing the launchers/blocks. Every intermediate mismatch therefore suppresses capture, and no active block can retain a deadline longer than the committed duration. Recovery claims the intent using the existing dead-owner proof, accepts only exact recorded preimages or candidates in both transaction domains, and deterministically completes or rolls back the whole direction-specific sequence; substituted, missing, mixed, or unowned state becomes `reconciliation-required` and never guesses. The intent clears only after configuration and every installed launcher/block are durably revalidated at one matching generation/duration, after which superseded launchers are retired. Doctor exposes only the closed state and explicit reconciliation action. It can otherwise explain effective destination, endpoint, routing, policy mode, and rule-source provenance without exposing references, selectors, paths, or matched content; forbidden overrides are rejected before mutation or delivery.

### ADR-004: Version and compose one secret-safe outer document

**Decision:** Core owns strict outer configuration version 2 containing a nonnegative mutation generation, destination package namespaces, a policy reference, and routing policy version 1. Routing version 1 contains an unconditional explicit set of at most 32 connection identities and one integer hook duration from 50 through 60,000 milliseconds; an empty set means delivery disabled. The adjacent outer-configuration migration from version 1's prior routing shape writes the reviewed 2,000 millisecond default, so hook-time parsing never invents or silently defaults it. A known first-party destination namespace is accepted only when its settings version and every connection block pass the registered `DestinationDescriptor`; connection identities are stable opaque IDs, globally unique names are presentation selectors, and every routed identity names one exact known connection. Duplicate or unknown routed identities reject a mutation before hook time. Credential fields accept only closed non-secret OS-store references or explicit CI environment-variable references, never values.

**Context:** Destination packages own their local settings meaning, but they cannot own cross-connection identity, routing, credential persistence, or downgrade safety. An older atomic CLI can encounter a namespace introduced by a newer release.

**Consequences:** A tolerant read reconstructs and freezes bounded plain JSON, preserves an unknown valid first-party destination namespace exactly, and marks the snapshot unsafe to mutate. A selected identity under an unsupported preserved namespace also makes the hook snapshot unavailable rather than guessing its connection meaning. Current-version mutation is allowed only when every namespace is registered and the complete composed document validates. The hook snapshot freezes selected connections in canonical identity order and the exact configured duration; array order has no priority semantics. Configuration contains no trace payload, canonical graph, credential value, endpoint secret, conditional value selector, or arbitrary top-level extension bag. The compare-and-swap service owns serialization and downgrade refusal in ADR-002; schema parsing alone performs no filesystem mutation.

### ADR-005: Store credential references through explicit backend adapters

**Decision:** Core owns a closed credential-backend registry for macOS Keychain, Windows Credential Manager, Linux Secret Service, and an explicit CI environment-reference adapter. Before stored-credential creation or backup retirement it exclusively persists and fsyncs one bounded credential mutation intent containing only the operation, backend, deterministic opaque reference, ownership tuple, generation, and process/start owner; it contains no credential value. A stored credential is then created as that pending ownership-bound generation, resolved through the hook-equivalent path, committed only as its opaque reference through ADR-002, and activated. The intent is removed only after the configuration commit has become durable ownership authority or after proven compensation. Retirement retains the intent across configuration advance and credential deletion, so a crash after the reference-free backup commit remains discoverable and resumable. Post-commit activation failure remains discoverable through the committed reference. CI resolution reads only the exact persisted environment-variable reference as an own data property; it never enumerates or copies the environment.

**Context:** Configuration changes span two independent commit domains: an operating-system credential store and the canonical configuration document. Neither domain can participate in the other's atomic rename, while hooks must resolve the same reference without exposing its value.

**Consequences:** Once a stored-backend creation call begins, any failure is conservatively treated as possibly committed and returns the already-derived opaque reference while retaining the intent; a later proof-bound cleanup may safely remove that exact owned generation even when the backend actually created nothing. Before configuration commit, other failures compensate only the intended pending generation; failed or interrupted compensation retains the intent as discoverable orphan evidence. The credential-intent name and the configuration-transaction name are reciprocal fences: each creator checks the other before and after exclusive creation, and a configuration write may cross an active intent only with the exact Core-minted intent authority used by that credential lifecycle. Credential-intent recovery uses the same fixed hard-link claim gate. Every configuration writer reads the fixed intent before the recovery claim, so the monotonic fixed-to-both-to-claim handoff cannot be observed as fence-free; every observed claim rejects the write. The intent/claim therefore remains held across the final active-plus-backup absence proof and irreversible backend deletion, so another process cannot reintroduce the reference in that interval. Any credential recovery claim is reported as `reconciliation-required`, not active, whether or not the original intent name remains. After configuration commit, failed activation records `referenced-pending` and never deletes the referenced value. A dead-owner creation intent whose reference is absent from both active and last-known-good configuration is cleaned up only by removing that exact owned generation through its declared backend and then deleting the claimed intent; an intent whose exact reference is already configuration-owned is cleared without deleting the credential. Rotation or removal first commits a reference-free candidate. A separate explicit retirement operation writes the retirement intent, advances one otherwise identical configuration generation so the bounded backup is also reference-free, revalidates both documents, deletes the superseded owned credential, and only then clears the claimed intent. Recovery clears a pre-commit retirement intent while the reference remains configuration-owned, or resumes exact owned deletion after the reference-free commit; deletion failure retains the claim. The raw purge primitive is Core-private and requires the exact active intent. Doctor only reports this condition because deletion is irreversible. CI values are never deleted as credentials and do not use the stored-credential intent. Resolution returns a process-local opaque capability, and all expected failures/results are closed and content-free: credential values never enter configuration, mutation intents, diagnostics, logs, command arguments, receipts, or serialized result objects. [CLI Installation ADR-003](/docs/blueprints/operations/cli-installation) owns the support manifest and native-runner evidence for operating-system persistence, ACLs, hook-equivalent access, and same-filesystem hard-link claims; this ADR defines and tests only the backend-neutral Core contract.
