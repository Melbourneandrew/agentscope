## Capability Summary

The CLI is the user-facing application: it configures AgentScope, installs first-party harness integrations, retrieves traces when supported, and diagnoses setup.

## Architecture Decision Records

### ADR-001: Use Commander and Zod for command parsing and validation

**Decision:** `apps/cli` uses Commander for command definitions, nested commands, generated help, and standard Node CLI behavior. Zod validates command DTOs and is the shared schema implementation library; each data-contract layer retains ownership of its own schema.

**Context:** AgentScope needs a conventional Node CLI with commands such as `init`, `install`, `destination configure langfuse`, `traces search`, and `doctor`; it does not need a TUI, a runtime plugin host, generated installers, or a framework-owned application lifecycle. Commander is the familiar, mature choice for contributors; Zod makes runtime input checks and TypeScript types derive from the same schema.

**Consequences:** Commands are small Commander definitions that parse flags then validate a command-specific Zod schema before delegating to injected services. Core composes first-party descriptor schemas and owns final configuration invariants; Protocol owns canonical schemas. TypeScript types are inferred rather than separately maintained. Unit tests call command services directly with validated inputs, while a small command smoke suite verifies Commander parsing and exit behavior.

### ADR-002: Separate presentation from domain operations

**Decision:** Command modules own argument validation, human-readable help, stdout/stderr, exit-code selection, and optional machine-readable output. Core and integration packages own all domain mutation and never write directly to process streams.

**Context:** Hook invocation, unit tests, and integration scenarios need the same operations without a terminal dependency.

**Consequences:** Human output is stable enough for users but not a compatibility API; structured output is opt-in and versioned before it is documented for automation. Expected operational failures return stable diagnostic codes without stack traces by default.

### ADR-003: Treat command documentation as a versioned product surface

**Decision:** Every public command and subcommand has a hand-authored Fumadocs page under `apps/docs/content/docs/cli/`, backed by its Commander/Zod definition. The page contains syntax, required arguments, destination-specific configuration flags, examples, exit/diagnostic behavior, and automation-safe structured-output guidance.

**Context:** Coding agents will invoke the CLI as well as humans. Generated `--help` is necessary for discovery but cannot explain configuration intent, destination tradeoffs, or safe operational flows in sufficient detail.

**Consequences:** `agentscope <command> --help` remains concise, deterministic, and generated from Commander metadata. Detailed documentation is reviewed and versioned with command changes; CI checks documented command paths against the registered command tree.

### ADR-004: Compose one read-only Doctor report

**Decision:** The CLI owns the user-facing `agentscope doctor` orchestration required by [Agentscope Doctor](/docs/requirements/agentscope-doctor). It resolves one approved machine home, invokes Core's read-only configuration, credential-intent, operational-state, and writer-lock inspection seams, and composes them with harness discovery, hook-installation, destination-declared reachability, and Git-context inspectors. It maps every component result into one closed finding, severity, freshness, and suggested-action vocabulary before presentation.

**Context:** Core can certify its bounded state parsers and proof-bound repairs, but it cannot truthfully claim that the installed hook, native harness, destination endpoint, Git repository, and platform credential session were all inspected together.

**Consequences:** Doctor never infers health from stale or absent evidence, never displays credential values or provider bodies, and distinguishes unavailable inspection from a negative finding. Human and structured output derive from the same immutable report. Any transaction, credential, or operational recovery claim—whether fixed-plus-claim or claim-only—is an error with `reconcile-recovery-claim`, never an informational retry. `doctor --fix` delegates only the explicitly reversible, proof-bound repairs named by [Operational State ADR-004](/docs/blueprints/operations/operational-state); interrupted-claim reconciliation, credential cleanup, backup restoration, installation mutation, and remote writes remain separate authorized commands. End-to-end Doctor acceptance evidence stays planned until this CLI composition and its installed-context tests exist.
