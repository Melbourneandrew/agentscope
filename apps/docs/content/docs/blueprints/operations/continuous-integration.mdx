## Capability Summary

CI certifies exact repository revisions against quality, package, documentation, native, and harness-compatibility gates while separating privileged deployment and release work from pull requests. Local feedback and caching are deliberately non-authoritative.

## Architecture Decision Records

### ADR-001: Make quality, unit, docs, native, and integration independent required checks

**Decision:** Pull requests report independently visible `quality`, `unit`, `docs`, `native`, and hermetic `integration` checks. Quality, unit, documentation, and integration start from the exact clean checkout, install frozen dependencies, and execute their complete governed gates without accepting an Nx result-cache hit as passed evidence; package-manager download caching is an input-transfer optimization only. The quality lane owns repository-wide workspace-policy, acceptance-evidence, formatting, lint, and strict TypeScript enforcement defined in [Code Quality and CI](/docs/blueprints/operations/code-quality-and-ci). The unit lane owns complete coverage-enforced unit tests, builds, and packed CLI artifact verification. Documentation and integration run their complete production-build and hermetic-matrix contracts under the [Test Strategy](/docs/blueprints/testing/test-strategy).

The native check authenticates the exact pull-request base and head revisions and observes their complete name-only diff with rename detection disabled so both sides of a rename and deleted paths remain visible. Protected `main` uses strict up-to-date status checks or an equivalent merge-group check, so the admitted result is bound to the current merge base rather than a stale branch result. In this personal-repository operating model, required checks are bound to the GitHub Actions application rather than an exact workflow identity. Workflow and classifier files therefore remain reviewed repository code, and any change to either authority, its mechanically checked closure policy, or a transitive action dependency requires complete native execution. Every external action reachable by the native decision or execution is pinned to a reviewed immutable commit SHA; workspace policy mechanically verifies the all-and-only action reference closure and rejects mutable action references.

The native check may report an explicit successful no-execution disposition only when every observed path belongs to one closed, reviewed allowlist of documentation or test/evidence inputs proven unable to affect CLI packaging, Local SQLite code, native tooling or evidence, dependency resolution, workspace or validation policy, workflow authority, or the pinned action closure. The classifier policy mechanically validates that allowlist against the audited workspace dependency graph, packed CLI input inventory, native authority paths, validation/workflow authority, and transitive action inventory. A change to any of those closure authorities requires native execution and must preserve that mechanical proof before a later no-execution disposition is admissible. Any empty, malformed, oversized, unavailable, mixed, or unknown change set runs the complete native lane.

A required native execution checks out the authenticated head without persisting credentials, installs frozen dependencies, builds and verifies the packed CLI, and produces fresh live evidence for the complete [CLI Installation ADR-003](/docs/blueprints/operations/cli-installation) native certification composition. For each selected native Local SQLite tuple, that composition is the exact all-and-only aggregate of the ordinary-bin configuration, actual-harness delivery, and maintenance/upgrade operational profiles plus the Local manifest's closed crash-gate record set, all bound to the same candidate, native tuple, and full-platform tuple. The Docker-backed `verify:native-candidate` component verifier is non-admitting evidence and cannot alone satisfy the native lane. No cached result, artifact, attestation, prepared runtime, or prior run may satisfy native execution or cleanup proof; caching is limited to authenticated deterministic dependency acquisition and preparation whose integrity remains bound by the frozen lockfile and pinned action closure. Pull-request workflows receive no secret or write authority that head code can use.

**Context:** A single monolithic job hides the class of failure and makes expensive harness testing block basic feedback.

**Consequences:** Protected `main` requires the named checks and squash merges. During any workflow or status-context migration or rollback, branch protection continuously requires at least one context that carries complete native execution for relevant or unknown pull-request changes; the concrete transition is tracked in Beads. Every protected `main` revision and every release path runs the complete native lane unconditionally, including fresh live runtime, containment, adversarial, and cleanup evidence, so a pull-request no-execution disposition never becomes release evidence. A failed protected-main native run marks that revision uncertified, blocks release use, and is recovered only by a revert or corrective revision whose complete native run passes. [Local Feedback](/docs/blueprints/operations/local-feedback), [Nx Task Caching](/docs/blueprints/operations/nx-task-caching), Crabbox development runs, and prior CI results cannot satisfy a required execution. The merge workflow has no npm publishing authority; documentation deployment and tagged CLI release are separate workflows.

### ADR-002: Separate untrusted PR work from privileged main work

**Decision:** No workflow receives third-party destination credentials or contacts a public destination service. PR workflows also receive no npm publishing identity or GitHub Pages deployment authority. Main-only workflows deploy docs.

**Context:** A pull request can change test code and must not be able to exfiltrate a privileged token through logs or network traffic.

**Consequences:** CI uploads only sanitized test logs and ledgers. Publishing follows [NPM Publishing](/docs/blueprints/operations/npm-publishing), and Pages follows [Documentation Site](/docs/blueprints/operations/documentation-site).

### ADR-003: Bind every privileged job to a trusted source and environment

**Decision:** Every publishing job uses a named GitHub environment restricted to protected `main` or protected release tags. Candidate-branch checks use no production secret.

**Context:** Safe trigger names and approvals do not establish which workflow revision runs or which source bytes receive authority.

**Consequences:** Environment/ref policy is a documented repository prerequisite. Release records identify the trusted source commit and bind the tested package digest as defined by NPM Publishing.

### ADR-004: Gate mandatory requirements by evidence

**Decision:** Every mandatory `AC-*` identifier is referenced by at least one automated test or an explicitly approved manual verification record, and CI rejects orphaned acceptance criteria.

**Context:** Passing named jobs proves those commands ran, not that the external requirements source of truth has evidence.

**Consequences:** PR summaries report requirement coverage. Adding or changing acceptance criteria updates evidence in the same change; release gates consume the same traceability record and exact tested artifact.
