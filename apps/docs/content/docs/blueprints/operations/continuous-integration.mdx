## Capability Summary

CI certifies exact repository revisions against quality, package, documentation, `0.1.0` Local SQLite packed-absence, and harness-compatibility gates while separating privileged deployment and release work from pull requests. Local feedback and caching are deliberately non-authoritative.

## Architecture Decision Records

### ADR-001: Make quality, unit, docs, alpha packed-absence, and integration independent required checks

**Decision:** Pull requests report independently visible `quality`, `unit`, `docs`, `Native candidate verification`, and stable hermetic `integration` checks. Quality, unit, documentation, and every executed integration scenario start from the exact clean checkout, install frozen dependencies, and execute their governed gates without accepting an Nx result-cache hit as passed evidence; package-manager download caching is an input-transfer optimization only. The quality lane owns repository-wide workspace-policy, acceptance-evidence, formatting, lint, and strict TypeScript enforcement defined in [Code Quality and CI](/docs/blueprints/operations/code-quality-and-ci). The unit lane owns complete coverage-enforced unit tests, builds, and packed CLI artifact verification. Documentation runs its complete production build under the [Test Strategy](/docs/blueprints/testing/test-strategy). Integration follows the intermediate affected-scenario and exact-head final-admission policy in [Workstation, CI, and Crabbox Execution ADR-002](/docs/blueprints/testing/integration/ci-execution); its required context remains successful and independently visible when that policy proves no intermediate scenario execution is required.

The named `Native candidate verification` check authenticates the exact pull-request head revision; protected `main` uses strict up-to-date status checks or an equivalent merge-group check, so the admitted result is bound to the current merge base rather than a stale branch result. In this personal-repository operating model, ordinary required checks are bound to the GitHub Actions application rather than an exact workflow identity; the fallback integration final-admission context is instead bound to the distinct admission application required by Workstation, CI, and Crabbox Execution ADR-002. Workflow and packed-artifact verification remain reviewed repository code. Changes to that authority, its mechanically checked closure policy, or a transitive action dependency require complete integration execution and the alpha packed-absence proof below. Workspace policy mechanically verifies the final-admission controller and permission closure. Every external action reachable by native-context decision, execution, cancellation, or aggregation and by integration is pinned to a reviewed immutable commit SHA; workspace policy mechanically verifies the all-and-only action reference closure and rejects mutable action references.

For the `0.1.0` alpha, the release/support decision is fixed here: the publishable CLI contains no Local SQLite executable, loader, support manifest, or native `.node` tuple, and Local SQLite is not admitted. The still-required named check builds and verifies a fresh publish-shaped CLI artifact from the exact checkout and inspects its packed inventory, including case-folded native extensions and the owned Local loader and manifest paths. It reports the explicit nonexecuting disposition `Local SQLite not admitted`, never a native execution pass or support admission. A missing, malformed, stale, substituted, or contradictory packed inventory fails closed; changes to Local SQLite source cannot silently put its executable tuple into the alpha package. This candidate decision applies to pull requests, protected `main`, and release candidates. Release rehearsal additionally authenticates the exact candidate manifest, source revision, and tarball identity and proves that the same candidate's packed inventory and a fresh pack from that revision both exclude the tuple before publication. A candidate that includes any Local executable, loader, support manifest, or native binary cannot publish as `0.1.0`, even if an isolated native verifier happens to pass. The earlier irrelevant-path native no-execution disposition is not used for alpha: every candidate obtains fresh packed-absence proof, including documentation-only changes.

The Docker-backed `verify:native-candidate` component verifier is not run as a `0.1.0` admission gate against an intentionally absent Local tuple. This deferral does not weaken [CLI Installation ADR-003](/docs/blueprints/operations/cli-installation): a later proposal to publish Local SQLite first requires a standalone, approved Blueprint change, restoration of complete fresh native runtime, containment, adversarial-execution, and cleanup evidence on the proposed packed tuple, the separate exact all-and-only native admission aggregate, and a protected-status migration with no required-check gap. The alpha no-execution disposition cannot be reused as any part of that evidence. No cached artifact, prior run, or attestation substitutes for the alpha candidate's fresh packed-absence proof; caching remains limited to authenticated deterministic dependency acquisition under the frozen lockfile and pinned action closure. Pull-request workflows receive no secret or write authority that head code can use.

**Context:** A single monolithic job hides the class of failure and makes expensive harness testing block basic feedback.

**Consequences:** Protected `main` requires the named checks and squash merges. Merge-group protection requires the App-bound `hermetic-integration-final` context for the exact merge-group commit. Without merge queue, protected-main branch protection requires both the stable intermediate `hermetic-integration` context and the App-bound final context for the exact pull-request head. During any workflow or status-context migration or rollback, branch protection continuously requires at least one complete integration-matrix context and the named `Native candidate verification` context. For `0.1.0`, that context proves fresh exact-candidate packed absence and reports `Local SQLite not admitted`; it never reports a green native execution that did not occur. The concrete transition is tracked in Beads and follows the shadow, cutover, and rollback order in Workstation, CI, and Crabbox Execution ADR-002. Every protected `main` revision and release candidate reruns the packed-absence decision without accepting a prior pull-request disposition as release evidence. Complete integration coverage still runs at final pull-request admission, on protected `main`, on the governed schedule, and for release candidates as required by Workstation, CI, and Crabbox Execution ADR-002. A failed protected-main candidate run marks that revision's candidate evidence failed and is recovered only by a revert or corrective revision whose required check passes. Neither a successful context nor its no-execution disposition alters CLI Installation ADR-003 support-admission authority. [Local Feedback](/docs/blueprints/operations/local-feedback), [Nx Task Caching](/docs/blueprints/operations/nx-task-caching), Crabbox development runs, and prior CI results cannot satisfy required CI evidence. The merge workflow has no npm publishing authority; documentation deployment and tagged CLI release are separate workflows.

### ADR-002: Separate untrusted PR work from privileged main work

**Decision:** No workflow receives third-party destination credentials or contacts a public destination service. PR workflows also receive no npm publishing identity or GitHub Pages deployment authority. Main-only workflows deploy docs.

**Context:** A pull request can change test code and must not be able to exfiltrate a privileged token through logs or network traffic.

**Consequences:** CI uploads only sanitized test logs and ledgers. Publishing follows [NPM Publishing](/docs/blueprints/operations/npm-publishing), and Pages follows [Documentation Site](/docs/blueprints/operations/documentation-site).

### ADR-003: Bind every privileged job to a trusted source and environment

**Decision:** Every publishing job uses a named GitHub environment restricted to protected `main` or protected release tags. Candidate-branch checks use no production secret.

**Context:** Safe trigger names and approvals do not establish which workflow revision runs or which source bytes receive authority.

**Consequences:** Environment/ref policy is a documented repository prerequisite. Release records identify the trusted source commit and bind the tested package digest as defined by NPM Publishing.

### ADR-004: Gate mandatory requirements by evidence

**Decision:** Every mandatory `AC-*` identifier is referenced by at least one automated test or an explicitly approved manual verification record, and CI rejects orphaned acceptance criteria.

**Context:** Passing named jobs proves those commands ran, not that the external requirements source of truth has evidence.

**Consequences:** PR summaries report requirement coverage. Adding or changing acceptance criteria updates evidence in the same change; release gates consume the same traceability record and exact tested artifact.
