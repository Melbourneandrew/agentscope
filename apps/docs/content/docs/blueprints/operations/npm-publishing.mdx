## Capability Summary

NPM releases must be attributable, reproducible, and limited to the intentionally public CLI without long-lived repository secrets.

## Architecture Decision Records

### ADR-001: Bootstrap the public package once, then use stage-only trusted publishing

**Decision:** The public package is `agentscope-cli`, and its executable remains `agentscope`. Because npm cannot configure trusted publishing for a package that does not yet exist, the owner establishes the package once through an interactive two-factor-authenticated publication of an inert `0.0.0-bootstrap.0` tarball under the `bootstrap` dist-tag. That tarball has no executable, lifecycle script, dependency, or product-support claim. Immediately before mutation, the owner rechecks that the name is unclaimed and records the tarball's SRI and inert inventory. After a missing or ambiguous response, the owner compares public metadata, authenticated ownership, exact bootstrap version and tag, SRI, and inventory. Work resumes only when those identities prove the exact owner-controlled bootstrap; any collision or mismatch stops publication and reopens the package-identity decision without selecting an alternative automatically.

After ownership is established, the package trusts only `Melbourneandrew/agentscope`, the exact release workflow, the `npm-release` GitHub environment, and the `npm stage publish` action. Configuration inspection records that tuple but does not claim to prove OIDC exchange. The first exact `0.1.0` stage is the initial credential exchange and remains non-public until separate npm approval, so a binding error fails before publication and may be corrected and retried against the same transaction. The bootstrap version is deprecated after the first product release. No product version uses a long-lived `NPM_TOKEN`.

**Context:** npm trusted publishing and staged publishing require an existing package. A deliberately inert bootstrap establishes ownership without making the first real product release depend on a repository token or bypassing the later release controls.

**Consequences:** The bootstrap is a one-time owner operation and is never installed by a normal package request because it is not assigned `latest`. The package's npm settings require two-factor authentication, disallow granular publishing tokens after trusted publishing is configured, and require human approval of each staged publication. GitHub-hosted release jobs use OIDC and npm provenance; local, self-hosted, and Crabbox workers cannot publish.

### ADR-002: Publish only the tested CLI

**Decision:** The `agentscope-cli` release build bundles all private Agentscope TypeScript workspace code into one self-contained CLI artifact. Ordinary non-bundleable third-party modules are public runtime dependencies. A destination Blueprint may instead authorize an install-script-free vendored native closure when it pins every registry/source artifact in a separate exact release-material manifest; acquires each as inert integrity-checked bytes without workspace dependency resolution or lifecycle execution; compiles the complete bounded archive before any write and materializes only manifest-owned canonical regular-file targets into a fresh private no-follow/exclusive-create staging root; binds every redistributed binary to an attested exact build-material ledger or an Agentscope-owned credential-free sandboxed native build; defines an exact source-to-artifact regular-file allowlist with complete license/notice and SBOM evidence plus per-file digests; supplies an owned closed loader with no discovery or fallback path; and binds every runtime support claim to native packed-artifact evidence. Such a build input and its dependency graph do not appear in workspace or published dependency metadata. The packed CLI contains neither its package manifest/build authority nor package-manager, end-user, install-time, or otherwise unmanifested source-build output. It may contain only the exact finite support-manifest set of checksum/provenance-bound native binaries independently admitted as inert bytes: exactly one unique binary path and digest for each native-binary compatibility tuple, with no incompatible tuple/path/digest aliases or extra binary. Each owned sacrificial build emits exactly one native-binary tuple's binary. Full supported-platform tuples may share it only through the manifest's identical total native projection; their independent credential, filesystem, lifecycle, and other evidence remains distinct. No private workspace package appears in published dependency metadata.

**Context:** Publishing an internal package turns its folder layout and types into an accidental long-term compatibility promise.

**Consequences:** `npm pack` inspection and ordinary clean installation of the exact tarball with lifecycle scripts enabled, no workspace, no compiler toolchain, and no separately assembled Agentscope dependency closure are release gates. A vendored native closure additionally requires exact bounded archive-compilation/inert-acquisition, tarball inventory, build and execution sandbox profiles, provenance, material, notice, and SBOM verification; hostile archive, scripted direct/transitive no-execution, hostile build-grammar isolation, and hostile native-execution containment negatives; native load and capability tests on every claimed full support tuple; an all-and-only native-tuple-to-binary pack-inventory fixture with safe many-support-to-one-native sharing and incompatible/ambiguous alias negatives; and proof that installation ran no compilation or download subprocess. Native builders and execution guests have no publishing or signing credential. The trusted aggregator/publisher treats builder/candidate output only as bounded verified inert bytes, accepts only supervisor-authenticated content-free native evidence bound to the immutable candidate digest, shares no writable state with those jobs, and never loads the candidate or runs source/build metadata. Release automation publishes the checksum-addressed tarball already exercised by the hermetic matrix; if rebuilding is unavoidable, it proves normalized content and dependency-metadata equivalence first, then performs an isolated registry-install smoke. Release evidence records source commit and tested/published digest.

### ADR-003: Cut releases from one protected tag and one certified candidate

**Decision:** A candidate workflow on protected `main` packs the CLI once and retains the exact tarball, SHA-256 and SRI digests, source revision, version, package and bin identities, support-admission record, SBOM, attestations, and sanitized evidence index. Before accepting a release tag, the release lane authenticates two layered semantic-version tag rulesets: a creation rule with only the narrow approved release authority as bypass actor, and a separate update/deletion rule with no routine release-actor bypass and administrator enforcement. It also authenticates the protected-`main` enforcement required by the completion and incident ledgers and repository immutable-Release enforcement. Evidence uses exact production API inspection plus generic authorized/denied mutation evidence in a disposable canary repository; it never probes production `v*` refs. The first real annotated release tag supplies production creation evidence. Missing, ambiguous, or changed controls fail closed.

A release begins only when an authorized operator creates the protected annotated tag `v<version>` at that exact candidate revision. The tag-triggered workflow proves byte-for-byte equality among the tag version, candidate package version, CLI version, source revision, candidate digest, and release record; verifies that the revision is reachable from protected `main`; and consumes the retained tarball without rebuilding it. The same repository controls are authenticated again immediately before npm staging and before publishing or quarantining a draft GitHub Release. Drift after npm publication prohibits a success transition and enters the already-immutable or incident reconciliation path; it never weakens the required evidence boundary.

All non-privileged verification completes before any job enters the protected `npm-release` environment. A release-record job receives `contents: write` but no OIDC permission; it creates the draft GitHub Release, attaches the exact tarball, checksum manifest, SBOM, attestations, and sanitized evidence index, and appends the first machine-readable transaction record. Transaction records are immutable, uniquely numbered draft assets; each binds the draft release database identity, previous record digest, transition, actor, candidate, protected tag, and source revision. Writers use the repository-wide concurrency group and compare the expected latest sequence and digest before appending, so retries never replace or delete history. The latest valid hash-linked record is pre-publication authority.

The stage job receives `id-token: write` but no GitHub write permission, re-verifies the candidate, and submits that exact tarball with `npm stage publish`. Both jobs use the environment; for a single-owner repository its approval policy permits the tag creator to approve, while npm's later interactive two-factor approval remains the distinct final publication act. Preventing environment self-review requires a separately authorized maintainer and is not enabled implicitly.

Before staging, an authenticated owner supplies a fresh transaction-bound checkpoint confirming that npm has no conflicting pending stage. The stage job emits only a bounded result containing the returned stage identifier and immutable identities. A dependent recorder job receives `contents: write` but no OIDC permission, validates that result against the existing transaction, and persists the stage identifier, package, version, immutable dist-tag, candidate digest, protected tag, and source revision before requesting human approval. If the stage response is missing or ambiguous, the recorder marks the transaction quarantined rather than inventing an identifier.

One repository-wide concurrency group serializes every release-record, stage, recorder, continuation, and recovery job. Automation reconciles only the active GitHub transaction record, draft or published GitHub Release, public registry, and dist-tags. Pending-stage state remains owner-only: before a mutation for which it matters, an authenticated owner lists and inspects pending stages, downloads the candidate stage, verifies its exact tarball, and supplies a fresh transaction-bound reconciliation checkpoint through the protected continuation interface. Public-registry absence is not proof that staging failed. The concurrency group prevents simultaneous checks and mutations, while the durable transaction plus required owner checkpoint preserves the fence after a workflow run ends. Any other active or unaccounted-for transaction fails closed.

An authorized maintainer separately reviews and approves that exact staged publication through npm with interactive two-factor authentication; the workflow cannot approve it. A bounded continuation resumes from the original protected tag and release record, authenticates the approved stage identity, and performs registry verification and GitHub Release publication. It receives `contents: write` but no OIDC permission, cannot select a different workflow revision or candidate, and repeats the serialized external-state reconciliation. A stale or lost continuation is replaced only by another continuation authenticated against that same protected tag and transaction record. Normal pushes, pull requests, manual jobs on arbitrary refs, local machines, and remote development workers cannot mint publishing authority.

**Context:** A Git tag identifies source, but npm publishes immutable bytes. The release must bind the human release decision to the exact artifact that passed the product's acceptance and platform gates rather than rebuilding equivalent-looking bytes under stronger credentials.

**Consequences:** A missing, expired, mixed-revision, rebuilt, unattested, incorrectly versioned, already-differently-published, or incompletely certified candidate fails before privileged staging. Retrying a transaction is safe only when every immutable identity matches; if npm already contains the exact version, automation compares its registry integrity with the certified tarball and either resumes post-publication verification or enters incident handling.

### ADR-004: Use conventional npm channels and matching GitHub Releases

**Decision:** Product version `0.1.0` is published with the npm `alpha` dist-tag and its GitHub Release is marked as a prerelease. `latest` is reserved for independently certified stable releases and is never created or moved by an alpha publication. Later alpha releases may move `alpha`; a stable release explicitly assigns `latest`. Promoting stability requires a newly certified release version rather than silently relabeling `0.1.0`.

The GitHub Release and npm publication are separate records bound to the same candidate. The GitHub Release owns the protected Git tag, release notes, prerelease status, exact npm tarball, checksum release manifest, SBOM, and sanitized evidence index. The npm registry owns the immutable installable `agentscope-cli@<version>`, its integrity and provenance, and movable dist-tags. Before staging, the workflow prepares the draft GitHub Release and uploads every candidate asset so source evidence no longer depends on temporary Actions retention. An authorized maintainer approves the staged publication through npm with interactive two-factor authentication; then the bounded continuation verifies the public registry artifact and publishes the immutable GitHub Release. Creating one record never substitutes for creating the other.

**Context:** npm convention reserves `latest` for the default stable installation channel, while GitHub Releases provide a durable source-and-assets record rather than a package registry. Keeping those roles explicit prevents an alpha from becoming the default install and prevents generated source archives from being mistaken for the tested npm tarball.

**Consequences:** `npm install -g agentscope-cli@0.1.0` and `npm install -g agentscope-cli@alpha` select the first alpha; a bare package install does not. Immediately before GitHub publication, the continuation appends a `ready-to-publish` manifest that binds every prior transaction record; it does not claim that publication or verification succeeded. After the publication call or any ambiguous response, the continuation reconciles the release database identity, draft status, tag, assets, and immutable-release attestation before choosing another transition.

If the Release remains a draft and npm publication or later verification fails, the transaction remains active, the owner performs the ADR-005 quarantine ceremony, and the continuation appends a final quarantined manifest before publishing the retained draft as an immutable quarantined prerelease record. If the Release is already immutable, no asset or manifest is added: the owner quarantines the npm channel and a reviewed append-only completion or incident manifest on protected `main` records the observed outcome. A later continuation must reconcile and finish one of those states before another release can begin.

Release success is not announced until the public registry reports the expected version, `alpha` mapping, integrity, provenance, package and bin identities; the registry tarball matches the candidate; a fresh exact-version install passes bounded version, help, init, and Doctor smoke checks; the GitHub Release and its assets verify against the protected tag; and a reviewed append-only completion manifest under `release-records/releases/` on protected `main` binds those results to the immutable Release attestation and `ready-to-publish` manifest digest. Facts discovered after immutability are new append-only incident manifests under `release-records/incidents/`, keyed to that completion or ready-manifest digest and cross-linked to any replacement Release. Every ready-to-publish manifest declares both ledger locations so later records can be discovered without mutating history.

### ADR-005: Preserve immutable history when a release fails

**Decision:** A bad release is never overwritten and is not routinely unpublished. Automation produces and verifies a bounded recovery plan, but an authenticated package owner performs every npm dist-tag change, deprecation, or exceptional unpublish through an interactive two-factor-authenticated incident ceremony. That ceremony moves or removes the affected channel tag, deprecates the exact bad version with a corrective message, and requires a newly versioned candidate for the fix. Unpublish is reserved for exceptional disclosure or legal incidents where npm policy permits it.

A suspected publisher compromise first disables the ordinary `npm-release` environment and release workflow and independently verifies that freeze, then revokes the npm trusted publisher. Through interactive two-factor authentication, the owner lists, inspects, downloads, and reconciles every transaction-bound or otherwise unaccounted-for pending stage and rejects each suspect stage with `npm stage reject`; the incident record binds every rejection or ambiguity. The owner then quarantines any affected public channel. Unreconciled pending-stage state keeps all release authority frozen.

A separate protected `release-incident` path has no npm or OIDC authority and may only verify already-retained assets, append the quarantined final manifest, and publish the existing draft as an immutable quarantined Release. If repository integrity is also suspect, the ordinary automation remains frozen; the owner independently verifies the retained attestations and assets and performs the bounded GitHub quarantine publication through owner authentication rather than executing repository workflow code. No recovery release is permitted until a separately reviewed restoration re-establishes both authorities and proves no suspect stage remains pending.

The immutable GitHub Release retains its ready-to-publish or quarantined final transaction manifest, candidate attestations, source and tag revision, candidate digest, workflow identities, and pre-publication state. The protected-main completion manifest owns the observed registry identity, published digest, approval identity, dist-tag state, and post-publication checks. Later deprecation, channel, compromise, and replacement facts are new append-only incident manifests on protected `main`, keyed to the completion or ready-manifest digest and cross-linked to any replacement Release; the original Release is never edited.

**Context:** npm package versions are immutable and cannot be safely reused after publication or unpublication. Movable channels and deprecation provide conventional recovery without erasing the evidence needed to understand what users may have installed.

**Consequences:** Pre-publication failures may resume from the same verified candidate. Post-publication failures preserve the original version and evidence, direct users to the last known-good or replacement version, and require an explicit incident trail. Deleting a GitHub Release or tag cannot be used to imply that an npm publication never occurred.
