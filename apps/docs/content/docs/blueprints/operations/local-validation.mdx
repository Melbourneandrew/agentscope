## Capability Summary

Agentscope gives contributors prompt local feedback without turning cached output into evidence that a live platform or runtime was certified. Local pre-push validation selects deterministic gates from the complete pushed change, while GitHub CI remains the full merge and release authority.

The baseline on 2026-09-05 used commit `8a2c9b1084080cbc1b1b8a2a5d37fdb482e90814`, Node 22.23.2, pnpm 9.15.0, macOS 15.7.4 arm64, Docker 29.7.2, `NX_DAEMON=false`, and one initially empty dedicated Nx cache. The cold and immediately repeated warm runs both passed:

| Current `validate` stage            |        Cold |        Warm |
| ----------------------------------- | ----------: | ----------: |
| Workspace verification              |       4.06s |       3.19s |
| Acceptance evidence                 |       0.28s |       0.27s |
| Formatting                          |       5.93s |       5.34s |
| Lint                                |      50.59s |      43.95s |
| Typecheck                           |      11.87s |      11.27s |
| Unit and workspace-policy tests     |      82.70s |      82.49s |
| Coverage                            |      31.80s |      31.69s |
| Build                               |      14.52s |      14.56s |
| CLI artifact verification           |       5.69s |       5.61s |
| Live native-candidate certification |     313.75s |     320.11s |
| **Total**                           | **521.19s** | **518.48s** |

Current inferred package targets have no explicit `cache: true`. A controlled repeat of `@agentscope/protocol:typecheck` produced the same Nx hash, `7457040259383286263`, but two `cache-miss` results (2.88s and 2.64s). A warm all-project build likewise reported 17 cache misses. Cache files exist, but current validation receives no reusable task result.

## Architecture Decision Records

### ADR-001: Classify the complete pushed change before selecting local gates

**Decision:** The pre-push hook parses every ref-update tuple supplied by Git and authenticates its local object type. A commit object is its own validation commit. One annotated tag object that points directly to a commit is supported by retaining both the tag-object ID and its exactly peeled commit ID; lightweight tags arrive as commit objects. A tag-to-tag chain, tree, blob, or any other object type aborts with the stable `prepush-ref-object-unsupported` diagnostic. Every distinct validation commit runs from an immutable detached checkout of that exact commit; the caller's mutable checkout never substitutes for pushed bytes.

The hook derives one canonical, NUL-delimited union of changed paths for each ref tuple and classifies both sides of renames and copies, including deleted paths, against ADR-002. A normal commit update compares the complete `remote commit ID..validation commit ID` range. A new ref, annotated tag, force-update ambiguity, missing object, malformed or oversized Git output, unknown path, classifier failure, or empty classification for a nonempty range selects the full deterministic and live-native local gates. Classification runs on every invocation. Execution results are reusable only per exact validation-commit ID, original local-object ID, gate ID, deterministic-profile identity, and validation-policy identity, and only when that individual gate is also selected by the newly computed range; the same commit under a different base never reuses an aggregate narrower selection. Failure to materialize or retain the exact checkout aborts the push. A ref deletion contributes no introduced bytes after its exact zero local object ID is validated. The selector never trusts shell-delimited path text, a caller-supplied project name, remote-tracking refs, an additional remote enumeration, or the working-tree diff.

**Context:** A path-aware hook is safe only if it cannot omit a changed path because of whitespace, rename direction, multi-ref pushes, or history shape.

**Consequences:** The existing hook remains mandatory. No path class authorizes `--no-verify`, changes GitHub branch protection, or suppresses a failing selected gate. A new ref or annotated tag deliberately pays the conservative full-gate cost instead of inferring reachability from mutable remote state. An update may exit without gates only after every tuple is proven to introduce no changed bytes. Exact-checkout creation, output roots, and teardown are bounded validation orchestration and cannot create support or release evidence.

Every exact checkout materializes dependencies with the pushed commit's frozen lockfile, its declared package-manager version, and the admitted exact Node/toolchain profile. It uses a checkout-owned dependency tree and never links or copies the caller checkout's mutable `node_modules`. A shared content-addressed package store may supply integrity-revalidated locked bytes, but missing or mismatched material fails before any gate or cache population.

### ADR-002: Bind changed-path classes to a conservative gate matrix

**Decision:** Every nonempty change runs the fast repository invariants: workspace-policy verification, acceptance-evidence verification, and formatting for every changed supported text file. The selector then takes the union of all matching rows; it never chooses only the cheapest match.

| Changed-path class                                                                                                                                                                                                                                                                  | Additional local gates                                                                                                                                                                                                                                                                    |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repository prose and documentation content, including `README.md`, `CONTRIBUTING.md`, and `apps/docs/content/**`                                                                                                                                                                    | Documentation lint, typecheck, and production build. Requirement, Blueprint, navigation, or `acceptance-evidence.json` changes also run the complete acceptance-evidence and documentation-link checks.                                                                                   |
| Documentation application code or configuration under `apps/docs/**`                                                                                                                                                                                                                | Affected documentation build, lint, typecheck, and tests where present.                                                                                                                                                                                                                   |
| One or more Nx project roots under `apps/**`, `packages/**`, or `tests/integration/**`                                                                                                                                                                                              | Nx-affected `build`, `lint`, `typecheck`, `test`, and `coverage` for the changed projects and the graph dependants required by each target. Integration changes run only deterministic integration project targets locally; they do not turn a pre-push into live scenario certification. |
| CLI code, every production input in the `agentscope-cli` packed-candidate dependency closure, packaging metadata, or CLI artifact tooling                                                                                                                                           | The affected-project gates, packed CLI artifact verification, native preparation, and one fresh live native certification against that exact candidate.                                                                                                                                   |
| Workspace-wide dependency, target, compiler, test, formatting, quality, or validation policy such as root manifests and lockfiles, `nx.json`, `tsconfig.base.json`, `vitest.config.ts`, `eslint.config.mjs`, `quality-policy.json`, `.prettierignore`, `.husky/**`, or `scripts/**` | All deterministic project gates and CLI artifact verification.                                                                                                                                                                                                                            |
| Native-candidate manifests, material records, binaries, runtime bundle, owned loader/tooling, native package composition, native verification authority, or a workspace-wide dependency/toolchain input that can alter them                                                         | All deterministic gates, native preparation, and one fresh live native certification.                                                                                                                                                                                                     |
| Unclassified or ambiguous path                                                                                                                                                                                                                                                      | All deterministic gates, CLI artifact verification, native preparation, and one fresh live native certification.                                                                                                                                                                          |

**Context:** Documentation-only changes do not alter the packed CLI or native candidate, while native and workspace-policy changes can cross most project boundaries. Nx's project graph supplies dependency expansion; the explicit path policy owns cases outside project roots. The native-trigger closure is generated from every source, resource, manifest, and transitive production project consumed by the packed CLI build, not inferred from a package-name substring.

**Consequences:** The matrix is versioned executable policy with table-driven tests, not a shell glob list duplicated inside the hook. Project discovery comes from the Nx graph. A change to CLI, Core, Protocol, a bundled destination or harness, or any other packed production dependency receives the live native gate; test-only and documentation-only projects remain outside that closure. Adding a project, packed resource, root policy file, native authority file, or new top-level directory must update or deliberately satisfy the fail-closed classifier tests in the same change.

### ADR-003: Cache only explicitly deterministic Nx task results

**Decision:** A no-output project/target pair becomes eligible for local cache reuse only through reviewed `cache: true`, complete declared inputs, and an enforceable deterministic execution profile. Eligibility is audited separately for each package `lint`, `typecheck`, and deterministic `test` target; no target kind is cacheable by name alone. Ordinary `build` and `coverage` outputs have no independent pre-existing digest oracle and remain non-cacheable. An output-producing target becomes eligible only when an already-governing artifact authority independently supplies its exact expected inventory, sizes, and digests; Local Validation never creates a parallel generated-manifest authority. Validation orchestration, workspace-policy process-authority tests, cleanup, integration scenarios, and every live native certification target remain non-cacheable. A restored no-output local result proves only that the same closed deterministic command previously succeeded for the same input hash. It never proves that an external service, Docker engine, operating-system behavior, process teardown, or current runtime was observed. Required CI cache policy is owned only by [Continuous Integration](/docs/blueprints/operations/continuous-integration); local result reuse has no CI or release authority.

Every cacheable hash includes the project files, transitive production inputs selected by the Nx graph, project and root package scripts, lockfile, Nx configuration, TypeScript/Vitest/ESLint/Prettier and quality policy, target implementation scripts, exact Node and package-manager versions, and the complete admitted OS, architecture, filesystem, locale, timezone, and other platform profile. The execution boundary supplies a closed environment and executable/toolchain allowlist, read-only source inputs, fresh exact output roots, and denied network and undeclared host-file access. An ambient value such as `GITHUB_ACTIONS` is either denied or explicitly allowlisted and hashed. A target that can still observe an unbound environment, executable, network, clock, filesystem, service, process, or secret is non-cacheable.

Local task-result entries are untrusted optimization inputs, never candidate or release authority. Nx's repository-local database and cache directory are the sole persistent task-cache authority; remote caches are disabled. The namespace is a user-private directory bound to the physical repository and validation-policy identity, and reuse, population, recovery, and garbage collection all run under the repository validation lease. The same operating-system principal is its administrative trust boundary. Executable policy caps the active namespace at 2 GiB, 16,384 completed entries, and 30 days since last validated use. It admits at most one fenced recovery quarantine and caps the complete active-plus-quarantine namespace at 4 GiB. Nx's atomic store and least-recently-used size eviction remain the entry implementation; validation orchestration adds the count, age, identity, and crash-recovery ceilings without creating another result format. A malformed no-output result is never interpreted as success.

Output restoration, when an existing artifact authority permits it, occurs atomically into a fresh staging root. A fresh, non-cacheable, nonexecuting admission step derives the expected source, toolchain, output inventory, sizes, and digests from the exact pushed snapshot and governing manifest rather than from the cache entry or a verifier result stored beside it. Only admitted bytes may replace the exact declared output root.

A failed restore is durably tombstoned under the exact cache-key fence, quarantines or removes only that entry and the run's staging root, and permits at most one cache-disabled execution in a fresh output root. A successful fresh execution atomically replaces the tombstoned generation; the next invocation must prove it can consume that replacement. On startup under the lease, validation either resumes one exact tombstone/staging transition or moves the physically authenticated repository cache namespace to the single bounded quarantine and starts empty; it never follows links, recursively targets an unresolved path, or deletes another repository's cache. A terminal cache-reconciliation diagnostic names the exact supported repository-cache reset operation. Successful-entry eviction authenticates the entry grammar and holds the same lease; an unclassifiable entry triggers namespace quarantine rather than ad hoc deletion. Failure to lock, inventory within bounds, invalidate, clean, replace, or execute terminates validation; it never repeatedly adopts the rejected entry.

**Context:** Nx currently calculates stable hashes but records cache misses because inferred targets are not explicitly cacheable. Broad shared globals already invalidate many tasks, but toolchain and environment boundaries also need to be explicit before reuse is trustworthy.

**Consequences:** Changes to source, a transitive dependency, command text, shared policy, lockfile, toolchain, platform tuple, or declared environment invalidate the applicable local results. Denied ambient inputs, exact-profile drift, stale output, and corrupted cache records cannot become a hit. Cross-repository or externally supplied entries are inadmissible. The governing CI lanes repeat their mandatory gates from the exact checkout and do not accept a local result-cache record as an attestation.

### ADR-004: Separate content-addressed native preparation from fresh certification

**Decision:** Local Validation owns only path selection, cache orchestration, and the decision to request existing native authorities. [Local SQLite ADR-007](/docs/blueprints/destinations/local-sqlite-destination), [CLI Installation ADR-003](/docs/blueprints/operations/cli-installation), [Matrix Operations](/docs/blueprints/testing/integration/matrix-operations), and [Workstation, CI, and Crabbox Execution](/docs/blueprints/testing/integration/ci-execution) remain the sole owners of material and support manifests, acquisition, build, candidate assembly, execution, run claims, consumer handoff, evidence, settlement, retirement, and recovery. Local validation creates no parallel manifest, ledger, support row, runner, or cleanup authority.

This decision permits native preparation and live certification to become separate targets, but it does not permit cross-run persistence or reuse of native preparation output. Admitted material bytes, compiled native binaries, runtime bundles, and build metadata remain run-owned under the existing controller and are terminally reconciled with that run. The packed candidate is always freshly assembled and verified from the exact pushed checkout; its resulting digest binds the later live run but cannot serve as a pre-existing cache oracle. Native preparation must remain non-cacheable until an earlier standalone amendment to the governing Matrix Operations and execution-controller Blueprints defines the exact persistent artifact roles, independent oracles, registry representation, aggregate count/byte/age ceilings, consumer fencing, eviction order, crash recovery, quarantine bound, and cleanup owner. Those roles never enter the Nx task cache.

Live native certification always executes under the existing run-generation and outer-controller lifecycle. It freshly proves candidate loading and Local SQLite behavior, current platform and filesystem observations, Docker/VM isolation, network and credential denial, hostile input rejection, process and handle containment, bounded cleanup, and terminal resource reconciliation. Source-tag reachability, image availability, current engine behavior, wall-clock timing, and cleanup evidence are observations, not cacheable proof. Live evidence identifies the exact admitted prepared-candidate digest, immutable pushed object ID, controller/run generation, and current run identity and cannot be synthesized from a preparation cache hit. Cancellation, timeout, unsettled daemon mutation, failed stop/join, or uncertain inventory fails certification and blocks reuse or retry until the governing authority reaches its defined reconciled or quarantined terminal state.

**Context:** The present native verifier mixes deterministic material acquisition and two equal builds with more than five minutes of live Docker/runtime certification. Reusing immutable bytes is sound; reusing a prior environmental attestation is not.

**Consequences:** A native-relevant pre-push runs fresh native preparation and fresh certification as distinct stages. Documentation and unrelated package changes avoid both locally. The split makes preparation cost and future eligibility measurable without silently creating a persistent artifact authority. No local build record or live result can become support or release evidence. CI and release behavior remains solely governed by [Continuous Integration](/docs/blueprints/operations/continuous-integration), CLI Installation, and NPM Publishing.

### ADR-005: Prove selection and cache invalidation adversarially before rollout

**Decision:** The path selector ships with table-driven positives for every matrix row and negatives for newline/space paths, rename and copy across classes, deletion, multiple ref updates and distinct local object IDs, the same commit under different remote bases, non-checked-out refs, lightweight and annotated tags, tag-to-tag and non-commit objects, new refs after a narrower prior push, force updates, missing objects, mutable-worktree substitution, exact-checkout or frozen-dependency loss, malformed or oversized Git output, unknown top-level paths, and classifier exceptions. Every ambiguous change selects the conservative superset against the exact pushed snapshot or aborts before claiming validation.

Cache tests first prove a same-hash second no-output execution reports a real hit, then prove misses after changing project source, transitive production source, a project script, each shared policy/config input, lockfile, exact Node/tool version, platform tuple, and each declared environment input. Profile tests prove undeclared environment, PATH/executable, network, clock, and host-file observations are denied; a target without that proof remains non-cacheable. Cache-lifecycle tests cover byte, entry-count, age, and active-plus-quarantine equality and overflow; concurrent consumer/eviction attempts; interruption before and after tombstone, staging publication, quarantine rename, fresh replacement, and eviction; unclassifiable entries; next-invocation recovery; and exact repository-bound reset without symlink or foreign-root traversal.

Restore tests for any future existing-authority-backed outputs reject deletion, substitution, extra artifacts, wrong digest, partial publication, foreign namespaces, verifier output supplied by the same cache, and repeated adoption of one rejected entry. They prove atomic fresh staging, independent expected-digest derivation, fenced durable tombstoning, exact cleanup, one cache-disabled execution, atomic healthy replacement, next-invocation reuse, and terminal failure on uncertainty. Native tests prove preparation and certification use distinct run-owned stages, a fresh packed candidate registers through the existing controller, no preparation result can satisfy certification, and stale or forged live evidence cannot satisfy it. Benchmark tests preserve cold/warm per-stage timings, task hashes, hit/miss status, selected pushed object ID and path class, and selected gates as bounded sanitized artifacts.

**Context:** A fast path that is difficult to falsify will eventually skip a required gate or trust stale evidence.

**Consequences:** Each optimization remains disabled until its executable policy, deterministic profile, failure transitions, and adversarial tests pass independently. End-to-end evidence must demonstrate documentation-only selection, representative package and native selections, cache-hit and invalidation behavior, exact pushed-snapshot binding, distinct fresh native preparation and certification identities, and one unchanged full GitHub CI wave.

### ADR-006: Fail closed outside the supported local-validation profile

**Decision:** Executable validation policy publishes one closed contributor profile covering POSIX Git object/worktree behavior, exact Node and pnpm versions, package-store integrity, filesystem identity and atomicity, cache namespace privacy and locking, and the existing controller prerequisites for native preparation and certification. Startup verifies the applicable capabilities before creating a checkout, cache entry, Docker/VM resource, or other mutable state. A missing deterministic prerequisite emits a stable `local-validation-profile-unsupported` diagnostic; a selected native gate without its governed controller profile emits `local-native-certification-unavailable`. Either result aborts the push without claiming a passed gate. Deferral to CI is not a hook bypass.

**Context:** Path selection reduces native work but broad, native, and ambiguous changes still require capabilities that are not available on every workstation.

**Consequences:** Documentation identifies the supported contributor prerequisites and exact remediation or alternate supported runner. Local platform support is a validation-tooling claim, not a released Agentscope product support claim. The hook never treats Docker availability alone, a shared developer daemon, or an eventual CI run as equivalent to the existing native controller authority.
