## Capability Summary

Core owns only the small operational state needed to diagnose installations and recover configuration changes. It never uses machine-local state as a deferred trace-delivery system.

## Architecture Decision Records

### ADR-001: Keep trace data out of operational state

**Decision:** `AGENTSCOPE_HOME` may contain versioned configuration, short-lived owned mutation records, bounded sanitized diagnostics and health markers, and versioned non-content incremental capture checkpoints. It shall not contain raw native artifacts, canonical trace graphs, pending batches, reporter payloads, credential values, or a retry queue.

**Context:** A hook must fail open when reporting is unavailable. Persisting failed telemetry would create an unrequested local trace repository with privacy, retention, encryption, and recovery obligations.

**Consequences:** A hook reports at most once per selected connection within its deadline. On any failed or incomplete delivery it discards the batch and records only permitted health evidence; checkpoints contain native source identity/generation and acknowledged position, never trace content.

### ADR-002: Bound diagnostics and make loss explicit

**Decision:** Core writes one canonical, atomically replaced operational-state generation under the resolved machine-local home. The closed document schema contains a format version, a monotonically increasing safe-integer update sequence, three separate monotonically increasing retention-loss counters, and exact diagnostic, health, and checkpoint arrays; it has no open metadata or string-valued extension field. The complete document is limited to 256 KiB; diagnostics and health expire after seven days, checkpoints expire after thirty days, and deterministic `(observed timestamp, update sequence)` oldest-first retention keeps at most 128 diagnostics, 64 health markers, and 128 checkpoints. The closed vocabularies and count limits make every valid generation fit the byte ceiling; Core never truncates a field or entry to fit. Each age or count eviction increments only its corresponding loss counter, and counter or sequence exhaustion rejects the update rather than wrapping.

**Context:** Diagnostics must aid support without becoming a covert event store or consuming a machine indefinitely.

**Consequences:** Every update first exclusively creates and fsyncs one owner-recorded operational-state lock, then rereads and merges the latest generation, rechecks the exact lock, and uses same-directory durable temporary files and atomic replacement. The update sequence is assigned only while that cross-process lock is held, so it is the deterministic tie-breaker for equal trusted timestamps. Contending processes return unavailable without overwriting state; they never retry inside a hook. A stranded lock is inspected read-only and removed only after its exact process/start owner is independently proven dead. One recovery exclusively hard-links that fixed lock to a fixed same-filesystem claim, fsyncs and revalidates both names and the owner, removes the original name, and releases only the exact claim. Writers check the claim before and after creating their lock and remove only their exact record if a recovery began. A competing recovery, substituted lock, or delayed cleanup therefore cannot unlink a replacement writer; any recovery claim is conservatively reported as `reconciliation-required` and blocks mutation pending a separate explicit reconciliation command, whether or not the original fixed name remains. Corrupt, noncanonical, oversized, symlinked, or hostile state is rejected rather than salvaged. Read-only inspection treats a missing store as empty and does not create directories. Doctor reports retained status and loss counts; it cannot replay or reveal a discarded trace.

### ADR-003: Retain minimal positive and negative pipeline health evidence

**Decision:** Core's frozen hook result contains exactly one non-content marker for the invocation and one for each selected connection, up to Configuration Management's maximum of 32 routed connections. The hook marker contains only the closed stage/outcome vocabulary, configuration generation, and policy mode; a connection marker additionally contains the opaque connection identifier, destination type, and the matching closed receipt class or `null`. A fixed diagnostic contains only a closed code and severity, nullable configuration generation, and an optional exact destination-type/connection-id pair. No marker accepts a message, native error, path, selector, policy identity, delivery identity, trace/session identity, provider value, or arbitrary metadata. That returned result is the required in-process record even when Operational State is unavailable. While the hook budget remains, Core may also retain the same bounded markers with one trusted timestamp in Operational State; persistence failure never changes or delays the returned result, and Core starts no state write after global expiry.

**Context:** Failure-only diagnostics cannot distinguish a hook that never ran from capture, redaction, routing, delivery, or remote-acceptance boundaries.

**Consequences:** Markers contain no trace/session identifier, prompt, path, payload, credential, or provider response body. Doctor reports where local evidence ends without claiming remote history. Destination reachability uses declared non-mutating bounded probes and never sends trace content.

Checkpoint absence, expiry, eviction, corruption, or an unavailable state store means there is no acknowledged position. Before capture, Core exposes only a frozen one-shot resolver bound to the selected connections and current store; it reconstructs one exact plain-data request without executing caller accessors, derives the non-content digest from that frozen reconstruction, returns the authoritative retained or replay start, and is revoked immediately when capture returns or throws. An incremental adapter must select its window from that result and cannot submit an arbitrary initial tail. It otherwise uses its declared bounded replay window and preserves the original stable identity inputs. This can repeat previously delivered items, which is the safe at-least-once failure mode and is reported with a fixed checkpoint-unavailable diagnostic independently of whether capture or subsequent delivery succeeds. If the native source no longer contains the bounded replay window, capture starts at the earliest still-available boundary and records explicit loss rather than claiming continuity. Restart tests cover every loss class and prove that no still-available unacknowledged event is skipped.

Checkpoint mutation is a separate closed compare-and-advance operation performed under the same writer lock. Its key is the exact adapter registry identity, continuity digest, native-identity kind, source generation, position kind, and connection identifier. The attempted boundary's `startPosition` is the sole compare-and-swap expectation; Core advances only when `end > start` and, when the exact key exists, `start` equals its durable acknowledged end. A missing exact key is an initial or loss-replay insertion; for the same adapter, continuity digest, native-identity kind, position kind, and connection, its generation must be strictly greater than every retained older generation. A gap, overlap, out-of-order acceptance, generation reuse, or tuple mismatch returns a fixed non-advancing disposition and never replaces the durable entry. Only an `accepted` connection receipt may request advancement; rejected, unavailable, deadline-exceeded, outcome-unknown, and every partial-batch result never do. A successful update returns the new durable end but no native evidence. The raw continuity evidence is bounded to 4 KiB, canonical UTF-8, hashed by Core with a versioned domain separator, and discarded before this API; it can never enter the operational document.

### ADR-004: Keep Doctor inspection read-only and repair proof-bound

**Decision:** Core exposes one fixed, content-free Doctor report over the active configuration read result, immutable configuration-transaction and credential-mutation owner evidence, opaque credential-reference resolution, the operational writer lock, and bounded operational state. Inspection never reads a resolved credential capability into output and never creates, migrates, repairs, or rewrites machine state. Every finding has a closed code, severity, and suggested-action vocabulary.

**Context:** A diagnostic command must remain safe to run precisely when configuration, locks, credential sessions, or retained health evidence are malformed or unavailable.

**Consequences:** `doctor --fix` may delegate only to the fenced dead-owner configuration recovery defined by [Configuration Management](/docs/blueprints/operations/config-management) and dead-owner operational-state lock removal; it never deletes a credential because credential deletion is not reversible. Any recovery claim—whether fixed-plus-claim or claim-only—produces an error with the closed `reconcile-recovery-claim` action rather than an informational retry; the separate reconciliation command must re-establish proof for its exact state family before changing anything. Live or unknown owners, conflicting generations or digests, credentials, vendor state, and arbitrary files are never repaired or deleted. [CLI Architecture](/docs/blueprints/operations/cli-architecture) owns Doctor orchestration and its unified finding presentation. It composes read-only [Harness Discovery](/docs/blueprints/operations/harness-discovery), [Hook Installation](/docs/blueprints/operations/hook-installation), destination-declared reachability from [Trace Destination](/docs/blueprints/destinations/trace-destination), and Git-context inspection from [Native Trace Mapping](/docs/blueprints/foundations/native-trace-mapping). This Core seam is component evidence rather than a claim that every Doctor acceptance criterion is complete; a provably orphaned stored credential is only reported for a separate explicit cleanup command governed by Configuration Management.
