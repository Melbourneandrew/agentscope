## Capability Summary

Agentscope is an agent-developed TypeScript monorepo and needs mechanical, non-negotiable quality gates that preserve architectural boundaries before code reaches a pull request or `main`.

## Architecture Decision Records

### ADR-001: Use one strict shared quality baseline with narrow local additions

**Decision:** The repository uses one versioned shared ESLint flat-config baseline, strict TypeScript compiler settings, and Prettier for every TypeScript package and application. Package-local ESLint configuration may add rules, but may not relax the shared baseline without a time-bounded, reviewed exception.

**Context:** A many-package workspace otherwise drifts into inconsistent style and type-safety rules. Agent-generated changes benefit from immediate, deterministic feedback rather than informal conventions.

**Consequences:** ESLint uses type-aware rules for production and tests, including unsafe-value, promise, import, and unused-code checks. Test files receive no blanket promise or unsafe-type exemptions. Prettier is the sole formatting authority; ESLint does not duplicate formatting rules. TypeScript runs with the strictest practical settings, including `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, and `useUnknownInCatchVariables`; a proposed relaxation requires an ADR amendment.

### ADR-002: Enforce import direction mechanically

**Decision:** ESLint boundary rules enforce these dependency directions: `apps/cli` may depend on application Core and first-party integrations; `packages/core` may depend on Protocol and destination family Core; destination family Core may depend on Protocol but not application Core; concrete destination packages may depend on Protocol and destination family Core; harness packages may depend inward on Protocol, application Core, and harness family Core; `packages/testkit` may depend only on test-safe contracts; and tests may not import another package's private paths.

**Context:** Folder structure alone cannot prevent a convenient import from silently collapsing the canonicalization, redaction, and transport boundaries.

**Consequences:** Each workspace package declares a role and public entry points in the repository quality policy. Cross-package imports use package exports, never `src` paths. Destination code cannot import harness-native artifacts, and harness code cannot import a destination reporter. The workspace dependency graph and source entry graphs must be acyclic; unreachable production modules and duplicate imports fail validation. Seeded boundary, private-import, and cycle violations prove the controls fail closed.

### ADR-003: Give local feedback and CI distinct authority

**Decision:** Pre-commit and pre-push follow [Local Feedback](/docs/blueprints/operations/local-feedback). Local Nx result reuse follows [Nx Task Caching](/docs/blueprints/operations/nx-task-caching). CI never adopts local affected selection or cached success. Quality, unit, documentation, and integration follow the independently observable full-gate contract in [Continuous Integration](/docs/blueprints/operations/continuous-integration); native candidate verification alone may use that Blueprint's separate exact-revision, fail-closed changed-path decision and otherwise executes its complete component gate.

**Context:** Fast commit feedback prevents routine violations, while staged-only checks cannot establish workspace-wide correctness or detect changed public contracts.

**Consequences:** Generated files and approved vendored fixtures are explicitly excluded in configuration rather than ignored ad hoc. A hook is a convenience layer, not the authority: its affected selection and cache hits never become release evidence, and no PR may merge with a failing required CI job.

### ADR-004: Split CI by feedback horizon and trust boundary

**Decision:** CI has named, independently observable lanes: `quality` (format, lint, type check), `unit`, `docs`, `Native candidate verification`, and hermetic `integration`. Dependency installation is lockfile-frozen and cache keys include the lockfile and Node version. No CI lane receives third-party destination credentials or contacts a public destination service.

**Context:** The integration matrix is materially slower and has different Docker/artifact requirements than code quality. Separating lanes gives actionable failures and allows safe parallelism.

**Consequences:** Pull requests report quality, unit, docs, native candidate verification, and the defined hermetic compatibility matrix. Native candidate verification does not run inside the unit lane; its check either records the governed irrelevant-path disposition or runs the fresh non-admitting component verifier. Integration work is sharded by scenario without sharing scenario containers. Scheduled/manual workflows may run a wider hermetic version matrix. Documentation deployment remains a separate post-merge workflow and never grants publishing credentials to pull-request jobs.

### ADR-005: Enforce complexity and test posture through reviewed policy

**Decision:** The shared ESLint baseline limits cyclomatic complexity to 30, nesting depth to four, function length to 120 nonblank noncomment lines, and parameters to five. A versioned quality-policy registry declares every workspace role, unit-test posture, and coverage thresholds. Substantive TypeScript production code requires real Vitest tests; `--passWithNoTests` is permitted only for mechanically bounded marker-only scaffolds, while non-unit-test applications require a specific reviewed rationale.

**Context:** Uniform extreme thresholds would force cosmetic splitting in the disposable reference Core, while unbounded exceptions would let new packages silently evade tests. Marker bounds make temporary scaffolds self-expiring when implementation begins.

**Consequences:** The initial Core coverage floors are 40% statements, 35% branches, 45% functions, and 40% lines; Testkit floors are 70%, 45%, 85%, and 70%, respectively. These are rounded-down measurements of the current executable suites, not targets. Pull requests may raise but not lower an established threshold, and policy changes require review. Deterministic meta-tests seed architecture, private-import, dependency-cycle, type-safety, promise, formatting, complexity, dead-module, test-presence, and coverage failures.

### ADR-006: Bound authored source modules prospectively

**Decision:** Every authored JavaScript or TypeScript module has a ceiling of 500 substantive lines, measured by ESLint `max-lines` with blank and comment-only lines skipped. One canonical candidate grammar covers `.js`, `.jsx`, `.cjs`, `.mjs`, `.ts`, `.tsx`, `.cts`, and `.mts`, including their declaration forms; discovery, ESLint configuration, lint-staged, and CI consume that grammar. Authored JavaScript or TypeScript outside this grammar, including an extensionless Node entry point, is prohibited, and package, workflow, and script entry-point references are mechanically checked. One versioned quality policy performs closed, all-and-only discovery of tracked candidate paths and classifies each exactly once as governed authored source or a reviewed exclusion. New files and files at or below the ceiling fail when they exceed it. An explicit legacy inventory grandfathers each existing oversized file at its measured baseline, but never permits it to grow: recorded caps are monotonically non-increasing upper bounds, every accepted reduction lowers the cap in the same pull request, and the entry is removed when the file reaches 500 lines or is deleted. A pure rename may transfer one legacy cap from one removed path to one byte-identical new path; copies, multiple destinations, changed bytes, and rename-plus-growth are new-source failures.

Generated sources, vendored code, and data-only fixtures are outside this rule only through reviewed path classifications in that policy; executable fixture logic and tests remain governed authored source. Every exclusion mechanically proves its category: generated output bytes bind to a tracked generator and its governed inputs through a reproducible derivation, vendored files bind reviewed provenance, and data-only fixtures pass a non-executable content check. Category drift fails closed. A new or renewed exception requires a reviewed architectural rationale explaining why separation would weaken a concrete guarantee, a non-increasing path cap, an accountable removal-owner role, a machine-comparable expiry, and a removal condition. Unclassified, multiply classified, absent, stale, or expired entries fail closed. Inline rule suppression, narrower command discovery, and package-local configuration cannot bypass or relax this policy.

Required CI is authoritative for no-growth and policy admission. It compares the candidate policy and measured counts with the exact, unique merge base of the protected target branch; a missing or ambiguous base fails closed. It rejects a raised cap, exposes a new or widened exclusion for policy review, and rejects an exception renewal that raises its cap. The sole recovery transition is an isolated exact revert of one previously accepted change: CI verifies protected-main lineage, restores every source and policy path in the revert byte-for-byte to its state immediately before the reverted change, and permits no unrelated change. Any restored cap is therefore an earlier accepted value, never a new maximum. Local lint, including pre-commit feedback, consumes the same candidate grammar and policy but remains non-certifying under ADR-003.

**Context:** Several current integration and lifecycle modules combine thousands of substantive lines and cannot be split safely as an incidental change. Warning-only feedback would still admit further growth, while an immediate repository-wide failure would couple unrelated delivery to bulk refactoring.

**Consequences:** The initial inventory is a temporary migration boundary, not precedent for similarly sized modules or authority to add behavior to a listed file. Large test suites split by behavior when practical. Outside the exact recovery transition, no policy change may raise a recorded cap; widening an excluded path or creating an exception requires review of the classification, concrete rationale, and removal obligation. Non-legacy exceptions expire unless renewed through that review, and renewal cannot raise the cap. The prospective rule therefore blocks new debt without requiring a repository-wide rewrite before unrelated work can proceed.
