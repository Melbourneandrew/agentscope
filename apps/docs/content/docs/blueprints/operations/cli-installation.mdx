## Capability Summary

The `agentscope` command must be easy to install, stable for hooks, and publishable to npm.

## Architecture Decision Records

### ADR-001: Publish a dedicated CLI package

**Decision:** Publish `@agentscope/cli` from `apps/cli` with an unhyphenated `agentscope` bin entry. No library or SDK package is a supported public product.

**Context:** Hooks need one stable executable. Publishing internal packages before a concrete external-library use case would create accidental compatibility promises.

### ADR-002: Hook config calls an owned launcher, not embedded implementation

**Decision:** Generated harness configuration invokes the version-1 launcher at the exact machine-home path `<agentscope-home>/bin/agentscope-hook-v1` on POSIX and `<agentscope-home>\\bin\\agentscope-hook-v1.exe` on Windows. The launcher is an Agentscope-owned regular file rather than a symbolic link. Installation binds its contract version, exact physical path, release identity, runtime executable, bundled machine-entry path, digest, and mode in owned metadata and replaces it through the same durable transaction used for owned hook configuration. A POSIX verified script names one absolute Node executable in its shebang; a Windows launcher is a directly executable artifact. Neither form invokes a shell, searches `PATH`, consults a file association, or embeds harness-specific capture logic.

The launcher verifies its physical path and embedded home authority, derives no home or registry authority from the process environment, and enters the bundled machine command in the same process with that already resolved home. Generated harness configuration supplies only the exact versioned argument vector and the harness-native per-invocation evidence stream. Project `AGENTSCOPE_HOME` and process-current-directory changes cannot redirect the launcher or its machine home. A platform is unsupported for hook installation until its exact launcher form and replacement behavior are present in the release support manifest and verified on a native runner.

**Context:** Upgrades should replace one stable launcher rather than rewrite bespoke code into every harness config, while avoiding hook-time `PATH` lookup, shell interpretation, environment-selected loaders, or relocation ambiguity.

**Consequences:** A release upgrade changes the verified launcher at its stable machine-home path and leaves a compatible installed hook block unchanged. A missing, relocated, digest-mismatched, mode-mismatched, newer, or otherwise incompatible launcher is reported by status and Doctor before hook mutation; it is never adopted or downgraded implicitly. Launch failure remains fail-open at the harness-owned call site. Native-runner tests cover clean packed installation, absolute runtime resolution, environment redirection, relocation, compatible replacement, downgrade refusal, and removal.

### ADR-003: Make platform support a release-gated manifest

**Decision:** The CLI owns a machine-readable support manifest covering Node versions, operating systems, architectures, credential backends, required same-filesystem exclusive-create, durable rename, directory sync, and hard-link semantics, native dependencies, and the applicable evidence policy.

**Context:** Linux containers cannot prove Windows path/rename behavior, macOS or Windows credential access, GUI hook execution, or native dependency availability.

**Consequences:** A platform/runtime combination is supported only when install, configuration, credential, hook invocation, Doctor, upgrade, and uninstall checks pass on an appropriate native runner. Unsupported combinations fail with stable diagnostics; documentation derives claims from the manifest and current evidence.
