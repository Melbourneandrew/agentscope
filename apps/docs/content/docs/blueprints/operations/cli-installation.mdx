## Capability Summary

The `agentscope` command must be easy to install, stable for hooks, and publishable to npm.

## Architecture Decision Records

### ADR-001: Publish a dedicated CLI package

**Decision:** Publish the unscoped `agentscope-cli` package from `apps/cli` with an unhyphenated `agentscope` bin entry. No library or SDK package is a supported public product.

**Context:** Hooks need one stable executable. Publishing internal packages before a concrete external-library use case would create accidental compatibility promises.

### ADR-002: Hook config calls an owned launcher, not embedded implementation

**Decision:** Generated harness configuration invokes one version-1 launcher whose deterministic machine-home filename binds the exact harness registry-identity digest and canonical configured hook duration: `<agentscope-home>/bin/agentscope-hook-v1-<harness-digest>-d<duration>` on POSIX and the same basename with `.exe` on Windows. The launcher is an Agentscope-owned regular file rather than a symbolic link. Installation binds its contract version, exact physical path, full harness registry identity, configured duration, release identity, runtime executable, bundled machine-entry path, digest, and mode in owned metadata and replaces it through the same durable transaction used for owned hook configuration. The configuration generation used to plan installation is transaction evidence only; it is not launcher runtime authority, so an unrelated same-duration configuration mutation does not stale the block. The hook supplies no argument token; only its native per-invocation evidence stream enters standard input. A POSIX verified script names one absolute Node executable in its shebang; a Windows launcher is a directly executable artifact. Neither form invokes a shell, searches `PATH`, consults a file association, or embeds harness-specific capture logic.

Before planning any launcher or hook mutation on POSIX, the CLI resolves the exact Node executable and proves that its filesystem-byte representation is absolute, valid UTF-8, contains no NUL, carriage return, line feed, space, or tab byte, and produces one `#!<absolute-node-path>\n` line of at most 127 bytes. Failure is a fixed unsupported-runtime result and leaves the launcher and every hook target untouched. The release support manifest may narrow this admission rule for a platform but cannot admit a representation that its native runner has not executed directly through the kernel. The launcher is never generated with `/usr/bin/env`, a quoted interpreter, a second shebang argument, or a shell trampoline.

At its first userland instruction, before loading the general CLI or bundled machine entry, the launcher snapshots its physical path, rejects every external argument, parses the canonical duration and harness digest from its own basename, caps the duration at 60,000 milliseconds, and creates the monotonic absolute deadline. It then verifies the exact owned metadata and resolves the full registered identity under that deadline before entering the process-private bundled machine function with a non-serializable authority object. The identity is derived from owned launcher authority; it is not represented as independently observed proof that a particular external harness process made the call. Native executable-version evidence remains a separate observed-or-unavailable field. Direct manual execution of a genuine launcher cannot select a different adapter or duration and makes no stronger caller-authentication claim. The launcher derives no home or registry authority from the process environment. Project `AGENTSCOPE_HOME` and process-current-directory changes cannot redirect it or its machine home. A platform is unsupported for hook installation until its exact launcher form and replacement behavior are present in the release support manifest and verified on a native runner.

**Context:** Upgrades should replace one deterministic owned launcher rather than rewrite implementation code into every harness config, while avoiding hook-time `PATH` lookup, shell interpretation, environment-selected loaders, or relocation ambiguity.

**Consequences:** A release upgrade replaces the verified launcher at the deterministic authority path and leaves a compatible installed hook block unchanged; a harness or duration change creates the new authority path and transactionally replaces the owned block before retiring the old launcher under [Configuration Management ADR-003](/docs/blueprints/operations/config-management)'s reconciliation fence. A missing, relocated, digest-mismatched, mode-mismatched, newer, or otherwise incompatible launcher is reported by status and Doctor before hook mutation; it is never adopted or downgraded implicitly. Launch failure remains fail-open at the harness-owned call site. Native-runner tests cover clean packed installation, zero external arguments, authority-filename aliases, absolute runtime resolution, every rejected shebang byte/length boundary before mutation, direct kernel execution of the admitted launcher, environment redirection, relocation, compatible replacement, downgrade refusal, and removal.

### ADR-003: Make platform support a release-gated manifest

**Decision:** The CLI owns a machine-readable support manifest covering Node versions, operating systems, architectures, credential backends, required same-filesystem exclusive-create, durable rename, directory sync, and hard-link semantics, native release-build inputs and their exact vendored runtime files, and the applicable evidence policy. It also binds the exact product destination and advertised harness registry identities; registry presence, immutable-candidate execution eligibility, and published-release support admission are distinct authorities. It distinguishes a full supported-platform tuple, which owns credential/filesystem/lifecycle and other end-to-end evidence, from a native-binary compatibility tuple, which owns only the binary's Node ABI and admitted-major, OS/minimum, architecture, and libc/minimum dimensions. Every admitted full tuple has one total unambiguous native projection; several full tuples may reference one native tuple only through an identical projection. A vendored native capability entry binds its upstream artifact and source integrity, exact binary origin and build-material ledger, license/notice inventory, provenance and SBOM digests, owned loader contract, build and native-execution sandbox profiles, exactly one included regular-file path/size/digest per native-binary tuple, and the required supervisor evidence policy. Ambiguous projections, multiple binaries for one native tuple, a binary claimed by incompatible native tuples, missing/unreferenced binaries, and extra binaries reject the manifest; merely registering, shipping, or loading a binary never marks the capability supported.

An immutable unpublished candidate may contain and execute a manifest-declared proposed tuple so the credential-free sacrificial certification boundary can produce evidence for that same candidate digest. This is execution eligibility, not a public support claim. The external release gate, not the candidate itself, authenticates that evidence and admits the tuple for publication. Publication is forbidden until the complete required packed-CLI lifecycle passes, so no independently rebuilt or post-evidence-mutated artifact is needed and an end user never receives a release whose declared tuple lacks its external admission record.

For a native Local SQLite tuple, the external admission record is the exact all-and-only aggregate of three same-candidate, same-native-tuple, same-full-platform operational profiles plus the Local manifest's closed crash-gate record set. The ordinary-bin configuration profile proves clean install, registration, configure, non-content Doctor, unconfigure, a fresh-process retained-data inspection, and confirmed deletion. The actual-harness delivery profile proves Reporter deadline/failure behavior, retention, routing, and search/get. The maintenance/upgrade profile proves migration, backup/restore, CLI upgrade, retained ownership, deletion, and uninstall. Across those profiles, credential creation, resolution in the installed and hook-equivalent contexts, rotation or replacement, and cleanup use the exact credential backend named by the full tuple; CI environment references satisfy only a tuple that names that backend.

The maintenance profile contains an exact one-to-one predecessor case set equal to the support manifest's finite nonempty predecessor set, with no missing, extra, or duplicate predecessor. Each predecessor case starts from one exact eligible tarball named by disposition, version, source revision, integrity digest, product-registry identity, support-manifest identity, lifecycle fingerprints, and configuration-reader window. Nested inside it is an exact all-and-only case for every harness that predecessor advertised for the full tuple. Each nested case binds the harness identity and launcher contract/release identity, uses that predecessor's ordinary bin to create valid destination configuration, installs that exact harness and owned launcher/block, and invokes the launcher before upgrading in the declared direction to the candidate. After upgrade it invokes the preserved compatible launcher or proves the exact removal/incompatibility was reported before harness mutation, then verifies status and Doctor expose the governed installed or reconciliation state. Candidate-new harnesses are separately clean-installed and do not masquerade as upgrade cases. A same-version reinstall, synthetic state, rebuilt predecessor, unsupported direction, missing predecessor, mixed predecessor identities, absent installed integration, or missing, extra, duplicate, or untested predecessor/harness pair rejects the profile.

Ordinary successor entries name a prior published release. The first admission of each exact full-platform Local support lineage may instead name exactly one bootstrap predecessor: an immutable protected-main candidate from an earlier source revision, produced by the same trusted release pipeline, eligible for publication, retained by digest, and independently proven through that tuple's configuration, actual-harness delivery, installed-launcher, and lifecycle setup, but intentionally withheld from users. The permanent bootstrap-consumption key is only the complete full platform tuple plus the stable Local destination support-lineage identifier; native projections, product registries, lifecycle capabilities, configuration readers, and harness inventories are ordered generations and explicit admissible transitions inside that lineage, never new lineage keys. The support manifest permanently records admitted and retired lineage keys and their generations; removal, renaming, contract evolution, or later re-addition never resets bootstrap eligibility. Every post-first generation for that lineage uses the exact published-predecessor and predecessor-by-harness case sets. An empty predecessor set can publish only an artifact that claims no supported full platform tuple and returns the stable unsupported diagnostic before mutation.

The closed crash-gate record set proves every deterministic durable prefix through owned test-only fault barriers against the production built artifacts. The candidate pack verifier accepts no independent rebuild: it consumes those exact verified component artifacts in the candidate build, records the exact input file digests, build-tool/configuration identity, and bundler closure map into the candidate outputs, and proves every crash-tested production file is included in the candidate closure. Each crash record binds its operation, prefix, expected disposition, component artifact, fault-barrier version, candidate closure map, and candidate digest. Missing, extra, duplicate, mixed-candidate, unmapped, or unassigned operational-profile or crash-gate evidence rejects the aggregate. Only that aggregate admits publication.

**Context:** Linux containers cannot prove Windows path/rename behavior, macOS or Windows credential access, GUI hook execution, or native dependency availability.

**Consequences:** A platform/runtime combination is supported only when install, configuration, credential, hook invocation, Doctor, upgrade, and uninstall checks pass on an appropriate native runner. Unsupported released combinations fail with stable diagnostics before destination or harness mutation; documentation derives claims from the product registry, support manifest, and external admission record. The tarball verifier proves that no alternate registry, certification harness, or mutating test entry enters the publication closure.
