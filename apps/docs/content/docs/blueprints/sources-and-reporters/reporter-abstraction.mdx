## Capability Summary

Reporters send redacted canonical batches to an external destination for the [Reporting and Destinations](/docs/requirements/reporting-and-destinations) capability.

## Architecture Decision Records

### ADR-001: Require reporting, make retrieval optional

**Decision:** Every Trace Destination has a reporter; only destinations that support queries expose a retriever.

**Context:** Delivery is core product behavior while many valid destinations are write-only.

### ADR-002: Centralize delivery policy

**Decision:** Core owns redaction, batching, idempotency, retries, and spool limits; reporters map a batch and return a receipt.

**Context:** Failure semantics cannot vary by destination or block a harness.

### ADR-003: Make destination testing a package capability

**Decision:** Each first-party Trace Destination package supplies a `DestinationTestAdapter` that configures its mock endpoint and translates its request ledger into generic reporting/retrieval assertions.

**Context:** Langfuse/OTLP is the first destination, not an assumption embedded in harness tests.

**Consequences:** A future Phoenix/Arize, direct-Langfuse, warehouse, console, or internal reporter extends the suite through a reviewed Agentscope pull request without changing scenario orchestration or harness packages.

### ADR-004: Do not ship a runtime plugin loader in v1

**Decision:** V1 supports only first-party harness and Trace Destination packages published from this monorepo. Adding a harness or destination is a reviewed pull request and release, not a user-installed executable plugin.

**Context:** A Node package loaded in the CLI process has ambient filesystem, environment, and network authority. A generic plugin loader would create a security, compatibility, and support commitment before there is a demonstrated external need.

**Consequences:** Core owns credentials, redaction, delivery, and retrieval boundaries. The package contracts remain internal but well-tested so they can become a public SDK only after real contribution patterns justify a stable ABI.

### ADR-005: Reserve a constrained enrichment seam instead of arbitrary code

**Decision:** V1 supports declarative, schema-validated filtering, redaction, and additional metadata rules owned by Core. It does not execute user-supplied enrichers or filters. A future enrichment SDK must receive an already-redacted canonical envelope and pass its output through final redaction, with explicit capability, privacy, ordering, and failure semantics.

**Context:** Filtering and metadata attachment are the most plausible user extension needs, but arbitrary callbacks could see sensitive data, block hooks, or make output non-reproducible.

**Consequences:** Declarative rules have deterministic tests and Doctor diagnostics. Any later executable extension must be separately designed with a real isolation boundary, narrow RPC/capabilities, no inherited credentials, and a stable public versioning policy.

### ADR-006: Drain delivery opportunistically without a resident daemon

**Decision:** A hook makes one bounded delivery attempt, then enqueues retryable work with persisted due time and backoff state. Core drains due entries under a single-writer lock on later hook or CLI invocations, and `agentscope flush` provides explicit foreground delivery; there is no background daemon in the initial release.

**Context:** A hook process usually exits immediately, so a spool without a later execution trigger does not provide reliable delivery. A resident process introduces platform service management, credentials, and lifecycle complexity outside the first release.

**Consequences:** Retry scheduling uses persisted exponential backoff with jitter and idempotency keys. The integration matrix includes restart, due-entry drain, lock-contention fail-open, and explicit-flush scenarios. Delayed delivery is observable through Doctor rather than silently promising immediate retry.
