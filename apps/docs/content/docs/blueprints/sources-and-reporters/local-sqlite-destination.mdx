title: Local SQLite Destination
description: ADRs for an explicit local durable Trace Destination.
---

## Capability Summary

The local SQLite destination gives a user an opt-in durable trace repository and retrieval capability without requiring Langfuse or another remote observability service.

## Architecture Decision Records

### ADR-001: Make local SQLite a separate opt-in destination

**Decision:** A first-party Local SQLite Trace Destination provides both reporter and retriever behavior. It is disabled by default and exists only after `agentscope destination configure local-sqlite` succeeds with explicit user confirmation.

**Context:** Default AgentScope capture is intentionally non-durable: a failed hook-time report is discarded. A local database materially changes privacy, disk, retention, and backup expectations and must be a user-selected destination rather than hidden runtime state.

**Consequences:** Once configured, Local SQLite receives the same redacted Protocol graph as every other destination. It has no credentials by default. Its retention and data controls are destination settings, not Core diagnostics.

### ADR-002: Treat remote SQLite-compatible services as distinct destinations

**Decision:** Local SQLite is a filesystem destination. A remote SQLite-compatible service such as libSQL/Turso is a separate future Trace Destination type with its own endpoint, credential slots, network behavior, and availability contract.

**Context:** A network filesystem SQLite file is not a safe substitute for a database service: locking, durability, latency, and failure semantics differ substantially from a local database.

**Consequences:** A shared internal SQLite schema/migration utility may be reused, but `local-sqlite` and a future remote service do not share a configuration type or pretend to have identical reliability properties.

### ADR-003: Configure and migrate deliberately

**Decision:** Local SQLite configuration validates the selected path, retention settings, and writable directory before atomically recording the destination. Database schema provisioning and future schema migrations run transactionally on first configuration or explicit upgrade, with a schema-version record and clear failure diagnostic.

**Context:** Creating a database is a material mutation and must not occur merely because `agentscope init` discovered that local storage is possible.

**Consequences:** Init may propose the destination but never enables it by default. The database driver and migration runner remain an implementation decision until a short prototype measures packaging, cross-platform behavior, backups, and upgrade recovery; an ORM is not selected solely to provide migrations.
