## Capability Summary

This Blueprint records the technical boundaries behind [Reporting and Destinations](/docs/requirements/reporting-and-destinations).

## Architecture Decision Records

### ADR-001: Keep harness extraction separate from destination export

**Decision:** Harness adapters own native extraction; core owns normalized trace semantics; reporter plugins own destination protocol mapping.

**Context:** A harness should not need Langfuse knowledge, and a new destination should not require hook changes across every harness.

**Consequences:** The first-party Langfuse reporter is an implementation of the plugin boundary, not a special case in adapters.

### ADR-002: Centralize reliability behavior in core

**Decision:** Core owns redaction, batching, idempotency, retry classification, and bounded spooling before invoking a reporter.

**Context:** Delivery semantics must not drift per destination or cause a harness to block on network behavior.

**Consequences:** Reporters return delivery receipts and errors; they do not implement their own durable queue or access raw source artifacts.

### ADR-003: Start Langfuse with OTLP

**Decision:** Ship Langfuse reporting through an OTLP mapping first and permit a direct Langfuse reporter later behind the same normalized boundary.

**Context:** OTLP gives the integration suite a clear mock collector contract while preserving room for a destination-specific ingestion path.
