## Capability Summary

The same manifest drives a small selected local scenario and the complete hermetic CI matrix without leaving dependencies, containers, or mock routing on a developer workstation.

## Architecture Decision Records

### ADR-001: Make local execution targeted and safe by default

**Decision:** Local commands select an explicit scenario, harness, tag, deterministic shard, or deliberate full run and execute it in Docker. They print exact named containers, networks, images, and fixed-root artifact paths before cleanup; `pnpm test:integration:clean` removes only validated owned targets.

**Context:** Developers may use AgentScope and coding harnesses outside this repository. A test command must not alter their real configuration or make their active agents talk to MockServer.

**Consequences:** The suite never mounts the user's home or injects model endpoint variables into the host shell. Repeated local runs reuse only named, bounded prepared inputs; scenario and sidecar resources have explicit memory, process, request, concurrency, and time ceilings. Resource names and labels bind the canonical physical Docker daemon-incarnation identity from ADR-003, repository identity, workspace identity, and fresh run nonce. Run registration and repository-owned artifact mutation use one host-local OS socket lease derived from that daemon incarnation plus repository identity, so separate worktrees of this repository cannot hold conflicting cleanup authority. Each run then holds a fresh-nonce claim in that repository-scoped registry bound to the same daemon, repository, and workspace identities plus either a non-reusable operating-system process handle or the authenticated tuple of host boot identity, process identifier, and process start identity; PID-only liveness is never authority. Under the socket lease, a later controller double-checks the exact claim and may advance it to a new exclusive fenced recovery generation only after the bound operating-system identity proves that exact owner no longer exists. Live or indeterminate identity blocks reclamation; every admitted crash prefix therefore resumes the exact live generation, advances a proved-dead generation for exact reconciliation, or fails closed. A proved stale claim authorizes reconciliation only of the exact run identities recorded by that generation, and generation revalidation precedes each mutation. Cleanup removes only exact repository/run-specific containers, networks, volumes, tags, references, archives, contexts, and evidence; it never deletes a shared content digest from the Docker or BuildKit store, whose garbage collection remains daemon-owned. The kernel releases exclusion when its owner exits, so interruption cannot leave a stale pathname lock. Cleanup is inspectable, accepts only exact bound labels and identities, and never follows symlinked roots or recursively accepts an arbitrary path.

### ADR-002: Gate pull requests with the defined hermetic matrix

**Decision:** Pull requests run unconditional, separately sharded scenarios for all and only the finite exact support rows claimed by the applicable release support manifest. Each shard binds the exact support-row identity, clean-installs the same packed CLI candidate, invokes the catalog-pinned actual binary, uses only internal model mocks and the loopback OTLP ledger, denies public egress, and proves cleanup. No path, relevance classifier, or deduplication by version/mode may omit or combine claimed rows. Scheduled/manual CI may run broader advisory coverage, but it never changes the required pinned set or contacts a model provider, Langfuse, or another public destination service.

**Context:** The fast required matrix detects cross-harness regressions without making every PR wait for every historical version. Hermetic execution keeps evidence deterministic and avoids exposing provider credentials or test data to an external service.

**Consequences:** A prerequisite job prepares the candidate once; shard and replay jobs consume that exact checksum-bound artifact, exact support-row identity, and catalog-authenticated harness identity. Manual dispatch can select one exact manifest scenario. The CI summary reports the exact support-row identity, including its harness claim, full-platform tuple, and destination combination, plus the backend-appropriate prepared artifact identity and scenario identity. A matrix change that lowers a release claim requires changing the release support manifest rather than silently weakening CI.

### ADR-003: Fence uncertain daemon mutation across controller exit

**Decision:** Before a trusted executor starts an operation that may mutate the Docker daemon after its client stops responding, it uses the ADR-001 socket lease to durably add one operation record inside that run's existing canonical registry claim. There is no second claim, ledger, or recovery-generation authority. Each run serializes these operations and has at most one unresolved operation record. The enclosing run-claim generation is the sole mutation authority and is revalidated for every operation transition and reconciliation step; the nested operation revision is only a compare-and-swap record identity. The immutable operation plan binds the canonical daemon incarnation, repository, workspace, run, exact executable and operation, family-owned settlement class, and an all-and-only terminal inventory projection. The projection classifies every exact builder, tag or reference, container, network, volume, context, archive, and evidence identity as temporary or success-retained; it never includes shared Docker or BuildKit content digests. Success-retained output transfers atomically to the enclosing run claim and its consumer lease only after authenticated success. Without that transfer, every operation-created resource is terminal only when absent, apart from the one bounded failure record.

Launch is two-phase. Under the socket lease, the controller first durably writes the `reserved` plan, then starts an exact trusted launch gate in a fresh authenticated process set without daemon authority or the operation request. It durably binds that gate's process-start identity and advances the operation to `armed`; a closed control channel before release makes the gate exit without mutation. Only after revalidating the run-claim generation, operation revision, gate identity, and daemon incarnation does the controller send the one-use daemon authority and exact request. The operation then moves through the closed `released`, `observed`, `uncertain`, `reconciling`, and `reconciled` states. Every transition uses private no-follow state, atomic replacement, and directory durability. Clearing a reconciled operation record returns only the enclosing run claim to active state; only ADR-001's complete run cleanup may clear the run claim.

Each admitted operation kind has one family-owned settlement mapping. A passive output is never a settlement witness. An authenticated success response plus terminal operation process set is the normal witness; a single-resource create may instead use authenticated appearance of its sole exact output when that API contract proves no later mutation. A build requires a joinable boundary that covers the builder and every import or publication step; if such terminal settlement is unavailable after client failure, same-incarnation resource absence cannot clear the fence. The controller records `reconciled` only after the settlement witness is terminal and every immutable inventory projection is satisfied. An uncertain operation and its enclosing run claim survive client close and controller exit, block later repository mutation on that daemon, and retain no success output or consumer lease.

A later controller may enter `reconciling` only under the socket lease, after advancing the enclosing run claim to one exclusive recovery generation and independently proving the recorded owner and operation process set dead. It revalidates that run generation, operation revision, and daemon incarnation before every exact-identity mutation. If the operation-specific settlement witness cannot be proved, the fence remains until the recorded daemon incarnation is independently retired. One canonical daemon-incarnation identity is used by the lease, run claim, operation, labels, and evidence; it authenticates the endpoint process lifetime, backend daemon lifetime, and storage root. Retirement proves that exact endpoint and daemon process set terminal and unable to publish, and replacement binds a distinct authenticated incarnation. A backend that cannot prove this identity or retirement cannot use daemon replacement to clear uncertainty. The replacement daemon's exact bound inventory is reconciled before the operation becomes `reconciled`.

Malformed, oversized, substituted, symlinked, or otherwise unauthentic operation authority is quarantined without interpreting its resource identities and blocks automated mutation or cleanup. It can return authority only after an operator supplies a distinct authenticated daemon incarnation and storage root with no repository-owned inventory, then uses the socket lease to archive the exact quarantined inode and advance the enclosing run claim to a closed `authority-replaced` failure disposition. Otherwise it remains fenced. Its bounded content-free failure record binds only independently trusted outer-run identity, quarantined inode identity and digest, replacement daemon incarnation, and the closed disposition; the original operation revision and daemon identity remain explicitly unknown. An ordinarily uncertain operation instead binds its authenticated run, operation revision, daemon incarnation, and closed recovery disposition. Neither record is prepared-input, successful-cleanup, cache-adoption, or scenario-pass evidence.

**Context:** A client timeout or closed local socket does not prove that daemon-side creation or publication stopped. An in-memory marker disappears with the controller and can permit a later run to race a surviving mutator or delayed resource publication.

**Consequences:** This is one testing-infrastructure recovery authority shared by uncertain preparation builds and Docker evidence-volume creation; those capabilities do not define parallel ledgers or clearing rules. Prefix sweeps, elapsed polling, tag or name absence alone, controller-exit cleanup, and deletion of shared daemon content cannot establish terminal state. The claim stores identities and closed state only, never credentials, commands containing secrets, artifact contents, or scenario evidence.
