## Capability Summary

The same manifest drives a small selected local scenario and the complete hermetic CI matrix without leaving dependencies, containers, or mock routing on a developer workstation.

## Architecture Decision Records

### ADR-001: Make local execution targeted and safe by default

**Decision:** Local commands select an explicit scenario, harness, tag, deterministic shard, or deliberate full run and execute it in Docker. They print exact named containers, networks, images, and fixed-root artifact paths before cleanup; `pnpm test:integration:clean` removes only validated owned targets.

**Context:** Developers may use AgentScope and coding harnesses outside this repository. A test command must not alter their real configuration or make their active agents talk to MockServer.

**Consequences:** The suite never mounts the user's home or injects model endpoint variables into the host shell. Repeated local runs reuse only named, bounded prepared inputs; scenario and sidecar resources have explicit memory, process, request, concurrency, and time ceilings. Resource names and labels bind the canonical physical Docker daemon-incarnation identity from ADR-003, repository identity, workspace identity, and fresh run nonce. Run registration, daemon-incarnation selection, and repository-owned artifact mutation use one host-local OS socket lease derived from host-boot plus repository identity, so separate worktrees or daemon incarnations cannot hold conflicting cleanup or handoff authority. The canonical repository registry records the selected daemon incarnation. Each run then holds a fresh-nonce claim in that registry bound to the same daemon, repository, and workspace identities plus either a non-reusable operating-system process handle or the authenticated tuple of host boot identity, process identifier, and process start identity; PID-only liveness is never authority. Under the socket lease, a later controller double-checks the exact claim and may advance it to a new exclusive fenced recovery generation only after the bound operating-system identity proves that exact owner no longer exists. Live or indeterminate identity blocks reclamation; every admitted crash prefix therefore resumes the exact live generation, advances a proved-dead generation for exact reconciliation, or fails closed. A proved stale claim authorizes reconciliation only of the exact run identities recorded by that generation, and generation revalidation precedes each mutation. Cleanup removes only exact repository/run-specific containers, networks, volumes, tags, references, archives, contexts, and evidence; it never deletes a shared content digest from the Docker or BuildKit store, whose garbage collection remains daemon-owned. The kernel releases exclusion when its owner exits, so interruption cannot leave a stale pathname lock. Cleanup is inspectable, accepts only exact bound labels and identities, and never follows symlinked roots or recursively accepts an arbitrary path.

### ADR-002: Gate pull requests with the defined hermetic matrix

**Decision:** Pull requests run unconditional, separately sharded scenarios for all and only the finite exact support rows claimed by the applicable release support manifest. Each shard binds the exact support-row identity, clean-installs the same packed CLI candidate, invokes the catalog-pinned actual binary, uses only internal model mocks and the loopback OTLP ledger, denies public egress, and proves cleanup. No path, relevance classifier, or deduplication by version/mode may omit or combine claimed rows. Scheduled/manual CI may run broader advisory coverage, but it never changes the required pinned set or contacts a model provider, Langfuse, or another public destination service.

**Context:** The fast required matrix detects cross-harness regressions without making every PR wait for every historical version. Hermetic execution keeps evidence deterministic and avoids exposing provider credentials or test data to an external service.

**Consequences:** A prerequisite job prepares the candidate once; shard and replay jobs consume that exact checksum-bound artifact, exact support-row identity, and catalog-authenticated harness identity. Manual dispatch can select one exact manifest scenario. The CI summary reports the exact support-row identity, including its harness claim, full-platform tuple, and destination combination, plus the backend-appropriate prepared artifact identity and scenario identity. A matrix change that lowers a release claim requires changing the release support manifest rather than silently weakening CI.

### ADR-003: Fence uncertain daemon mutation across controller exit

**Decision:** The trusted outer controller is the sole attestation owner for one canonical Docker daemon-incarnation identity covering the exact endpoint process lifetime, backend daemon lifetime, and storage root. Every Docker backend proves that identity before the ADR-001 lease admits selection or mutation; an unavailable or weaker identity makes the backend unsupported. Before a mutation that may outlive an unsettled client, the controller uses that lease to durably add one operation record inside the run's existing canonical registry claim. There is no second claim, ledger, or recovery-generation authority. Each run serializes operations and has at most one unresolved operation. The enclosing run-claim generation is the sole mutation authority and is revalidated for every transition and reconciliation step; the nested operation revision is only compare-and-swap identity.

The immutable operation plan binds the daemon incarnation, repository, workspace, run, exact executable and operation, family-owned settlement class, and an all-and-only terminal inventory projection. It classifies every exact builder, tag or reference, container, network, volume, context, archive, and evidence identity as temporary or success-retained; it never includes shared Docker or BuildKit content digests. On authenticated success, retained output moves in one atomic registry transition from the operation into the enclosing run's generation-fenced retained-resource set. Every consuming run generation is added to or removed from that same set under the socket lease; there is no separate consumer lease. Without successful transfer, every operation-created resource is terminal only when absent, apart from the bounded failure record.

Launch is two-phase. The controller durably writes `reserved`, starts an exact trusted launch gate in a fresh authenticated process set without daemon authority or the request, durably binds its process-start identity as `armed`, then durably records `releasing` before it can send the one-use daemon authority and exact request. `reserved` cancels without spawn; an `armed` gate whose channel closes exits without mutation; `releasing` is conservatively mutation-possible whether transmission occurred or not. An authenticated gate acknowledgement advances to `released`; observation or loss advances to `observed` or `uncertain`. The remaining closed states are `reconciling`, `reconciled`, and `retired-failure`. Every transition uses private no-follow state, atomic replacement, and directory durability. Clearing `reconciled` returns only the enclosing run claim to active state; only ADR-001's complete run cleanup may clear that claim.

Settlement mappings are closed here. A BuildKit preparation succeeds only when the exact gated buildx client returns authenticated success, its process and streams join, its isolated builder is terminal, every import or publication step is complete, and the prepared identity matches; after any client uncertainty it has no same-incarnation settlement shortcut and requires daemon-incarnation retirement. Docker evidence-volume creation is a single-output operation: authenticated appearance of the sole exact generation-labelled volume proves that create call can perform no later mutation, after which exact removal settles failure cleanup. Other operation kinds are unsupported until an earlier Blueprint adds their exact causal witness. Passive tags, references, archives, or partial build outputs never witness settlement.

A later controller enters `reconciling` only under the socket lease, after advancing the enclosing run claim to one exclusive recovery generation and independently proving the owner and operation process set dead. It revalidates that run generation, operation revision, and daemon incarnation before every exact mutation. It records `reconciled` only after the operation witness is terminal and the immutable inventory projection is satisfied. If no witness can be proved, the old endpoint and daemon process set must be terminal and the old storage authority must be irreversibly offline and non-reusable. Under the same host-and-repository lease, the controller writes a permanent tombstone for that incarnation and atomically selects a distinct authenticated daemon incarnation and clean storage root. The operation ends as `retired-failure`, never cleanup success; old resources may remain only inside the permanently quarantined storage. Selecting a tombstoned incarnation or storage root is always rejected.

Malformed, oversized, substituted, symlinked, or otherwise unauthentic nested operation authority is quarantined without interpreting its resource identities. If the enclosing run claim remains authentic, only the known bound daemon-incarnation retirement and permanent-tombstone path above can return mutation authority. If the enclosing claim or daemon identity is unauthentic, no in-place replacement is allowed: the host-and-repository registry remains fenced, and work may resume only on a fresh disposable host with a distinct authenticated host boot, daemon incarnation, and empty storage root; the old host remains quarantined. Corrupt-authority failure evidence binds only independently trusted outer identity and quarantined inode identity and digest; original operation and daemon fields are explicitly unknown. Ordinary uncertainty instead binds its authenticated run, operation revision, daemon incarnation, and closed disposition. Neither is prepared-input, successful-cleanup, cache-adoption, or scenario-pass evidence.

**Context:** A client timeout or closed local socket does not prove that daemon-side creation or publication stopped. An in-memory marker disappears with the controller and can permit a later run to race a surviving mutator or delayed resource publication.

**Consequences:** This is one testing-infrastructure recovery authority shared by uncertain preparation builds and Docker evidence-volume creation; those capabilities do not define parallel ledgers or clearing rules. Prefix sweeps, elapsed polling, tag or name absence alone, controller-exit cleanup, and deletion of shared daemon content cannot establish terminal state. The claim stores identities and closed state only, never credentials, commands containing secrets, artifact contents, or scenario evidence.
