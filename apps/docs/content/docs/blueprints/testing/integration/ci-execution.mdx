## Capability Summary

The same manifest drives a small selected local scenario and the complete hermetic CI matrix without leaving dependencies, containers, or mock routing on a developer workstation.

## Architecture Decision Records

### ADR-001: Make local execution targeted and safe by default

**Decision:** Local commands select an explicit scenario, harness, tag, deterministic shard, or deliberate full run and execute it in Docker. They print exact named containers, networks, images, and fixed-root artifact paths before cleanup; `pnpm test:integration:clean` removes only validated owned targets.

**Context:** Developers may use AgentScope and coding harnesses outside this repository. A test command must not alter their real configuration or make their active agents talk to MockServer.

**Consequences:** The suite never mounts the user's home or injects model endpoint variables into the host shell. Repeated local runs reuse only named, bounded prepared inputs; scenario and sidecar resources have explicit memory, process, request, concurrency, and time ceilings. Resource names and labels bind the physical Docker daemon identity, repository identity, workspace identity, and fresh run nonce. Run registration and repository-owned artifact mutation use one host-local OS socket lease derived from the physical Docker daemon plus repository identity, so separate worktrees of this repository cannot hold conflicting cleanup authority. Each run then holds a validated host-process claim in that repository-scoped registry. Cleanup removes only exact repository/run-specific containers, networks, tags, references, archives, contexts, and evidence; it never deletes a shared content digest from the Docker or BuildKit store, whose garbage collection remains daemon-owned. The kernel releases exclusion when its owner exits, so interruption cannot leave a stale pathname lock. Cleanup is inspectable, accepts only exact bound labels and identities, and never follows symlinked roots or recursively accepts an arbitrary path.

### ADR-002: Gate pull requests with the defined hermetic matrix

**Decision:** Pull requests run unconditional, separately sharded scenarios for every harness version and mode claimed by the applicable release support manifest. Each shard clean-installs the same packed CLI candidate, invokes the catalog-pinned actual binary, uses only internal model mocks and the loopback OTLP ledger, denies public egress, and proves cleanup. No path or relevance classifier may omit a claimed row. Scheduled/manual CI may run broader advisory coverage, but it never changes the required pinned set or contacts a model provider, Langfuse, or another public destination service.

**Context:** The fast required matrix detects cross-harness regressions without making every PR wait for every historical version. Hermetic execution keeps evidence deterministic and avoids exposing provider credentials or test data to an external service.

**Consequences:** A prerequisite job prepares the candidate once; shard and replay jobs consume that exact checksum-bound artifact and the catalog's authenticated harness identity. Manual dispatch can select one exact manifest scenario. The CI summary reports each harness/version/destination result, canonical prepared-image identity, and scenario identity. A matrix change that lowers a release claim requires changing the release support manifest rather than silently weakening CI.
