## Capability Summary

Workstation execution provides the focused deterministic development checks selected by [Local Feedback](/docs/blueprints/operations/local-feedback). Mutation-heavy integration runs only on a disposable Crabbox guest or a GitHub-hosted CI runner. Crabbox execution and CI execution share the inner hermetic scenario runner and manifest contract, while their outer orchestration and authority remain distinct: Crabbox is development and burst capacity, and GitHub-hosted CI is release authority.

## Architecture Decision Records

### ADR-001: Keep workstation execution focused and nonmutating

**Decision:** Workstation execution supports unit, lint, typecheck, build, package, and focused deterministic component checks selected by Local Feedback. It may validate integration catalogs, manifests, adapters, and candidate artifacts without starting a mutation-bearing integration backend. A workstation request for a mutation-heavy integration scenario fails with a concise instruction to use Crabbox execution or CI execution.

Workstation integration must not connect to Docker Desktop, a shared host daemon, or any ambient Docker context. It must not bootstrap Docker-in-Docker, a nested or private `dockerd`, a Lima or VZ guest, a custom daemon storage root, or a durable cross-run Docker registry or recovery ledger.

**Context:** A developer workstation may contain unrelated agents, credentials, containers, networks, and configuration. Attempting to make it a disposable mutation boundary adds a second platform architecture while still leaving host lifecycle and recovery coupled to a long-lived machine.

**Consequences:** Workstation checks remain useful and bounded without claiming scenario, compatibility, or release evidence. Mutation-heavy integration is not a workstation fallback. Local Feedback owns affected selection, [Nx Task Caching](/docs/blueprints/operations/nx-task-caching) owns local result reuse, and this Blueprint owns only the location boundary.

### ADR-002: Select intermediate PR scenarios without reducing pre-merge coverage

**Decision:** Path-aware integration selection applies only to intermediate pushes of a pull request. `tests/integration/capability-manifest.json` is the executable versioned catalog defined by [Matrix Operations ADR-001](/docs/blueprints/testing/integration/matrix-operations), not a second scenario authority. It is the one enumerable owner of integration scenario identities and finite adversarial substrate cases and also owns the closed Nx project/path-to-scenario selector index over those catalog identities. The selector authenticates the exact base and head, observes the complete name-status diff without rename detection so deleted paths and both sides of a rename remain visible, and resolves that index against the Nx project graph and every catalog scenario. Missing, extra, or multiply owned mappings fail closure and select the complete matrix. Each affected scenario clean-installs the same checksum-bound packed CLI candidate, invokes the catalog-pinned actual binary, uses only internal model mocks and the loopback OTLP ledger, denies public egress, and proves terminal lifecycle. An ordinary relevant adapter change runs each selected scenario once. A change to workflow or selection authority, the integration runner, isolation, cleanup, nondeterminism controls, release policy, release-support data, or their transitive inputs runs the complete matrix with three clean replays. An empty, malformed, oversized, unavailable, mixed, or unknown change set also runs that complete three-replay matrix.

Documentation-only and provably unrelated changes allocate no hermetic runner, but the stable required `hermetic-integration` context still succeeds with the canonical classifier reason. Every pull request then runs one complete candidate matrix before merge. With merge queue, the candidate identity is the exact merge-group commit, and merge-group branch protection requires the App-bound final context. Without merge queue, a ready-to-merge request made by an actor with merge authority binds the pull-request number and exact current head, and protected-main branch protection requires both the intermediate and App-bound final contexts for that head.

A dedicated repository-installed admission GitHub App is the sole issuer of the stable `hermetic-integration-final` context in both modes, and branch protection binds that context to the App's distinct application identity rather than to the general GitHub Actions application. One trusted default-branch admission controller is the sole holder of the App credential and interprets either the merge-group event or fallback request. The App has only repository `actions:read`, `checks:write`, `contents:read`, and `pull_requests:read` permissions; its credential is held by a protected environment available only to the controller executing protected-default-branch bytes.

Before minting a short-lived App token, the controller authenticates one closed final-evidence tuple from the GitHub API: the accepted merge-group event or authorized fallback request; exact candidate commit; integration workflow ID and path; protected-default-branch workflow commit; workflow event, run ID, attempt, and check-suite identity; immutable support and capability-manifest identities; candidate digest; and all-and-only expected shard, replay, adversarial-case, and aggregate job conclusions. The final workflow definition comes from the recorded protected-default-branch commit and runs candidate code without the App credential. Artifact fields are hostile bounded inputs and are accepted only when they match the controller's event, workflow, candidate, manifest, and GitHub job observations; an artifact claim alone cannot establish a conclusion. The controller emits success only for that complete tuple. A fallback head change invalidates the request, cancels its superseded run, and leaves the new head without the App-bound final context until a new request succeeds; a changed merge group is a new candidate and likewise cannot reuse a prior context.

The final admission executes every scenario and adversarial case enumerated by the capability manifest, using one clean replay for ordinary product or adapter changes and three clean replays whenever the pull request touches workflow or selection authority, runner, isolation, cleanup, nondeterminism, release policy, release-support data, or their transitive inputs. A selected intermediate result, successful no-execution disposition, Crabbox result, prior commit result, or scheduled result cannot satisfy final admission. Every external action reachable from integration selection, preparation, execution, aggregation, cancellation, or final-context issuance is pinned to a reviewed immutable commit SHA, and repository policy verifies its all-and-only action and permission closure across pull-request, merge-group, protected-main, scheduled, and release-candidate triggers.

`.github/workflows/integration.yml` is the sole integration-matrix entry point. It runs the complete three-replay manifest on every protected `main` revision and receives one best-effort scheduled request each day from protected-default-branch workflow bytes. An independent freshness check reads the immutable run history and reports a stable failure whenever the newest successful scheduled aggregate is older than 36 hours; it runs on every final admission, protected-main revision, release-candidate attempt, and scheduled invocation, so a delayed or dropped schedule cannot be represented as fresh evidence. The release-candidate workflow governed by [NPM Publishing ADR-003](/docs/blueprints/operations/npm-publishing) calls that same entry point with the already packed immutable candidate; the aggregate binds the source revision, candidate SHA-256 and SRI, support-manifest identity, capability-manifest identity, and workflow-run identity, and the release lane accepts only that same tarball and aggregate.

Main and release-candidate runs are never canceled by a newer revision or retry. Scheduled triggers coalesce pending overlap without canceling an active run. A retry is a fresh complete run whose evidence does not rewrite an earlier failure. Main or scheduled failure retains bounded sanitized diagnostics and remains failed until a later complete run succeeds; release-candidate failure or stale scheduled evidence blocks that candidate. Successful scheduled aggregates and freshness evidence use a fixed fourteen-day retention; failure and release evidence use the bounded retention required by Matrix Operations and NPM Publishing. Superseded pull-request runs cancel in progress; cancellation publishes no evidence authority.

**Context:** GitHub-hosted CI is the independently reproducible merge and release authority, but repeating every scenario three times on every intermediate push delays iteration without adding a distinct final coverage claim. The pinned CodexBar CI precedent at commit [`af080f574b7c05a502c95064af8f36db485a355b`](https://github.com/steipete/CodexBar/tree/af080f574b7c05a502c95064af8f36db485a355b) demonstrates exact diff classification, conservative fallback, rename-boundary coverage, explicit reasons, cancellation of superseded runs, and a stable aggregate check. Agentscope adds scenario-level manifest closure and mandatory exact-head final admission because CodexBar's path gate is not compatibility or release evidence. Crabbox accelerates development but does not lend its host state, result, or authority to a CI pass.

**Consequences:** A prerequisite CI job prepares the candidate once; shard and replay jobs consume that exact checksum-bound artifact, exact support-row identity, and catalog-authenticated harness identity. Policy tests cover every path class, both rename sides, deletion, mapping incompleteness, mixed and unknown changes, missing base or head, malformed and oversized diffs, stable no-execution reporting, replay escalation, candidate-request invalidation, final-App identity and granular permission closure, every missing, duplicate, extra, stale, mixed-run, mixed-attempt, or mismatched final-evidence field, hostile artifact fields, final-admission enforcement, action closure, trigger/candidate binding, schedule freshness, retention, and cancellation grouping. The CI summary reports the authenticated candidate identity, classification reason, selected scenario identities, replay count, and, for executed rows, the harness claim, full-platform tuple, destination combination, prepared artifact identity, and scenario identity. Manual dispatch can select one exact manifest scenario for diagnosis but cannot satisfy final admission.

App installation, environment protection, and the context-plus-App branch-protection binding are repository prerequisites. Before cutover, the controller and App issue a non-required shadow result for an exact complete candidate run and repository policy verifies its application identity, permissions, protected workflow revision, aggregate, and diagnostic path. The existing required `hermetic-integration` context continues to run the complete matrix until that proof is green; only then does an administrator add the App-bound final requirement before enabling intermediate selection. App-key rotation validates a new key through the same shadow path before revoking the old key. A missing request, credential, aggregate, or App result leaves `hermetic-integration-final` absent or failed and surfaces a stable reason through the ordinary integration summary. Rollback first restores and verifies complete execution under `hermetic-integration`, then disables selection, removes the App-bound requirement, and only afterward disables the controller or App. No scenario disappears from pre-merge coverage during cutover or rollback, and a matrix change that lowers a release claim requires changing the release support manifest rather than silently weakening CI.

### ADR-003: Contain mutation with disposable outer hosts

**Decision:** Mutation-heavy preparation and scenario execution may use an ordinary Docker daemon only inside the selected disposable outer host: the exact Crabbox guest allocated for the run or the GitHub-hosted runner allocated for the CI job. The trusted outer orchestrator authenticates that disposable host before the run begins. Repository code never selects a shared workstation daemon, starts a nested private daemon, or creates a durable cross-run Docker lifecycle or recovery authority.

Inside the disposable host, one run-scoped controller prepares images and model routes and executes every consuming scenario through the same hermetic scenario environment. It passes only bounded operational inputs to Docker clients, assigns fresh exact per-run names and labels to every container, network, volume, image reference, builder, and artifact, and owns the complete client and scenario process set. A successful run proves its clients, streams, scenario processes, and exact owned resources terminal. Exact identities prevent one run from inspecting or deleting another run's resources; prefix sweeps, ambient contexts, and deletion of shared content digests are forbidden.

Any timeout, disconnect, malformed response, incomplete join, contradictory inventory, or otherwise uncertain mutation fails the run. It cannot be converted to cleanup success by polling or resource absence. The outer host then becomes non-reusable: Crabbox execution requires the coordinator to destroy that exact guest, and CI execution relies on teardown of that exact GitHub-hosted runner. Outer-host destruction contains uncertain late mutation; it does not retroactively prove the inner operation succeeded or cleaned up.

**Context:** A client exit cannot prove that daemon-side mutation stopped. A disposable outer host supplies a causal terminal boundary without maintaining a workstation VM, custom daemon substrate, or recovery ledger across runs.

**Consequences:** Normal success remains strict and self-proving. Uncertain runs retain bounded failure evidence until their outer host is retired, but no repository process reopens, recovers, or reuses that host or its Docker state. Crabbox and CI may implement different allocation and destruction mechanisms; both must preserve the same inner runner contract and their own independently authenticated terminal outer boundary.
