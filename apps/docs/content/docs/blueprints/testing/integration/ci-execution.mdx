## Capability Summary

The same manifest drives a small selected local scenario and the complete hermetic CI matrix without leaving dependencies, containers, or mock routing on a developer workstation.

## Architecture Decision Records

### ADR-001: Make local execution targeted and safe by default

**Decision:** Local commands select an explicit scenario, harness, tag, deterministic shard, or deliberate full run and execute it in Docker. They print exact named containers, networks, images, and fixed-root artifact paths before cleanup; `pnpm test:integration:clean` removes only validated owned targets.

**Context:** Developers may use AgentScope and coding harnesses outside this repository. A test command must not alter their real configuration or make their active agents talk to MockServer.

**Consequences:** The suite never mounts the user's home or injects model endpoint variables into the host shell. Repeated local runs reuse only named, bounded prepared inputs; scenario and sidecar resources have explicit memory, process, request, concurrency, and time ceilings. Resource names and labels bind the canonical physical Docker daemon-incarnation identity from ADR-003, repository identity, workspace identity, and fresh run nonce. Run registration, daemon lifecycle, daemon-incarnation selection, and repository-owned artifact mutation use one host-local OS socket lease derived from host-boot plus repository identity, so separate worktrees or daemon incarnations cannot hold conflicting cleanup or handoff authority. Before creating any disposable-daemon endpoint, storage, containment authority, or process, the canonical registry durably reserves a fresh non-reusable daemon-lifecycle claim binding their deterministic exact identities and its own recovery generation. Its closed bootstrap states are `reserved`, `storage-created`, `endpoint-created`, `daemon-started`, `request-capable`, `selected`, `bootstrap-retired-failure`, and `closed`. Before `request-capable`, recovery revokes the endpoint, terminates and joins the exact process authority, proves no endpoint capability ever admitted a request, removes the complete exact disposable bootstrap root including daemon initialization metadata, and terminally closes the claim. At or after `request-capable`, the lifecycle claim—not a nonexistent run claim—advances its exclusive recovery generation, freezes bootstrap admission, revokes the non-aliasable endpoint, terminates and joins the daemon process set, irreversibly quarantines its storage, writes a permanent incarnation tombstone, and ends `bootstrap-retired-failure`. Selection of the fully attested incarnation atomically transfers that recovery authority into the canonical incarnation record and closes the lifecycle claim; only after that handoff can a run claim exist and ADR-003 retirement apply. The canonical repository registry then records the selected daemon incarnation. Each run holds a fresh-nonce claim in that registry bound to the same daemon, repository, and workspace identities plus either a non-reusable operating-system process handle or the authenticated tuple of host boot identity, process identifier, and process start identity; PID-only liveness is never authority. Under the socket lease, a later controller double-checks the exact claim and may advance it to a new exclusive fenced recovery generation only after the bound operating-system identity proves that exact owner no longer exists. Live or indeterminate identity blocks reclamation; every admitted crash prefix therefore resumes the exact live generation, advances a proved-dead generation for exact reconciliation, or fails closed. A proved stale claim authorizes reconciliation only of the exact run identities recorded by that generation, and generation revalidation precedes each mutation. Cleanup removes only exact repository/run-specific containers, networks, volumes, tags, references, archives, contexts, and evidence; it never deletes a shared content digest from the Docker or BuildKit store, whose garbage collection remains daemon-owned. The kernel releases exclusion when its owner exits, so interruption cannot leave a stale pathname lock. Cleanup is inspectable, accepts only exact bound labels and identities, and never follows symlinked roots or recursively accepts an arbitrary path.

### ADR-002: Gate pull requests with the defined hermetic matrix

**Decision:** Pull requests run unconditional, separately sharded scenarios for all and only the finite exact support rows claimed by the applicable release support manifest. Each shard binds the exact support-row identity, clean-installs the same packed CLI candidate, invokes the catalog-pinned actual binary, uses only internal model mocks and the loopback OTLP ledger, denies public egress, and proves cleanup. No path, relevance classifier, or deduplication by version/mode may omit or combine claimed rows. Scheduled/manual CI may run broader advisory coverage, but it never changes the required pinned set or contacts a model provider, Langfuse, or another public destination service.

**Context:** The fast required matrix detects cross-harness regressions without making every PR wait for every historical version. Hermetic execution keeps evidence deterministic and avoids exposing provider credentials or test data to an external service.

**Consequences:** A prerequisite job prepares the candidate once; shard and replay jobs consume that exact checksum-bound artifact, exact support-row identity, and catalog-authenticated harness identity. Manual dispatch can select one exact manifest scenario. The CI summary reports the exact support-row identity, including its harness claim, full-platform tuple, and destination combination, plus the backend-appropriate prepared artifact identity and scenario identity. A matrix change that lowers a release claim requires changing the release support manifest rather than silently weakening CI.

### ADR-003: Fence uncertain daemon mutation across controller exit

**Decision:** The trusted outer controller is the sole attestation owner for one canonical Docker daemon-incarnation identity covering the exact endpoint process lifetime, backend daemon lifetime, storage root, and lifecycle authority. A backend admitted for a mutation that may outlive an unsettled client must be a controller-owned disposable daemon with an exclusive non-shared storage root and an exclusive, non-aliasable endpoint capability; admission proves that the controller can stop and join the whole daemon process set and make that storage permanently unavailable. A shared developer daemon, shared storage root, or merely identity-attestable backend is unsupported for these mutations. Before mutation, the controller uses the ADR-001 lease to durably add one operation record inside the run's existing canonical registry claim. There is no second claim, ledger, or recovery-generation authority. The registry freezes new claims for an incarnation during retirement and enumerates every claim and process-set authority bound to it. Each run serializes operations and has at most one unresolved operation. The enclosing run-claim generation is the sole mutation authority and is revalidated for every transition and reconciliation step; the nested operation revision is only compare-and-swap identity.

The immutable operation plan binds the daemon incarnation, repository, workspace, run, exact executable and operation, family-owned settlement class, and an all-and-only terminal inventory projection. It classifies every exact builder, tag or reference, container, network, volume, context, local archive, and evidence identity as temporary or success-retained; it never includes shared Docker or BuildKit content digests. On authenticated success, a host-local retained output moves in one atomic registry transition from the operation into the enclosing run's generation-fenced retained-resource set. Before a consumer can discover, open, or launch against that output, its run generation is atomically registered in that set. Registration transfers atomically when a dead consumer advances generation, and removal is permitted only after that consumer's processes, streams, and handles terminally join. Cleanup takes the lease, proves the set empty, and revalidates the producer generation and exact identity immediately before deletion. There is no separate consumer lease. Without successful transfer, every operation-created resource is terminal only when absent, apart from the bounded failure record. Cross-host CI artifacts are not members of this host-local set and use the checksum-bound handoff authority in ADR-002.

Launch uses a durable rendezvous. The controller derives a fresh non-reusable containment/process-set authority identity from the operation generation and nonce and durably writes `reserved` before creating it. Creation is exclusive and idempotently inspectable by that exact identity; the authority exists independently of any child PID and can prove emptiness and terminally join every member. Recovery of `reserved` handles both closed outcomes: exact authority absent, or exact authority created. It closes any channel, proves the recorded authority empty, and removes it before clearing; it never assumes no spawn. After creation the controller durably records `contained`, then spawns the exact trusted launch gate inside it without daemon authority or the request. Recovery of `contained` never spawns or resumes: it revokes and closes the rendezvous, terminates and terminally joins every member of the exact authority whether empty or populated, proves emptiness, removes the authority, and returns the operation to its definite-noncommit terminal disposition. The gate publishes its authenticated process-start identity through the rendezvous and the controller durably advances to `armed`; an `armed` gate whose channel closes exits without mutation. The controller durably records `releasing` before it can send the one-use daemon authority and exact request; `releasing` is conservatively mutation-possible whether transmission occurred or not. An authenticated gate acknowledgement advances to `released`; observation or loss advances to `observed` or `uncertain`. The remaining closed states are `reconciling`, `reconciled`, and `retired-failure`. Every transition uses private no-follow state, atomic replacement, and directory durability. Clearing `reconciled` returns only the enclosing run claim to active state; only ADR-001's complete run cleanup may clear that claim.

Settlement mappings are closed here. A BuildKit preparation succeeds only when the exact gated buildx client returns authenticated success, its process and streams join, its isolated builder is terminal, every import or publication step is complete, and the prepared identity matches; after any client uncertainty it has no same-incarnation settlement shortcut and requires daemon-incarnation retirement. Docker evidence-volume creation is the sole exception to the generic volume-create mapping: authenticated appearance of its one exact generation-labelled volume proves that single-output call can perform no later mutation, after which exact removal settles failure cleanup. All other required image load/import and container, network, volume, and reference create, start, stop, kill, and remove operations settle only after the exact authenticated daemon response is complete, the request client and streams have joined, and an independent exact postcondition inventory agrees with that response. A timeout, disconnect, malformed response, failed join, or contradictory inventory has no absence-based shortcut and requires daemon-incarnation retirement. Every other operation kind is unsupported until an earlier Blueprint adds its causal terminal mapping. Passive tags, references, archives, or partial build outputs never witness settlement.

A later controller enters `reconciling` only under the socket lease, after advancing the enclosing run claim to one exclusive recovery generation and independently proving the owner and operation process set dead. It revalidates that run generation, operation revision, and daemon incarnation before every exact mutation. It records `reconciled` only after the operation witness is terminal and the immutable inventory projection is satisfied. If no witness can be proved, retirement first freezes admission for the incarnation and proves every bound run owner, launch authority, request client, stream, and handle terminal; any live or indeterminate claim blocks retirement. The old endpoint capability is revoked without reuse, the endpoint and daemon process sets are terminal, and the exclusive storage authority is made irreversibly offline and non-reusable. Under the same registry lease, one atomic tombstone transition assigns terminal failed/quarantined disposition to every claim, nested operation, and retained-resource relationship bound to that incarnation, then closes the triggering recovery generation. Only afterward may the controller select a distinct non-aliasable endpoint, authenticated daemon incarnation, and clean storage root for a fresh run claim. `retired-failure` is failure evidence, never cleanup success; old resources may remain only inside the permanently quarantined storage and every prior retained-resource relationship records that it is inaccessible rather than cleaned. The tombstone is the continuing fence, and selecting or reconnecting to its endpoint, incarnation, or storage root is always rejected.

Malformed, oversized, substituted, symlinked, or otherwise unauthentic nested operation authority is quarantined without interpreting its resource identities. If the enclosing run claim remains authentic, only the known bound daemon-incarnation retirement and permanent-tombstone path above can return mutation authority. An unauthentic daemon-lifecycle claim is outer-registry corruption: no endpoint, process, or storage identity from it authorizes in-place cleanup. Only independently authenticated outer identities may be terminally fenced; otherwise the registry and old host remain quarantined and work resumes only on a fresh disposable host with a distinct authenticated host boot, daemon incarnation, and empty storage root. The same fresh-host rule applies if the enclosing run claim or selected daemon identity is unauthentic; no in-place replacement is allowed. Corrupt-authority failure evidence binds only independently trusted outer identity and quarantined inode identity and digest; original lifecycle, operation, and daemon fields are explicitly unknown. Ordinary uncertainty instead binds its authenticated run or lifecycle recovery generation, operation revision when present, daemon incarnation, and closed disposition. Neither is prepared-input, successful-cleanup, cache-adoption, or scenario-pass evidence.

**Context:** A client timeout or closed local socket does not prove that daemon-side creation or publication stopped. An in-memory marker disappears with the controller and can permit a later run to race a surviving mutator or delayed resource publication.

**Consequences:** This is one testing-infrastructure recovery authority shared by uncertain preparation builds and Docker evidence-volume creation; those capabilities do not define parallel ledgers or clearing rules. Prefix sweeps, elapsed polling, tag or name absence alone, controller-exit cleanup, and deletion of shared daemon content cannot establish terminal state. The claim stores identities and closed state only, never credentials, commands containing secrets, artifact contents, or scenario evidence.
