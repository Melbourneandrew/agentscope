## Capability Summary

The integration matrix needs authenticated immutable harness inputs, a declared compatibility surface, safe local selection, and scalable CI execution as supported harnesses grow.

## Architecture Decision Records

### ADR-001: Declare compatibility as data

**Decision:** `tests/integration` owns the authoritative versioned catalog of tested harness representatives and consumes the exact-identity coverage policy from [Harness Abstraction](/docs/blueprints/foundations/harness-abstraction) and the support-row schema from [CLI Installation ADR-003](/docs/blueprints/operations/cli-installation). Each release-claim entry binds the exact support-row identity plus its official distribution reference, independently authenticated package or binary integrity, checksum-bound preparation recipe, required model protocol routes, scenario tags, checksum-bound scenario adapter, and evidence identity; an advisory entry uses the same closed identity shape without acquiring release authority. Each container preparation materializes an immutable per-run input record with one canonical prepared-image identity: the normalized OCI platform tuple plus the digest of the selected OCI image-manifest descriptor. If preparation produces an index, it resolves and records the one matching platform manifest. If Docker runs a locally loaded image, preparation also records the manifest's config descriptor and verifies that the created container uses that exact config digest; an image ID, tag, index digest, or bare layer digest cannot substitute. The harness descriptor remains the sole owner of eligible runtime compatibility ranges and its closed mode/output identities, and the release support manifest remains the sole owner of a release's published support claim.

**Context:** A prose list of harnesses cannot drive CI selection, image pinning, failure reports, or deliberate retirement.

**Consequences:** One passing representative certifies only its exact support-row identity; neither an interior point nor a boundary point extrapolates support across a range. Every finite release-manifest support row has exactly one matching catalog scenario and evidence record, and separately listed claims never imply a cross-product. Descriptor ranges express eligibility, not evidence or a release claim. Generic orchestration loads the selected manifest adapter rather than branching on harness or destination identity. Introducing a harness or changing its intended runtime compatibility range or mode set changes the descriptor and the affected exact catalog/evidence identities. Missing, extra, duplicate, or mismatched claim evidence yields an explicit unverified state rather than a second compatibility policy.

### ADR-002: Build immutable test inputs before isolating scenarios

**Decision:** Before scenario isolation, each trusted executor packs the self-contained candidate CLI tarball and prepares the harness from the exact documented vendor package or installer selected by its approved harness Blueprint. Preparation authenticates the input against independently obtained registry integrity, signature, transparency, or equivalent version-bound metadata. A container backend builds or installs it into an ephemeral local Docker image or OCI image layout, records the canonical prepared-image identity from ADR-001, and starts only the locally loaded image whose config digest is bound to that identity, with `--pull=false` and denied public egress. A native full-platform backend instead installs the same authenticated exact vendor artifact on its disposable native runner and records the runner, vendor artifact, installed binary, and outer-containment identities required by [Harness Execution ADR-006](/docs/blueprints/testing/harness-execution); it does not fabricate an OCI identity.

The trusted preparation controller creates one absolute monotonic deadline before the first acquisition, build, install, or inspection subprocess and reserves its final bounded subwindow for process-set termination, join, and temporary-state cleanup. Every preparation subprocess uses an exact absolute executable identity, authenticated process-set and intended backend authority, bounded output, an explicit environment allowlist, and disposable empty Docker, package-manager, and Git client configuration. Container preparation authenticates the intended physical Docker daemon and cannot inherit daemon, context, TLS, proxy, helper, credential-store, or developer configuration. Before starting a build or creation operation whose daemon mutation may outlive an unsettled client, preparation durably registers the exact operation and complete run-owned resource identities through [Local and CI Execution ADR-003](/docs/blueprints/testing/integration/ci-execution). Timeout, interruption, overflow, failed join, or uncertain cleanup retains that fence and publishes no prepared-input or cache-adoption evidence. A separately approved private source must name one narrow acquisition credential authority explicitly; it remains outside builders, candidates, scenarios, caches, commands, and retained evidence.

No persistent registry mirror is required by default. If an executor must transfer an image without publishing it, it uses a self-contained authenticated, unpublished OCI image-layout archive rather than a bare layer. Ordinary package-manager, Docker/BuildKit, and GitHub Actions caches are non-authoritative optimizations: every reuse is revalidated against the catalog identity and digest. A persistent GHCR mirror requires a later approved decision justified by availability, licensing, or measured performance. Public vendor packages use anonymous acquisition when their official distribution permits it; the default path introduces no npm credential or new GitHub secret.

**Context:** This is test-installation infrastructure, not an AgentScope delivery queue. Hermetic scenarios need a reproducible fresh install while still denying runtime public-network access.

**Consequences:** Local, GitHub, and Crabbox preparation consume the same authenticated catalog input. Container backends may independently produce an ephemeral image; native backends independently produce the exact installed-artifact/binary identity on their disposable runner. Per-harness official-source research decides the actual package or installer, authentication authority, licensing and cache permissions; it must not assume every harness uses npm. Repository-owned image references and authenticated OCI archives are retained only for their bounded container run or CI artifact-retention window, then removed by exact owned identity after the canonical Local and CI Execution registry proves its generation-fenced retained-resource consumer set empty. Shared Docker and BuildKit content is never deleted by Agentscope; daemon-owned garbage collection reclaims unreferenced content. A future private GHCR optimization uses the built-in GitHub Actions `GITHUB_TOKEN` with minimal package permissions rather than a separately provisioned credential.

### ADR-003: Use shared container bases and isolated sharded scenarios

**Decision:** Container-backend harness images share pinned base layers where practical, but every container scenario still runs in its own disposable container. Native-backend scenarios retain the disposable native runner and containment variant from ADR-002 and Harness Execution ADR-006. CI partitions manifest entries into deterministic shards by estimated duration, platform, backend, and resource class; a local command selects one harness, tag, or shard by default.

**Context:** One all-harness image couples unrelated release cycles and wastes cache space, while one sequential job makes feedback too slow. Sharing a container would compromise isolation.

**Consequences:** A failed shard can replay one manifest entry with the same backend-appropriate prepared identity and artifacts; manual CI accepts either that exact scenario identity or a deterministic shard selector. The matrix must not depend on test execution order or a shared mutable home.

### ADR-004: Retain only sanitized failure evidence

**Decision:** Failed scenarios upload bounded, sanitized lifecycle evidence and any model or destination ledgers produced before failure, plus the manifest and backend-appropriate prepared-input identity record. Harness adapters may add bounded sanitized harness logs and AgentScope diagnostics. Successful scenarios retain only the reviewed compatibility evidence required by the local certification workflow.

**Context:** The artifacts are needed to investigate harness drift but can contain prompts, paths, or request metadata.

**Consequences:** The fixture emits bounded sanitized checkpoints as model and destination work completes, so an authentic sidecar or harness failure retains the latest partial ledgers rather than only a terminal status. Artifact redaction runs before upload, has an explicit retention period, and is covered by unit tests. Raw transcripts, credentials, and complete production trace payloads are never CI artifacts.

### ADR-005: Separate deterministic pins from bounded drift sensing and adoption

**Decision:** Required compatibility uses only catalog-pinned authenticated inputs. A non-blocking drift sensor may resolve a newer official candidate during trusted preparation, authenticate and digest it, and run the ordinary isolated scenario without changing accepted pins.

One repository-owned GitHub Actions workflow from the protected default branch is the drift-state writer. Scheduled and manual entries share one global Actions concurrency group so only one writer runs and excess pending events coalesce. A fixed trusted controller uses the built-in `GITHUB_TOKEN` with minimal issue, pull-request, and adoption-branch permissions; the token never enters checkout-controlled code, acquisition builders, scenario inputs, commands, environment, caches, or evidence. No external state service or new secret is introduced.

A locked content-free control issue is the durable authority for the current per-harness candidate, stable failure fingerprint, supersession, bounded-retention cursor, and global notification-window reservations. Every visible side effect receives a deterministic operation identity and a durable `reserved`, `observed`, or `terminal` state. Stable hidden markers carry that identity in at most one incident or adoption pull request per harness.

The writer reserves budget and the operation identity before a side effect. After success, failure, timeout, or an unknown GitHub response, recovery searches the exact marker and reconciles the result before completing or retrying the same operation. If commit remains unprovable, the reservation quarantines that harness until an operator either binds the discovered work item or records terminal `abandoned-unknown`; that terminal consumes the budget and is never retried, accepting one dropped side effect to preserve at-most-once notification. Adoption refs use a deterministic name and compare-and-swap against the recorded expected base; an unexpected or externally changed ref fails closed for review rather than being overwritten. Excess runs coalesce, and excess or alternating outcomes update the control record without another message. For one candidate, only its first terminal result and a later recovery may notify.

A passing new candidate already inside the harness descriptor's approved compatibility range and mode/output set may open an adoption pull request that atomically changes a non-release-claim catalog representative, authenticated input identity, preparation recipe when necessary, and version-bound sanitized fixture identity. It cannot remove or replace an exact row required by the current release support manifest. Its verification records the backend-appropriate prepared-input identity as run evidence. A candidate outside that range or mode/output set creates or updates the single deduplicated research/decision incident and cannot open an adoption pull request. Automation cannot learn or rewrite semantic expected values from candidate output, cannot modify the harness descriptor or release support manifest, and cannot merge the adoption.

**Context:** A moving version as a required check makes unrelated pull requests depend on upstream publication. An unbounded schedule that repeats the same failure recreates noise without improving compatibility evidence.

**Consequences:** Drift sensing is advisory and cannot replace or invalidate the accepted pin. Schedule cadence, notification destination, and whether sensors are enabled are operator choices recorded outside the Blueprint; the bounded state-transition and deduplication rules apply whenever a sensor runs.
