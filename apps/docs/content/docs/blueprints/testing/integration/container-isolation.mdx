## Capability Summary

Every default real-harness scenario proves that AgentScope can install and capture from a clean machine-like environment without affecting a developer's real workstation configuration.

## Architecture Decision Records

### ADR-001: Use one disposable isolation boundary per support-row scenario

**Decision:** Each scenario selects one closed isolation backend. A container row receives a fresh container and private process/network namespaces. A native row receives a disposable native runner plus the approved process-set and network-containment authority for its full-platform tuple. The native controller and candidate execute under separate operating-system principals with restrictive ACLs, or an equivalently proven native sandbox. The candidate receives one manifest-bound capability set: its disposable scenario root, bounded mock endpoints, exact installed CLI and harness, runtime and system dependencies declared by the full-platform row, and the exact native credential backend named by that row restricted to isolated synthetic test entries and namespace for the candidate principal. A fake or alternate backend is valid only when that exact backend is the row's declared backend; no user credential collection or unrelated entry is accessible. The candidate can never access the controller checkout, mock or ledger process/storage, retained-evidence root, process-control authority, cleanup credentials, unrelated operating-system state, or another run. Both variants receive an empty user home, harness-specific home, `AGENTSCOPE_HOME`, Git worktree, and telemetry ledger. The authoritative harness Blueprint owns a closed model-auth-input choice for that exact mode: either no auth input or one fixed non-authoritative synthetic sentinel proven necessary for native parsing. A model-provider credential is never an allowed choice, and any sentinel is sent only to the internal mock.

For a Linux container row, the kernel supervisor is PID 1 in the private scenario PID namespace, uses non-reusable kernel handles or PID plus authenticated `/proc` start identity for launched work, and enumerates that namespace to classify residual descendants. The candidate cannot access a Docker socket or container-runtime credential. Before isolation-backend or runtime work, the trusted outer controller creates one hard absolute monotonic deadline and reserves a bounded final subwindow for shutdown and reconciliation. It gives the execution kernel an earlier cutoff and independently races the bounded result and result-channel settlement against that cutoff; inner or configured deadlines may shorten but never extend the outer authority. On a missing, late, malformed, or uncertain result, or after a normal result, it preserves any scenario failure, records the available residual classification, and uses the reserved subwindow to terminate and join the exact backend process set and reconcile every run-owned resource. For a container this means stop or kill the exact container and wait for the runtime to report it exited. Every runtime, process, and result-channel operation is individually deadline-bound and joined. An operation that does not settle leaves failed, uncertain cleanup evidence and a fenced run for later exact-identity reconciliation rather than hanging the controller or reporting a pass. A leak or uncertain inner classification remains a failed scenario even when outer destruction succeeds. A native backend needs equivalent independent deadlines, complete-process termination, join, and reconciliation evidence or cannot support a cleanup claim.

**Context:** Sharing homes, hooks, request records, or worktrees produces order-dependent tests and risks serving mock responses to a developer's real harness.

**Consequences:** Scenarios cannot mount a host home, credential store, active harness configuration, or writable project worktree. A host-binary mode may exist only as an explicit diagnostic command and is never the default local or CI suite.

### ADR-002: Prove the installation artifact, not the checkout

**Decision:** Every scenario receives the packed candidate `agentscope-cli` artifact as a checksum-bound immutable input. A real-harness acceptance scenario must install that artifact and execute `agentscope init` plus `agentscope install <harness>` before invoking the harness. The pre-harness destination checkpoint executes only the ordinary bin's initialization, destination configuration, Doctor, and Local lifecycle commands and cannot supply captured or branded trace input. That checkpoint counts only as release-artifact and destination-composition evidence. A platform-certification fixture may exercise only an explicitly identified test lifecycle adapter and does not count as real-harness or product acceptance evidence.

**Context:** Mounting the source checkout or relying on a global CLI can hide missing package files, bin metadata, and install-time assumptions.

**Consequences:** Candidate packaging is a prerequisite of every scenario. Neither certification mode may import a workspace package, replace a production destination, or place test-only material in the candidate. The generic platform and exact packed destination composition can be certified without inventing a vendor support claim; each advertised harness still requires a scenario that invokes the ordinary bin and asserts real owned-hook installation and uninstall behavior in the same isolated environment.
