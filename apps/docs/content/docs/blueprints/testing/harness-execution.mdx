## Capability Summary

This Blueprint owns the shared harness-process supervisor, semantic PTY behavior, acceptance-oracle separation, installed-CLI contract, per-harness architecture boundary, and cross-executor evidence contract. It composes isolation, mock networking, artifact lifecycle, matrix selection, and CI decisions from their authoritative testing leaves rather than redefining them.

## Architecture Decision Records

### ADR-001: Put one bounded execution kernel beneath pipe and PTY transports

**Decision:** `packages/testkit` owns one execution kernel used by non-interactive pipe and PTY transports. A run supplies an executable, exact arguments, working directory, explicit environment allowlist, input, output ceilings, absolute monotonic startup, execution, and shutdown deadlines, and one authenticated process-set observer from the selected isolation backend. The kernel bounds and concurrently drains output, propagates cancellation, joins the launched process and every input/output handle, and consumes that observer to classify residual descendants. A container run's observer enumerates the private scenario PID namespace; a native run's observer comes from its approved outer containment backend and supplies equivalent authenticated process-set identity, termination, and join authority without fabricating a PID namespace. The kernel attempts bounded cooperative termination and escalation, but any escaped descendant, incomplete drain, deadline race, open handle, or uncertain cleanup fails the scenario. Final containment evidence comes from the trusted outer lifecycle in [Container Isolation](/docs/blueprints/testing/integration/container-isolation), not from an inner privilege.

Process-set identity and containment come from the backend variant in [Container Isolation](/docs/blueprints/testing/integration/container-isolation); the kernel consumes that boundary without establishing a second process-ownership authority.

**Context:** The current helper inherits ambient environment, accumulates unbounded strings, sends one termination signal, and settles without proving descendant or handle cleanup. Process groups alone miss a child that creates a new session; PID-only tracking can target a reused identifier; returning before output and PTY handles settle can leave a hung test process.

**Consequences:** Adapters select a transport and describe native observations but cannot weaken deadlines, bounds, or cleanup. Raw process output remains ephemeral inside the disposable scenario. Acceptance settles only after the outer controller joins the selected backend's complete process set and reconciles its exact owned resources; outer containment cannot turn an inner leak classification into a pass.

### ADR-002: Drive documented interactive modes through a semantic PTY contract

**Decision:** The PTY transport controls terminal geometry, resize, input, EOF, interrupt bytes, and signals, and derives readiness and completion from a bounded terminal emulator. Tests assert semantic states and lifecycle facts rather than byte-for-byte ANSI output. PTY evidence applies only to the exact harness version and documented interactive mode exercised; it cannot substitute for a headless claim.

**Context:** TTY presence changes harness behavior, while terminal output can be fragmented or contain alternate-screen, cursor-query, progress, and malformed control sequences.

**Consequences:** Login or credential prompts fail the scenario. A release support manifest may claim an execution mode only when that mode has its own passing evidence.

### ADR-003: Keep acceptance oracles outside scenario adapters

**Decision:** Test families own fixed stimuli, correlation rules, pass criteria, and deliberately nonconforming fixtures. Scenario adapters may translate native paths and event shapes but may not supply expected success values or discard contradictory native records.

Real-harness acceptance independently correlates the actual harness process and cleanup result, internal model-mock ledger, hook invocations and native observations, loopback OTLP ledger and optional Local SQLite state, installed configuration, filesystem mutations, and owned-state cleanup. Retained evidence contains only reviewed bounded identities, digests, structural counts, categorical outcomes, and content-free diagnostics. Raw transcripts, prompts, terminal output, native record bodies, credentials, and complete trace payloads never leave the scenario.

**Context:** A synthetic adapter that creates both representative data and its expected outcome proves substrate plumbing, not product compatibility.

**Consequences:** Fake executables certify execution components only. Deliberate negatives with missing, duplicate, reordered, or cross-session native records must fail even when normalized output looks plausible.

### ADR-004: Test every public CLI contract from the exact packed artifact

**Decision:** A clean-installed contract suite packs the exact release candidate, installs it into an ordinary isolated user prefix, and invokes the installed `agentscope` executable. It covers every public command and command level in human and structured modes, including help/version, stream separation, stable outcomes, hostile arguments, confirmations and non-TTY EOF, idempotency and conflicts, Unicode and spaces, narrow terminals and broken pipes, signals and deadlines, and absence of mutation from read-only or rejected operations.

**Context:** Workspace tests and a root-command smoke test cannot prove what users install.

**Consequences:** The packed tarball is the product composition root for acceptance. Repository-source shortcuts, global developer installs, and fabricated installation markers are not acceptance evidence.

### ADR-005: Keep harness-native decisions in one Blueprint per harness

**Decision:** Each harness has one authoritative integration Blueprint. That Blueprint decides the documented binary source and license or redistribution constraints, supported headless and interactive interfaces, exact internal mock-server and model routing, updater/telemetry/authentication-fallback suppression, root hook installation and capture lifecycle, native observations and oracles, and the zero-real-token/no-provider-credential behavior for the harness. Unknown or unproven behavior remains an explicit admission blocker rather than an inferred decision.

**Context:** Distribution, routing, hooks, updater controls, and native evidence differ by vendor and version. A generic harness descriptor cannot truthfully own those integration-specific decisions.

**Consequences:** The shared matrix composes each approved harness Blueprint without copying its native decisions. Generic testing records cannot make or override a harness-native decision.

### ADR-006: Authenticate real trust-boundary crossings, not ordinary composition

**Decision:** Strong artifact authentication and durable terminal evidence are required only where data or authority crosses an actual external, native, provider, process, persistence, or destructive-cleanup boundary. Within the trusted controller process, modules compose through immutable typed values and direct calls. They must not copy exact-field schemas, serialize and digest values, or mint parallel runtime brands merely because the call crosses a module; any stronger internal mechanism must name a distinct caller-mutation, persistence, privilege, or ambiguity risk that an immutable owned value does not close.

| Boundary                                                                                            | Required assurance                                                                                                                                     | Governing need                                                                 |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| Registry, vendor, packed CLI, OCI, native binary, or cross-job artifact                             | Authenticate the exact immutable bytes and provenance once at ingress; recheck after an external transfer.                                             | `AC-INS-003.1`, `AC-INS-003.2`, `AC-PLAT-001.1`                                |
| Harness, PTY, child process, native runner, or provider/mock interaction                            | The sole execution kernel records bounded terminal process/handle state; the product scenario observes provider and destination effects independently. | `AC-CAP-001.1`, `AC-CAP-001.2`, `AC-REP-003.2`, `AC-PLAT-001.3`                |
| Hook, filesystem, container, credential entry, or guest cleanup that can destroy or overwrite state | Bind the exact owned target and retain terminal reconciliation before claiming success.                                                                | `AC-HAR-001.2`, `AC-INIT-002.2`, `AC-INS-002.1`                                |
| Same-process controller, scenario, adapter, oracle, and evidence composition                        | Use one validated immutable typed snapshot and read-only projections; no duplicate schema, digest, receipt, or authority wrapper.                      | No separate trust transition; oracle independence remains governed by ADR-003. |

GitHub CI and Crabbox use the same hermetic product-scenario entry point and evidence envelope. That envelope binds the exact source commit, candidate digest, manifest and catalog row, executor and backend, harness artifact, runtime and platform, resource and time ceilings, independent observation outcomes, containment disposition, and terminal owned-resource inventory. A container result additionally binds its prepared OCI and container identities and their cleanup; a native result instead binds its runner, installed artifacts, process set, and native-resource cleanup. Release evidence must match the exact release-support row; an advisory row has no release authority, and a missing or inapplicable backend field cannot be fabricated.

GitHub CI alone supplies merge or release authority. Crabbox remains a disposable development host: fleet credentials stay outside repository and candidate processes, and its exact guest destruction is an external cleanup boundary rather than proof that an inner failure passed.

**Context:** Exact bytes, processes, provider effects, and destructive cleanup can change outside the controller's type system. Re-authenticating each same-process handoff catches no additional failure class and has produced parallel schemas and amendment surfaces.

**Consequences:** Validate hostile or persisted data once when it enters the trusted process, preserve one immutable typed snapshot, and authenticate it again only after another real boundary crossing. The controller retains the authoritative cleanup and evidence identities for the snapshot's lifetime; stages receive read-only projections, and scenario adapters and independent oracles may compare typed observations directly. Missing or uncertain external identity, process settlement, provider observation, or destructive cleanup still fails closed.

### ADR-007: Use CodexBar as the prior art for PTY and CLI-process behavior

**Decision:** AgentScope keeps one execution kernel and one PTY transport. Before adding or changing PTY creation, terminal interaction, prompt driving, output bounds, absolute deadlines, post-exit draining, cancellation, or child cleanup, contributors must first compare the proposed behavior with the audited CodexBar snapshot at commit [`af080f574b7c05a502c95064af8f36db485a355b`](https://github.com/steipete/CodexBar/tree/af080f574b7c05a502c95064af8f36db485a355b). The primary examples are CodexBar's [`TTYCommandRunner`](https://github.com/steipete/CodexBar/blob/af080f574b7c05a502c95064af8f36db485a355b/Sources/CodexBarCore/Host/PTY/TTYCommandRunner.swift), persistent [`CodexCLISession`](https://github.com/steipete/CodexBar/blob/af080f574b7c05a502c95064af8f36db485a355b/Sources/CodexBarCore/Providers/Codex/CodexCLISession.swift) and [`ClaudeCLISession`](https://github.com/steipete/CodexBar/blob/af080f574b7c05a502c95064af8f36db485a355b/Sources/CodexBarCore/Providers/Claude/ClaudeCLISession.swift), live [`CodexStatusProbe`](https://github.com/steipete/CodexBar/blob/af080f574b7c05a502c95064af8f36db485a355b/Sources/CodexBarCore/Providers/Codex/CodexStatusProbe.swift) and [`ClaudeStatusProbe`](https://github.com/steipete/CodexBar/blob/af080f574b7c05a502c95064af8f36db485a355b/Sources/CodexBarCore/Providers/Claude/ClaudeStatusProbe.swift), and the corresponding [`TTYCommandRunnerTests`](https://github.com/steipete/CodexBar/blob/af080f574b7c05a502c95064af8f36db485a355b/Tests/CodexBarTests/TTYCommandRunnerTests.swift) and [`TTYIntegrationTests`](https://github.com/steipete/CodexBar/blob/af080f574b7c05a502c95064af8f36db485a355b/Tests/CodexBarTests/TTYIntegrationTests.swift). Matching problems use that precedent and its test cases instead of introducing a parallel runner, supervisor, PTY implementation, or scenario-specific lifecycle mechanism.

**Context:** CodexBar already drives real Codex and Claude CLI behavior through PTYs and has production experience with `openpty`, terminal geometry, bounded output, deadline classification, late-output draining, process-group and descendant cleanup, shutdown races, and fake-CLI and live integration tests. Re-solving those same problems in AgentScope has produced unnecessary bespoke infrastructure and review churn.

**Consequences:** A change that follows the CodexBar precedent records the matching source or test seam in its review evidence. A divergence must identify a concrete AgentScope requirement that CodexBar does not address and must extend the sole shared execution kernel rather than create another mechanism. AgentScope-specific hermetic installation, authenticated artifact preparation, denied public egress, hook and trace correlation, destination ledgers, and support admission remain AgentScope responsibilities; they compose around the shared kernel and do not justify duplicating its PTY or process lifecycle. The pinned snapshot is design evidence, not a runtime dependency or automatically moving authority; adopting a later upstream behavior requires an ordinary reviewed Blueprint update.

### ADR-008: Keep integration in three one-way layers

**Decision:** Integration has exactly three architectural layers, with dependencies flowing from scheduling to product scenarios to the execution kernel:

1. `packages/testkit` owns the sole CodexBar-aligned PTY/process execution kernel and transports. It owns spawn, bounded I/O, terminal semantics, its earlier child/handle cutoff, cooperative termination, process-set observation, and transport settlement, but no harness, destination, or release oracle.
2. `tests/integration` owns one admitted controller and the hermetic Agentscope product-scenario layer. Its control-plane seam creates the hard run deadline and reserved containment window, validates the immutable run context, prepares external artifacts, supplies the selected isolation backend and process-set observer, propagates an earlier cutoff into the kernel, persists boundary evidence, joins the backend, and reconciles owned resources. Its scenario-facing seam owns the catalog, test-only scenario adapters, independent product oracles, orchestration, and assertions over exact packed installation, hooks installed by the packed product, denied public egress, native observations, trace/destination correlation, and cleanup; both invoke rather than reimplement the kernel. Production harness packages retain configuration generation, native mapping, hook behavior, and their public contracts under ADR-005.
3. [Workstation, CI, and Crabbox Execution ADR-002](/docs/blueprints/testing/integration/ci-execution) solely owns affected selection, replay and hostile-certification escalation, the complete frozen-head matrix, protected-main and scheduled coverage, release-candidate execution, workflow-run supersession or cancellation, and final admission. Workflow code schedules catalog identities and consumes terminal scenario outcomes; it owns no PTY/process mechanism or product oracle.

**Context:** CodexBar proves that real CLI and PTY behavior can share one production process mechanism and path-aware CI. Agentscope needs additional product proof that CodexBar does not: the exact installable candidate (`AC-INS-001.1` through `AC-INS-001.4`, `AC-INS-003.2`); reversible, conflict-aware hooks (`AC-HAR-001.1`, `AC-HAR-001.2`, `AC-HAR-002.1`); provider isolation and OTLP-only destination observation (`AC-GOV-001.1`, `AC-REP-004.1`); trace and destination correlation (`AC-OVR-001.1`, `AC-OVR-002.1`, `AC-CAP-001.4`, `AC-REP-002.1`, `AC-REP-003.4`); and native lifecycle evidence (`AC-PLAT-001.1`, `AC-PLAT-001.3`). These requirements justify the product-scenario layer, not another runner.

**Consequences:** A module has one layer owner and a role-specific seam. Cancellation propagates one way from workflow to controller to kernel; the kernel joins its child and handles, the controller independently joins and reconciles the backend before returning, and a canceled workflow publishes no evidence authority. Kernel changes cannot encode scenario success, scenarios cannot choose CI frequency, and workflows cannot interpret raw terminal or trace content. The CI scheduling ADR is the only authority for affected intermediate scenarios, the complete frozen-head matrix, hostile-substrate certification, repeated clean replays, protected-main runs, scheduled runs, and release-candidate runs; no lower layer hard-codes or restates that cadence.
