## Capability Summary

Agentscope development may use disposable Hetzner Linux workers through the official Crabbox Cloudflare coordinator. The supported setup follows the documented Cloudflare, Wrangler, Crabbox, and Hetzner path, with ordinary least-privilege credentials and bounded leases. Crabbox is an optional development accelerator; workstation execution remains supported and GitHub-hosted CI remains merge and release authority.

This Blueprint owns the remote-development coordinator, credentials, lifecycle limits, cleanup, and cost controls. It composes the scenario, evidence, and isolation decisions in [Harness Execution Verification](/docs/blueprints/testing/harness-execution) rather than redefining them. Delivery order, ownership, and current blockers belong in Beads.

## Architecture Decision Records

### ADR-001: Use the official Crabbox Cloudflare coordinator

**Decision:** Brokered remote development uses the Cloudflare Worker and SQLite-backed `FleetDurableObject` from `openclaw/crabbox` tag `v0.46.0`, exact commit [`8ba71f913bbe57285ae29af45ef0d8ec6712477d`](https://github.com/openclaw/crabbox/tree/8ba71f913bbe57285ae29af45ef0d8ec6712477d). Deployment consumes that immutable source and its `worker/package-lock.json`; Agentscope does not copy the coordinator implementation or follow a moving branch. A version change requires a reviewed Blueprint update covering compatibility, migrations, lifecycle behavior, provenance, and security-relevant release notes.

The supported bootstrap is the upstream-documented path: install the locked Worker dependencies with `npm ci`, run the upstream Worker checks and build, authenticate Wrangler using its supported interactive login or an account-scoped API token, configure the required Worker secrets, deploy with the project-local Wrangler, and verify the workers.dev health endpoint. The pinned Crabbox client is then built or installed from the same admitted release, configured for that coordinator, and checked with `crabbox doctor` before the first bounded Hetzner run ([Crabbox infrastructure](https://github.com/openclaw/crabbox/blob/8ba71f913bbe57285ae29af45ef0d8ec6712477d/docs/infrastructure.md), [Cloudflare Workers CLI guide](https://developers.cloudflare.com/workers/get-started/guide/)).

**Context:** Crabbox already owns serialized leases, provider adapters, cost reservation, scheduled cleanup, and brokered Hetzner lifecycle. Its documented Cloudflare deployment uses Wrangler directly; reproducing deployment as a second security product delayed the first usable fleet without improving Crabbox's provider lifecycle.

**Consequences:** Cloudflare is the coordinator runtime for unattended development. The Node/PostgreSQL coordinator, Cloudflare Containers provider, custom domains, Cloudflare Access, GitHub OAuth, portals, artifacts, Tailscale, prewarming, and other provider integrations are outside the initial setup.

### ADR-002: Keep the deployment reproducible without a privileged launcher

**Decision:** The immutable Crabbox Worker project and lockfile own the Node dependency graph and project-local Wrangler version. Operators run the lock-installed Wrangler from that checkout; a global Wrangler or moving `latest` is not deployment authority. The exact source revision, lockfile, deployment profile, Worker name, and successful health result are recorded in a non-secret operator note or deployment receipt.

Wrangler's normal authentication mechanisms are supported. An attended operator may use `wrangler login`; noninteractive operation may use a dedicated account-scoped API token supplied through `CLOUDFLARE_API_TOKEN`. Neither path requires a root-owned launcher, a separate service account, signed executable roots, an immutable one-use plan, or repeated `sudo` observation gates. Authentication state remains in the operator's normal protected user environment and is never committed.

**Context:** Cloudflare documents browser login for interactive Wrangler use and API tokens for noninteractive deployments. The project-local Wrangler and lockfile provide the useful reproducibility boundary without replacing the upstream authentication and deployment workflow.

**Consequences:** A deployment can be reproduced by another authorized operator from the pinned checkout. Toolchain validation stays proportional to a development service and does not block initial setup on bespoke host installation.

### ADR-003: Use one personal Cloudflare account and one dedicated Hetzner project

**Decision:** The approved Cloudflare account may be the repository owner's personal account, including an account with unrelated zones, Pages projects, or Workers. The deployment targets only the Worker `agentscope-crabbox-development`, its `FLEET` Durable Object binding, its scheduled trigger, its workers.dev hostname, and its three required secrets. No zone route, Worker Domain, custom domain, Pages binding, D1, KV, R2, or unrelated Worker resource is part of the setup.

Cloudflare authentication uses the least privilege that supports the selected documented flow. A Wrangler OAuth session is acceptable for attended setup. An API token is dedicated to the coordinator and scoped to the approved account with Workers script deployment and the companion reads Wrangler requires; it receives no unrelated product write authority. The personal account's ordinary Workers plan is acceptable; setup does not require a dedicated Cloudflare account, a separate billing credential, or an independently signed billing observation. The operator confirms the intended plan in the Cloudflare dashboard before the first deployment and enables provider billing alerts where available.

Hetzner uses one dedicated project containing no unrelated resources and one project-scoped read/write API token for the coordinator. The coordinator token is not forwarded to a Crabbox guest, repository process, candidate, command argument, log, or artifact. The dedicated project is the cleanup and cost-accounting boundary.

**Context:** Cloudflare's Workers deployment permission is account-scoped, while Hetzner projects provide a practical provider-resource boundary. A personal Cloudflare account is an accepted blast-radius trade-off; unrelated resources remain out of scope and are not mutated or swept.

**Consequences:** Setup needs the credentials that the documented deployment actually consumes, not seven independent credential slots. Credential rotation uses Cloudflare, Hetzner, and Wrangler's ordinary supported controls.

### ADR-004: Store only the three coordinator secrets in Cloudflare

**Decision:** The coordinator receives exactly `HETZNER_TOKEN`, `CRABBOX_SHARED_TOKEN`, and `CRABBOX_ADMIN_TOKEN` as Cloudflare Worker secrets. The shared and admin tokens are independently generated random values and differ from the Hetzner token. Operators enter them using Wrangler's secret commands or an equivalently protected Cloudflare dashboard flow; they are never plain Wrangler variables, repository files, shell arguments, VM inputs, logs, or retained test artifacts ([Cloudflare Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/)).

The non-admin shared token is the normal Crabbox client credential. The admin token is retained only for attended coordinator administration and incident recovery. Agents and remote workloads receive neither Cloudflare nor Hetzner credentials; the remote guest receives only the source and inputs required for its bounded job.

**Context:** Worker secrets are the upstream-supported boundary for coordinator credentials. Separate opaque local slot/version identities and a custom pairwise-equality proof are not necessary for normal setup when the operator generates and stores three distinct credentials directly.

**Consequences:** Secret values can be rotated independently using documented provider commands. A suspected disclosure freezes new leases until the affected token is rotated and owned resources are reconciled.

### ADR-005: Bound every remote worker and the fleet

**Decision:** Agentscope selects Hetzner explicitly and uses `cx33` as the only initially admitted server type, Ubuntu 24.04, and the dedicated project. Every run is non-persistent by default (`keep=false`), has a hard TTL of at most 90 minutes, an idle timeout of at most 20 minutes, and an explicit lease identity. The coordinator admits at most four active leases total and per owner, and retains the existing USD 25 monthly reservation caps for the fleet, owner, and organization. A caller may request a smaller duration or lower concurrency but cannot broaden these limits.

The initial proof uses one worker and one bounded command. Parallel development increases only within the four-lease ceiling after that worker reaches terminal cleanup. The coordinator's cost reservation is a safety estimate, not a provider invoice ceiling; the operator also uses Hetzner project billing visibility and alerts.

**Context:** The upstream default class can resolve to substantially larger machines. Explicit type, count, TTL, idle, and budget limits prevent an ordinary development command from silently selecting an expensive or persistent fleet.

**Consequences:** Crabbox can provide parallel development capacity without becoming unbounded infrastructure. Any request outside the closed limits fails before provider creation.

### ADR-006: Let Crabbox own leases and make cleanup observable

**Decision:** The Crabbox coordinator and client own create, idempotent retry, stop, expiry, and scheduled cleanup through their documented APIs. Normal operation records the coordinator lease identity and Hetzner server identity, waits for the command result, requests stop on completion or failure, and confirms the lease is terminal. The inner Docker scenario separately reconciles its owned containers, networks, volumes, and images before the outer worker is accepted as clean.

After an ambiguous create or cleanup result, new leases pause while an operator compares Crabbox lease state with the dedicated Hetzner project, stops or deletes only the identified owned server, and confirms the project inventory is reconciled. Broad prefix sweeps and deletion of unrelated resources are prohibited. Retirement stops all leases, confirms the dedicated Hetzner project has no Crabbox servers or temporary keys, removes the three Worker secrets, and deletes the exact coordinator Worker and Durable Object using documented Cloudflare/Crabbox procedures.

**Context:** Automatic TTL and scheduled cleanup reduce leak duration but are not themselves proof that a billed server disappeared. The dedicated project and exact lease/server identities provide a comprehensible recovery boundary without a second signed operation ledger.

**Consequences:** Cleanup failures remain visible and block additional spend. Normal setup and use do not require a one-use signed plan, immutable consumption ledger, separate read-only observation token, or sudo-gated state observer.

### ADR-007: Preserve the hermetic and release boundaries

**Decision:** Crabbox supplies a disposable outer Linux host. Agentscope runs the same hermetic scenario runner inside it with the same candidate, manifest, dummy harness credentials, internal model proxy, loopback telemetry ledger, and denied public egress used by workstation and CI execution. Provider credentials never enter the guest or the inner scenario.

Crabbox results accelerate development and may provide supplemental evidence. GitHub-hosted required checks remain merge and release authority; fleet availability, Cloudflare availability, Hetzner capacity, or development-budget exhaustion cannot turn a failed required check into a pass or block a release that otherwise satisfies its release gates.

**Context:** Remote compute location does not change the test's trusted inner boundary or confer release authority.

**Consequences:** Workstation execution remains a supported fallback. A successful remote run is accepted only after both inner cleanup and the outer Crabbox lease reach a terminal state.

### ADR-008: Deprecate the protected bootstrap

**Decision:** The existing protected launcher, seven-slot credential model, signer roots, one-use plan and consumption ledger, account-wide state observer, and attended upgrade ceremony are optional deprecated implementation. They are not required for initial deployment, ordinary operation, credential rotation, cleanup, development, CI, or release, and their absence or failure must not block the documented happy path. No new operational dependency may be added to them.

Existing launcher files may remain temporarily so this standalone Blueprint changes architecture without mixing in implementation deletion. A later Beads-owned implementation change removes or archives them after the Wrangler/Crabbox path is documented and proven. Previously enrolled launcher credentials should be revoked after the replacement path is working; they are not migrated into the new setup or treated as authority for it.

**Context:** The protected bootstrap repeatedly failed before the first coordinator deployment and imposed credential and host ceremonies beyond the upstream operational model. Keeping it mandatory would preserve the blocker this decision is intended to remove.

**Consequences:** Implementation and operator documentation must converge on the supported happy path after this Blueprint merges. The deprecated path may be used only for diagnostic comparison at the owner's explicit request and cannot gate that convergence.
