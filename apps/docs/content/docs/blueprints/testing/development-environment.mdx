## Capability Summary

Agentscope development can use disposable remote Linux capacity without making a developer workstation the fleet-control authority. This Blueprint owns the remote-development coordinator, its operator and agent trust boundaries, lifecycle limits, reconciliation, and cost controls. It composes the scenario, evidence, isolation, and release-authority decisions in [Harness Execution Verification](/docs/blueprints/testing/harness-execution) rather than redefining them.

## Architecture Decision Records

### ADR-001: Adopt the official Crabbox Cloudflare coordinator

**Decision:** Unattended remote development uses the Cloudflare Worker and SQLite-backed `FleetDurableObject` from `openclaw/crabbox` tag `v0.46.0`, exact commit `8ba71f913bbe57285ae29af45ef0d8ec6712477d`. Every live coordinator deployment consumes the immutable tagged source and its `worker/package-lock.json`; it does not copy coordinator code into Agentscope or follow Crabbox `main`. The reviewed upstream is MIT-licensed (`LICENSE` SHA-256 `6ae2daf92d73e912aef033d56ce374df997ae0ad1d88ca9ef76f0c11123aae27`). A version change is a reviewed development-environment change that verifies client/coordinator compatibility, lifecycle behavior, migrations, provenance, and security-relevant release notes before rollout.

The only source exception is the terminal retirement artifact in ADR-014. It is a separately reviewed and authenticated Agentscope-owned no-op Worker entry point with no imports, exports, fetch or scheduled behavior, bindings, secrets, routes, assets, provider code, or acquisition/reaper authority. It cannot serve as a coordinator version or rollback target and is admitted only after terminal provider-zero reconciliation so Cloudflare can apply the final class-deletion migration that the live pinned entry point cannot express.

**Context:** Crabbox already provides serialized lease creation, fixed-ID replay, provider adapters, cost reservation, scheduled cleanup, and brokered Hetzner lifecycle ownership. Reimplementing those controls in a repository script would create a second and weaker fleet authority. The reviewed source is the [exact Crabbox commit](https://github.com/openclaw/crabbox/tree/8ba71f913bbe57285ae29af45ef0d8ec6712477d); the tag and peeled commit are both verified before use.

**Consequences:** Cloudflare is the only unattended coordinator runtime for this development environment. Direct provider mode remains an attended diagnostic path and is not an agent fallback. The terminal no-op artifact performs no remote development work. The Node/PostgreSQL coordinator and Cloudflare Containers provider are out of scope.

### ADR-002: Pin the deployment toolchain through the upstream lock

**Decision:** Deployment and validation run from the immutable Crabbox `worker/` project with the upstream-selected Node.js major 24 and `npm ci`. One exact Node 24 runtime release and distribution digest are admitted and recorded before building; the same runtime is reused for validation, deployment, and rollback preparation. The operator invokes its absolute `<owned-node>/bin/node` and `<owned-node>/bin/npm` paths in a closed execution environment whose child resolver places only that Node distribution plus an audited minimum of operating-system tools on `PATH`; ambient `NODE_OPTIONS`, user/global npm configuration, and another `node`, `npm`, or `npx` are excluded. Project scripts and `env node` shebangs must resolve to the admitted runtime. Wrangler is the project-local package resolved by the upstream lock, pinned to version `4.114.0`. Commands use `<owned-node>/bin/npm exec --prefix worker -- wrangler`; an absent global `wrangler` is expected, while unowned `npx`, moving `latest`, or another child runtime are prohibited. The executable identities and closed environment are reverified immediately before install, validation, deployment, or rollback receives Cloudflare authority. Deployment evidence records the exact Node/npm identities and resolved locked artifacts rather than duplicating their complete inventory here.

The privileged Crabbox client is built from the same exact source commit and `go.sum`. One exact Go `1.26.5` distribution and distribution digest are admitted before build; the launcher invokes its absolute `go` path with `GOTOOLCHAIN=local` so the upstream `go1.26.5` directive cannot select or download another compiler. The build uses `<owned-toolchain>/bin/go build -trimpath -ldflags="-s -w -X github.com/openclaw/crabbox/internal/cli.version=0.46.0" -o <owned-output> ./cmd/crabbox`. Its compiler distribution digest, binary digest, Go build identity, source commit, build flags, and `0.46.0` self-report must all match the operator-approved launcher record before the launcher supplies a coordinator bearer or permits lease mutation. Homebrew, `PATH`, a version string alone, automatic toolchain resolution, and an independently downloaded binary are not executable authority.

**Context:** Cloudflare recommends a project-local Wrangler so collaborators use the same version and can roll back ([Wrangler installation](https://developers.cloudflare.com/workers/wrangler/install-and-update/)). The pinned Crabbox source declares `wrangler ^4.114.0`, while its lock closes that range to one artifact.

**Consequences:** Agentscope does not add Wrangler or Crabbox to its product workspace. Deployment verifies every executable and lock identity before authentication or mutation.

### ADR-003: Give the development coordinator one explicitly owned environment

**Decision:** The repository owner controls one explicitly admitted Cloudflare account, one development-only Worker environment named `agentscope-crabbox-development`, and one dedicated Hetzner project containing no unrelated resource. The Cloudflare account may be the owner's shared personal account and may contain unrelated zones, Pages projects, or other resources; that accepted account-level blast radius does not make any unrelated resource part of the coordinator environment. A cryptographically random immutable coordinator-environment identifier namespaces every lease identity and is bound to the exact account, external operator record, deployment profile, Worker environment, secrets, and Durable Object namespace. Its account and Workers-plan identity, workers.dev hostname, Durable Object namespace, deployment identities, environment identifier, and provider project identifier are external deployment records, never guessed or committed as reusable authority.

The coordinator uses only its script-level workers.dev hostname binding. It creates no zone route, Worker Domain or other custom domain, Cloudflare Access application, Pages binding, or account-shared storage. Cloudflare grants Workers Scripts Write at account scope rather than for one Worker, so the human deployment credential necessarily has authority that could mutate unrelated Worker scripts, Worker Domains, and script settings. The architecture accepts that human-held breadth but does not misstate it as resource isolation: operator policy permits the credential to mutate only the exact Worker environment, secret names, scheduled trigger, versions, script-level workers.dev binding, and Durable Object namespace, and the agent and fleet-control service receive no Cloudflare credential or mutation capability. The credential is narrowed to Workers Scripts Write and the minimum companion read permissions needed to enumerate that mutation surface, is dedicated to coordinator deployment, and is stored separately from unrelated account credentials. It receives no separate zone, Pages, D1, KV, R2, billing, membership, or unrelated-product write authority.

Every Cloudflare mutation freezes coordinator acquisition and holds one owner-controlled account-mutation fence that prohibits concurrent dashboard, API, or deployment changes within the credential's Workers mutation surface until reconciliation completes. Before admitting the credential, the operator derives a reviewed permission manifest from Cloudflare's current API authority for Workers Scripts Write and its companion reads. That manifest enumerates every permitted action and classifies its observable projection, including Worker scripts, versions and deployments, script and account workers.dev settings, Worker Domains, scheduled triggers, secret-name sets, Logpush, observability, tail consumers and live tails, cache and other script settings, and Durable Object namespaces, bindings, migrations, deletion tombstones, renames, and transfers. Worker Domains, live tails, unrelated secret writes, and Durable Object deletion, rename, or transfer are forbidden during ordinary operation. The only admitted exceptions are write, rotation, or retirement deletion of the three exact coordinator secret names under the plan below, plus the exact terminal `FleetDurableObject` delete migration in ADR-014. A new or unclassified Cloudflare action fails admission.

The authenticated durable operator record binds the exact intended steps, the current coordinator resource/version identities, the permission-manifest identity, and an independently captured canonical identity and relevant-configuration digest for every other observable resource in that permission surface. Products outside the credential's permission surface are recorded as contextual account inventory but are not falsely claimed as a complete configuration proof; their protection comes from absent write authority. The human deployment launcher accepts only the exact plan authority in ADR-013 and has no general API operation mode; it rejects every forbidden, transient, unrelated-script, or unplanned action before resolving the credential. Each approved secret mutation binds the exact secret name to an opaque operator-store slot and immutable version identity authenticated under a separate operator evidence key; neither the plan nor evidence contains the value or a reusable plain digest. Before any value reaches Cloudflare or unattended authority, the operator performs a confidential equality check inside that protected store and proves that the resolved values for `HETZNER_TOKEN`, `CRABBOX_SHARED_TOKEN`, and `CRABBOX_ADMIN_TOKEN` are pairwise distinct; equality or an indeterminate comparison fails admission without exposing a value, digest, or comparison artifact. The launcher revalidates each slot version, consumes it directly into the exact Cloudflare secret request after plan authorization, and cannot substitute another slot or version. Because Cloudflare returns no secret value, validation is forward-only and credential-specific: it exercises the coordinator's bounded non-mutating authentication/provider-read path, proves that the shared token is rejected by a non-mutating admin-only route while the admin token succeeds, and proves that the provider token works only through the admitted provider-read path rather than either coordinator role. An uncertain or role-ambiguous result remains unadmitted until newly versioned pairwise-distinct secrets are applied and any superseded provider credential is revoked. Each completed prefix records the exact request identity and returned coordinator resource identity before the next prefix. A crash, lost response, missing post-inventory, audit gap, or unexpected observable change keeps acquisition frozen; the operator reacquires the fence, inspects exact per-resource state and uses Cloudflare audit history only as supplemental evidence, then gives each recorded prefix one identity-bound action: resume its idempotent step, compensate its own newly created resource, roll back to the recorded compatible Worker version, or quarantine for human reconciliation. It never deletes or rewrites an unrelated resource to make the before/after projection match.

Ordinary completion proves that the exact owned observable resources reached their recorded terminal state, every other observable projection remained unchanged, and the authenticated operator ledger contains no gap or out-of-plan request. It does not claim provider-observable proof that no transient or write-only action occurred. A ledger discontinuity, credential-exposure signal, unexpected Cloudflare action, ambiguous target, incomplete permission manifest, or unavailable required observable projection enters the ADR-010 all-affected-resource quarantine rather than being converted to a nonmutation claim.

The account-level workers.dev subdomain is shared account state, not a coordinator-owned retirement target. If it is inactive, enabling it is a separate owner-approved shared-account mutation recorded before coordinator deployment and it remains enabled after coordinator retirement. Ordinary coordinator deployment and retirement may enable or disable only the exact script-level workers.dev binding for `agentscope-crabbox-development`.

**Context:** A Cloudflare Worker version, Durable Object state, script-level workers.dev binding, and provider project form one operational unit even when their account is shared. Account-level isolation would reduce credential and runtime-data blast radius, but explicit resource identity, absence of zone routes and Worker Domains, human-only Cloudflare authority, and permission-derived before/after inventories bound intended control-plane mutation and detect collateral configuration change without requiring the owner to create another account. Those inventories cannot prove that compromised code caused no data-plane side effect through an unrelated Worker's existing bindings.

**Consequences:** Every operation and evidence record names the exact account and Workers plan, Worker environment, version identifier, Durable Object migration tag and namespace, script-level coordinator origin, permission-manifest identity, Hetzner project, and actor. Incident recovery and retirement use those identities rather than account-wide listing patterns or cleanup. Values that are sensitive or installation-specific remain in the operator record rather than documentation or repository configuration. Sharing the account and its account-scoped deployment credential is an accepted control-plane and potential runtime-data blast radius, not permission to reuse unrelated credentials, bindings, zone routes, Worker Domains, storage, billing configuration, or resources.

### ADR-004: Own one complete fail-closed deployment profile

**Decision:** Agentscope owns one reviewed, non-secret Cloudflare deployment profile separate from the immutable Crabbox source. Live deployment stages that profile beside the verified upstream `worker/` entry point; it never deploys upstream `worker/wrangler.jsonc` directly. The profile is the sole authority for the Worker name, compatibility date and flags, workers.dev/preview behavior, assets, `FLEET` SQLite Durable Object binding and migration history, 15-minute trigger, allowed non-secret variables, and required secret names.

The allowed variables are limited to the immutable coordinator-environment identifier, Agentscope development org/owner labels, four fleet/owner/org active-lease caps, USD 25 fleet/owner/org monthly reservation caps, and bounded run retention. The only initial Worker secret names are `HETZNER_TOKEN`, `CRABBOX_SHARED_TOKEN`, and `CRABBOX_ADMIN_TOKEN`. AWS/Azure/GCP/Daytona settings, workspace provider and prewarm, provider orphan-delete switches, GitHub OAuth, Access, portal bridges, artifacts, Tailscale, custom routes, and all upstream OpenClaw names, origins, orgs, capacities, and budgets are absent. Before any mutation, locked Wrangler validation and dry build must project exactly this allowlist; any extra, missing, inherited, dashboard-only, or differently resolved binding, trigger, migration, variable, secret name, route, or Worker identity fails closed.

**Context:** The pinned upstream Wrangler file is a production example for OpenClaw: it selects OpenClaw identities, AWS prewarm, multiple provider sweeps, active caps up to 20, and budgets up to USD 50,000. Source immutability does not make those deployment values safe for Agentscope. Cloudflare environment variables and bindings do not provide a general inheritance mechanism that can be assumed to remove unwanted top-level values.

**Consequences:** The deployment profile may reference pinned upstream source but copies no coordinator implementation. ADR-014 permits one terminal retirement projection of this profile that preserves the exact Worker identity and append-only migration history while removing the entry point's `FLEET` binding, trigger, variables, secrets, workers.dev binding, and runtime behavior and adding only the final class-deletion migration. Account IDs, origins, and secret values enter only the external operator record or authenticated deployment input; the reviewed live or terminal profile still determines which fields may exist.

### ADR-005: Separate deployment, administration, agent, and workload authority

**Decision:** Cloudflare deployment credentials and the Crabbox admin token are available only to the human-owned deployment path. `HETZNER_TOKEN`, `CRABBOX_SHARED_TOKEN`, `CRABBOX_ADMIN_TOKEN`, and any future session secret are Worker secrets, never plain Wrangler variables, repository values, shell arguments, VM inputs, scenario inputs, logs, or artifacts ([Cloudflare Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/)). The initial non-browser installation omits GitHub OAuth, portal bridges, artifact storage, Tailscale, and their secrets.

A separate project-scoped read-only Hetzner inventory token is held in the fleet-control principal's protected secret store and injected only into its dedicated provider-inventory client memory. It permits only independent provider list/get observations needed for server, SSH-key, and ownership reconciliation; it is unavailable to the Worker, agent session, shells, repositories, candidates, VMs, scenarios, environments, commands, logs, and artifacts and is rotated and revoked independently from the Worker's write token. A distinct human-owned project-scoped read/write recovery credential is retained in a separate operator-controlled secret store and is unavailable to the fleet service and unattended agents. Hetzner necessarily gives that credential GET, DELETE, POST, and PUT authority across the dedicated project; the architecture accepts that human-held breadth, while operator policy permits its use only for attended identity-bound inventory and deletion during incident or retirement recovery. Neither credential may be substituted for the Worker token or Crabbox authentication, and loss of read-only inventory authority freezes unattended acquisition and terminal claims without disabling the human recovery path.

Unattended agents invoke one host-owned service under a dedicated fleet-control OS principal through an out-of-band tool boundary that is unavailable to shells, repository processes, candidate processes, and remote workloads. Before an agent request, the owner creates an authenticated authorization record outside the agent session, bound to the exact immutable source, candidate, manifest, normalized intent, environment identifier, expiry, nonce, and operation identity. The agent cannot create, broaden, or edit that record. The host tool authenticates the agent session, requires an exact match, and atomically consumes the authorization before supplying a single-use capability for that closed job description; neither the authorization, capability, nor service endpoint is placed in an agent environment, filesystem, command, log, or artifact. The fleet service rejects unauthenticated direct local socket, HTTP, CLI, or subprocess callers and reconstructs the request from the consumed capability rather than accepting caller-selected provider operations. Replay, expiry, substitution, missing owner authority, and repository-induced requests without a matching prior record fail before acquisition.

That principal alone holds the non-admin Crabbox automation credential, the authenticated append-only operation ledger, per-lease keys, and one protected explicit Crabbox configuration selected with `CRABBOX_CONFIG`; the privileged client never discovers repository, user, or ambient Crabbox configuration. The service resolves the authorized source identity itself, stages the exact candidate and manifest into an owned immutable input area, recomputes their digests before acquisition and before remote execution, and rejects dirty or substituted inputs. It owns remote invocation and downloads evidence into a protected result area, verifies candidate, manifest, executor, cleanup, and evidence identities independently, and returns only the sanitized bounded projection through the host tool. The service enforces provider `hetzner`, type `cx33`, location `fsn1`, Ubuntu 24.04 amd64, per-lease SSH keys, `keep=false`, stop-always, TTL at most 90 minutes, idle timeout at most 20 minutes, and the current fleet cap before invoking the matching Crabbox client. It does not expose the bearer value, accept arbitrary coordinator origins, or offer admin, deployment, secret, image, pool, or direct-provider operations. Candidate and remote repository code receive no fleet capability or coordinator, Cloudflare, or Hetzner credential.

Only that principal may use the automation token, so a second launcher cannot become a concurrent writer. After every transition, the service writes and authenticates its ledger update before acknowledging success and maintains an owner-controlled encrypted backup. Lost, unverifiable, stale, or partially restored ledger continuity freezes acquisition. Host migration requires revoking the old automation token, reconciling coordinator and provider state after the freeze, restoring and authenticating the ledger and retired-ID set, provisioning a new token, and only then admitting work. Mac or launcher loss stops new acquisitions but cannot stop the cloud-side reaper.

**Context:** Crabbox shared-token authentication is non-admin but is a trusted-operator credential, not a hostile-tenant capability. Coordinator-side cost and count limits bound mistakes across callers; the launcher additionally removes expensive or persistent request shapes that the general Crabbox API legitimately supports.

**Consequences:** The initial fleet trusts authenticated Agentscope development sessions only within the exact authority the owner recorded independently; it does not trust repository or candidate code with control-plane credentials or invocation authority. If owner authorization, the host tool, provider inventory, independent input staging, or result verification is unavailable, unattended acquisition fails closed. A future multi-user or mutually untrusted service requires a new authentication decision rather than sharing this installation.

### ADR-006: Bind retries to one fixed, single-use lease identity

**Decision:** Each acquisition has one launcher-minted `cbx_` lease ID and operation record bound to the authorized task, source commit or dirty-patch digest, candidate digest when present, scenario manifest identity, exact normalized create inputs, and lease policy. Its canonical identity is the tuple of immutable coordinator-environment identifier and raw lease ID. The launcher invokes the pinned client's fixed-ID `warmup --lease-id` path. Retries reuse that exact raw ID and normalized intent within the same environment. A changed tuple requires a new raw ID and cannot adopt, replace, or release the earlier lease; a terminal raw ID is never reused within its environment, while a recreated coordinator receives a new environment identifier rather than inheriting the old raw-ID namespace.

The coordinator's single `FleetDurableObject` is the serialization and replay authority. The versioned fixed-ID `PUT` reserves a hash of the immutable normalized intent before provider work; an identical replay joins or returns the same provisioning or active lease, while drift or terminal-ID reuse fails before another provider create. A lost or ambiguous response is recovered only by repeating that exact fixed-ID request and then observing its bound state. The launcher does not issue a fresh create until the first identity is terminally reconciled. Conflicting identities, unknown state, or unavailable reconciliation fail closed.

**Context:** A provider may create a machine before its response is lost. Crabbox `v0.46.0` documents `--lease-id` as its automation idempotency contract. Its ordinary create-attempt token is process-local and therefore cannot be the launcher's durable cross-process identity.

**Consequences:** Local claim files are useful client state but never the sole proof that a provider resource exists or is gone. No agent can convert an unknown acquisition into success by deleting its claim.

### ADR-007: Enforce hard lifetime and capacity limits plus bounded cost reservations

**Decision:** The initial coordinator sets fleet, owner, and organization active-lease limits to four and monthly compute-reservation guardrails to USD 25. The non-admin automation identity is the only initial owner and organization. Every ordinary job remains one-shot and requests a maximum 90-minute TTL and 20-minute idle timeout; heartbeats may extend idle expiry only within the hard TTL. `keep` is prohibited. The launcher admits at most four operations and applies the exact provider/type/location/image bounds in ADR-005 even when the coordinator has spare capacity.

Raising concurrency, monthly spend, server type, lifetime, or identity count requires a reviewed policy change and a verified provider quota; it is not a runtime convenience flag.

**Context:** Crabbox reserves modeled worst-case compute cost before provisioning and rejects active-count or reservation overflow. Its model is not the provider invoice and excludes some network, address, snapshot, tax, credit, and discount effects. A powerful default type or unbounded kept lease would defeat the purpose of elastic development capacity even when cleanup eventually succeeds. In the approved shared account, Workers, Pages Functions, and Durable Object invocations consume account-level Free quotas; coordinator traffic can therefore reduce unrelated service availability, and unrelated traffic can delay coordinator alarms or scheduled cleanup until quota reset.

**Consequences:** The four-worker value is a safety ceiling, not a durable allocation or scheduling policy. Cloudflare deployment is admitted only while the exact shared account's Workers and Durable Objects products are independently verified to remain on the zero-overage Workers Free plan: Cloudflare currently caps Worker and Durable Object requests at 100,000 per day and fails further free-tier operations rather than billing overage ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)). Unrelated account subscriptions, zones, or Pages resources neither prove nor disprove that product-specific admission. The human operator uses an authenticated Cloudflare billing or product-plan authority independent of the deployment profile and resource inventory, records the effective Workers plan plus every current Worker, Durable Object, storage, and CPU quota, and fails closed if the Workers or Durable Objects plan is paid, permits usage overage, or cannot be verified.

One human-owned monitoring path holds a separate least-privilege read-only Cloudflare billing and product-plan credential in the deployment secret store; the credential is unavailable to agents, the fleet-control service, repositories, shells, VMs, scenarios, commands, logs, and artifacts. While the coordinator is deployed, that path refreshes and signs the authoritative plan observation at least every 15 minutes. The observation is bound to the owner authorization record required by ADR-005 and must be no more than 15 minutes old when the record is minted, when acquisition begins, and throughout every active or uncertain operation.

The fleet-control service verifies the signed record and freshness without receiving Cloudflare authority. A missing, expired, discontinuous, superseded, paid, or overage-capable observation freezes new acquisition while preserving release/reaper authority; active leases drain through bounded release or expiry, and the workers.dev deployment is disabled after provider reconciliation if a compliant observation cannot be restored. Cloudflare's sampled or delayed Workers, Pages Functions, and Durable Objects analytics are advisory diagnostics, not billing, quota, admission, cleanup-reserve, or terminal authority; the architecture claims no exact current aggregate-usage oracle that Cloudflare does not provide. Quota exhaustion may therefore delay the cloud reaper and deny unrelated Workers or Pages Functions without advance warning. That runtime availability blast radius is explicitly accepted for the shared account and cannot be reported as resource isolation. Coordinator unavailability or an observed quota rejection freezes acquisition immediately. Independent Hetzner inventory and attended identity-bound deletion remain available when Cloudflare cleanup cannot run, and no terminal claim is made until provider absence is observed. Because Workers-plan changes remain human-only account mutations, the owner may not change the Workers or Durable Objects plan while the coordinator environment is enabled; a planned or observed change first freezes acquisition and triggers incident reconciliation plus a reviewed policy decision. Deployment, authorization, and subsequent coordinator operation may not enroll, upgrade, or attach the coordinator to a paid Workers or Durable Objects plan.

A public caller may exhaust free availability but cannot create Cloudflare usage charges; quota pressure freezes acquisition and invokes the attended cleanup path for any provider resource at risk. Any Workers or Durable Objects plan change requires a reviewed policy change and separate owner approval. The external evidence reports modeled Hetzner reservation and actual provider billing separately and never calls USD 25 an invoice ceiling.

### ADR-008: Make cleanup independent and reconciliation terminal

**Decision:** The coordinator owns brokered Hetzner release, expiry, retry, and deletion. Its Durable Object alarm schedules the earliest lease expiry or cleanup retry, and the Worker retains the upstream 15-minute scheduled trigger as an independent wakeup. Cloudflare guarantees alarm execution at least once and retries a thrown handler at most six times; the design therefore relies on the pinned coordinator's idempotent lifecycle, explicit rescheduling, and scheduled wakeup rather than treating one alarm delivery as deletion proof ([Durable Object alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)). A launcher or developer-Mac interruption cannot cancel those cloud-side paths. The pinned coordinator exposes no authoritative successful-maintenance heartbeat, so neither alarm delivery nor cron invocation is a terminal or monitoring oracle. Unattended acquisition remains disabled until controlled client-loss, idle-expiry, hard-TTL, and cleanup-failure scenarios prove the observable outcome: coordinator state and independently authenticated provider inventory converge to absence, including recovery after automatic retries are exhausted.

An operation is terminal only when coordinator lease/run state, provider inventory, local claim and per-lease key state, and label-scoped nested-Docker containers, networks, volumes, and images reconcile to absence or an explicitly retained bounded evidence record. Pending release, scheduled cleanup, an expired record with a surviving provider machine, missing inventory authority, or contradictory observations remain an incident.

The launcher serializes admission against its durable operation ledger. Any ambiguous create, release, inventory, or cleanup transition writes an acquisition freeze before returning. Only an attended reconciliation performed after that recorded transition may clear the freeze: it must compare coordinator state with an independently authenticated Hetzner inventory, account for every operation ID and owned provider resource, and persist the matching observation before the next admission. Routine admission with no uncertain transition relies on the coordinator's serialized active-count and cost reservations rather than an arbitrarily aged provider snapshot.

The fleet-control service polls authenticated coordinator state and independent Hetzner inventory while any operation is active or uncertain and at least every 15 minutes otherwise. Those lifecycle outcomes, not a claimed scheduler heartbeat, are the monitoring authority. It alerts the owner and freezes acquisition on an owned resource surviving five minutes beyond expected terminal cleanup, exhausted cleanup retry without observed recovery, any coordinator/provider disagreement, ledger discontinuity, free-plan quota pressure, or 80% of a count or reservation cap. Cloudflare Worker exception/cron notifications and provider billing alerts are enabled when the account exposes them, but they are supplemental and never substitute for identity-bound reconciliation. A high-priority alert is acknowledged within one hour; until then the cloud-side TTL/reaper remains the preferred deletion path, the attended recovery authority remains available, and no new lease is admitted. Missing provider observation or an unproved cleanup outcome keeps unattended mode disabled.

**Context:** Automatic cleanup reduces leak duration but is not proof of deletion. An alarm is at-least-once work and can be retried; provider deletion and durable state must therefore be idempotent and observed, not inferred from scheduling.

**Consequences:** GitHub CI may accept no Crabbox result whose outer lease is unresolved. Operator reconciliation retains delete authority even while ordinary acquisition is frozen.

### ADR-009: Retain one bounded, non-content fleet evidence record

**Decision:** Every remote operation retains one sanitized external evidence record binding the identities in Harness Execution ADR-006 plus launcher operation identity, coordinator source commit, Crabbox client version, Worker version and environment, Durable Object migration tag, Cloudflare request/deployment identifiers where available, fixed lease and provider resource identities, approved normalized intent and reserved-cost quote, start/end times, lifecycle transitions, cleanup attempts, terminal coordinator/provider/claim/key observations, and estimated and actual billed cost when the provider exposes it. Secrets, commands containing user content, repository archives, prompts, harness output, trace payloads, raw terminal output, IP addresses, and SSH private material are excluded.

**Context:** Remote capacity is an accelerator, but its results are not reproducible or auditable without binding the exact control plane and terminal cleanup evidence.

**Consequences:** Evidence can diagnose cost and lifecycle failures without becoming another trace or credential store. External ordinary-operation and cost evidence is deleted within 90 days. An external incident record remains while reconciliation is unresolved and is deleted within 90 days after closure. The pinned coordinator separately retains sensitive operational control state—including owner/org, provider scope and resource identities, network address, SSH endpoint metadata, paths, and cost—inside the access-controlled Durable Object for the life of that coordinator environment because `v0.46.0` has no compatible terminal-lease pruning contract. It is never described as content-free or exported as routine evidence; orderly retirement deletes it only after zero-resource reconciliation. Any earlier compaction or pruning requires a reviewed compatible migration that preserves replay and cleanup authority. A minimal authenticated retirement tombstone containing only the immutable environment identifier, retirement time, and terminal reconciliation digest is retained outside the coordinator without expiry so a recreated environment cannot alias the retired namespace; it contains no lease, provider, network, repository, command, trace, or user-content data. Crabbox portal logs or artifacts are disabled initially rather than becoming a second authority.

### ADR-010: Freeze acquisition first during incidents

**Decision:** Suspected credential exposure, auth bypass, cost-limit failure, stale reconciliation, orphaned provider state, or cleanup disagreement immediately disables new acquisitions without disabling authenticated list, inspect, release, reaper, and provider-reconciliation authority. The operator then revokes the affected non-admin credential, rotates the relevant Worker secret or independent inventory/recovery credential, inventories coordinator and Hetzner state independently, deletes only identity-bound owned resources through the attended recovery authority, verifies zero unknown resources, preserves sanitized incident evidence, and re-enables acquisition only after a reviewed cause and bounded proof.

Suspected exposure of the account-scoped Cloudflare deployment credential additionally acquires the ADR-003 mutation fence, revokes that credential immediately, preserves the already deployed Worker's cloud-side reaper when its integrity remains credible, and compares Cloudflare audit history plus exact owned and unrelated control-plane state against the durable pre-incident record. A restored configuration digest cannot prove absence of transient code execution or data-plane effects. Every unrelated Worker and every zone, hostname, or domain owner reachable through the permission manifest is therefore quarantined for its resource owner's incident procedure; Worker-bound and origin secrets, external credentials, and affected session authority are rotated, and Durable Object, external data, traffic, and access history are reconciled using each resource's own authority before service restoration. Unknown historical access or data impact remains explicitly unresolved rather than being converted to a proof of non-impact. A new dedicated human deployment credential is admitted only after every affected resource owner accepts or resolves its incident state and the account-level mutation fence can be cleared; it never replaces the revoked credential merely to clear the freeze. Exposure or loss of the read-only plan credential revokes it independently and leaves acquisition frozen until a replacement produces a fresh continuous observation.

**Context:** Deleting the Worker or Durable Object first would remove the best cleanup authority while provider machines may still exist.

**Consequences:** Provider-console deletion is an emergency reconciliation step, not the normal lifecycle. Ambiguous ownership stays quarantined for human resolution rather than broad cleanup.

### ADR-011: Roll back code without rolling back durable ownership state

**Decision:** Worker deployments retain Cloudflare version identity and the upstream Durable Object migration history. A rollback may move traffic only to a version proven compatible with the current Durable Object schema and outstanding lease records; it never deletes, recreates, copies, or rewinds the namespace. If compatibility is uncertain, acquisition stays frozen while the newest known-compatible coordinator retains reaper and release authority. Durable Object class or storage migrations are forward-reviewed, append-only changes and cannot be undone by a Worker code rollback ([Durable Object migrations](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/), [Worker rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)).

**Context:** Cloudflare can roll back Worker code, but durable state and class migrations have a different lifecycle. Blindly reverting both can strand the records needed to delete provider resources.

**Consequences:** Each deployment records its compatible predecessor and runs no traffic split across coordinator versions unless both are proven against the same active-state schema. Rollback verification includes reaper continuity and provider reconciliation, not only `/v1/health`.

### ADR-012: Keep the remote host outside the hermetic and release boundaries

**Decision:** Crabbox provisions only the disposable outer Linux host. Agentscope launches the unchanged hermetic Docker scenario inside it with dummy harness credentials, internal model proxy/mock, loopback OTLP ledger, and denied public egress. Real provider model credentials and live Langfuse credentials are prohibited. The same candidate and manifest remain runnable through workstation execution and CI execution.

Crabbox checkpoints are disabled for the initial brokered Hetzner environment. The pinned checkpoint record does not authenticate prepared-image/tool digests or prove the absence of credentials and prior scenario state, and brokered Hetzner does not provide a native snapshot authority. Enabling checkpoint reuse requires a later reviewed decision for an authenticated provenance manifest, allowed cache contents, secret scanning, clean-room revalidation, retention, and deletion. A checkpoint can never become acquisition, candidate, harness, image, or support authority.

GitHub-hosted required checks remain merge and release authority. Crabbox results accelerate development and may supply supplemental evidence, but fleet availability, Cloudflare availability, provider quota, or the USD 25 development budget cannot block a product release or turn a failed required GitHub check into a pass.

**Context:** A remote shell is not an isolation boundary, and Cloudflare coordination does not alter what the scenario is allowed to contact or observe.

**Consequences:** Before unattended fan-out, bounded evidence must prove one disposable worker and complete nested/outer cleanup. A synthetic substrate fixture makes no harness compatibility claim, and remote development performs no npm publication.

### ADR-013: Require explicit mutation authority and pre-use proof

**Decision:** Cloudflare login, secret creation, Worker deployment, Durable Object creation, one-time account-level workers.dev activation when required, script-level workers.dev binding activation or deactivation, and brokered Hetzner leasing each require explicit owner-authorized mutation scope. Zone-route and Worker Domain configuration are prohibited. Before a Cloudflare mutation, the human deployment path emits and fully flushes one versioned immutable plan envelope binding the exact account, environment identifier, source and toolchain identities, deployment-profile digest, permission manifest, owned and unrelated observable pre-state identities, closed ordered operations, opaque authenticated secret-slot/version identities when applicable, rollback actions, expiry, nonce, and intended terminal state. The owner authorizes that exact displayed envelope outside the deployment process; apply atomically consumes a single-use authority for only that envelope. Immediately before each mutation, apply revalidates the account, target, permission manifest, profile, relevant pre-state, and secret-slot/version identities and refuses output failure, replay, substitution, expiry, or drift without starting another mutation.

Before unattended use, the locked source and deployment inputs are dry-validated, the owner reviews the account/environment/secrets/limits inventory and exact mutation/rollback sequence through that envelope, and one explicitly approved disposable-worker proof reaches terminal zero-resource reconciliation with reviewed cost evidence.

**Context:** Architecture approval does not authorize external mutation or recurring spend.

**Consequences:** Delivery sequencing, milestones, ownership, and blockers remain in Beads. Deployment evidence cannot retroactively justify divergence from this Blueprint.

### ADR-014: Drain provider authority before retiring the coordinator

**Decision:** Coordinator retirement first freezes acquisition, acquires the ADR-003 mutation fence, and records that freeze outside the Worker. The operator then resolves every in-flight create, stops or allows bounded expiry of every lease, runs coordinator/provider reconciliation after the last transition, verifies no owned Hetzner machine or per-lease key remains, revokes the non-admin launcher credential, and writes the authenticated environment-retirement tombstone and terminal evidence. The owner next authorizes removal of the scheduled trigger, exact script-level workers.dev binding, and coordinator secrets, then deploys the separately authenticated ADR-001 no-op entry point with the ADR-004 terminal profile: no `FLEET` binding or class reference remains, and one irreversible append-only migration deletes only the exact `FleetDurableObject` class after its zero-resource state and retained tombstone are independently proven. After Cloudflare confirms that migration, the remaining Worker versions and script are removed. The terminal artifact has no rollback or traffic claim, and no rollback crosses the class deletion. No zone route, Worker Domain, or account-level workers.dev subdomain is created or deleted during retirement.

The read-only inventory, Cloudflare plan-observation credential, and attended recovery credentials remain available through final Cloudflare and provider absence observations. After terminal account reconciliation proves the exact coordinator observable resources absent, every other observable projection in the permission-derived mutation surface unchanged, and a continuous operator ledger with no out-of-plan request, the coordinator-dedicated account-scoped deployment credential and read-only plan credential are revoked, the mutation fence is released, and the Hetzner credentials are revoked or rotated out of the retired environment. Any ledger gap or exposure signal follows ADR-010 and prevents an unchanged-state claim. A teardown failure leaves acquisition frozen and the remaining release/reaper, deployment, inventory, and recovery authority available for identity-bound retry.

If Cloudflare control is unavailable while a provider resource survives, the incident path uses the independently authenticated Hetzner inventory and deletes only resources whose exact ownership identity is bound by retained coordinator and launcher evidence. It does not destroy the unavailable Durable Object namespace merely to make the inventory appear empty.

**Context:** Worker deletion is not lease deletion. Removing the coordinator or its durable state first can discard the authority needed to identify, release, retry, and audit billed provider resources.

**Consequences:** An idle development fleet does not have to remain deployed forever, but decommission is an evidence-producing lifecycle rather than console cleanup. Recreating the environment later uses a new environment and deployment identity; raw lease IDs remain scoped by their environment rather than claiming global non-reuse after the old control state is destroyed.

### ADR-015: Borrow process-verification lessons from CodexBar, not fleet authority

**Decision:** CodexBar informs the shared subprocess and PTY verification work already owned by Harness Execution; it is not precedent or an authority for the Crabbox fleet, Cloudflare control plane, hermetic boundary, harness acquisition, or release evidence. Agentscope may independently implement transferable invariants after reviewing their fit, but copies no CodexBar source into this capability.

**Context:** The exact reviewed source is `steipete/CodexBar` commit [`c2eff4c8b6b5b072d28b13d1afd240a337bf3e5a`](https://github.com/steipete/CodexBar/tree/c2eff4c8b6b5b072d28b13d1afd240a337bf3e5a), MIT-licensed to Peter Steinberger (`LICENSE` SHA-256 `14293556b79940745123d0160c71d27ed0e9fe9b8a848093f3ed78f4853caafe`). Source-proven facts at that revision are:

- `SubprocessRunner` and `TTYCommandRunner` exercise bounded capture, timeouts, termination escalation, descendant/process-group cleanup, shutdown fencing, synthetic hostile children, and PTY parsing.
- `LIVE_CODEX_TTY` and `LIVE_CLAUDE_TTY` probes are explicitly opt-in and accept many missing, parse, login, timeout, or other failures by returning without a failing assertion; they are developer diagnostics, not deterministic compatibility admission.
- Remote Agent Sessions use an already reachable SSH host with `codexbar` installed; they inspect/focus sessions and do not create, meter, reap, or reconcile cloud machines ([Agent Sessions](https://github.com/steipete/CodexBar/blob/c2eff4c8b6b5b072d28b13d1afd240a337bf3e5a/docs/sessions.md)).
- Public maintainer guidance prefers focused CLI tests, requires explicit authorization for live provider or credential probes, and calls headless macOS app tests brittle ([repository guidance](https://github.com/steipete/CodexBar/blob/c2eff4c8b6b5b072d28b13d1afd240a337bf3e5a/AGENTS.md)).

The inference from those facts is deliberately narrow: CodexBar is useful prior art for process supervision, PTY semantics, fake executables, and the limitations of live host probes. The reviewed revision contains no Cloudflare Worker, Durable Object, Hetzner lease, replay-safe create, spend-cap, independent reaper, provider-reconciliation, or inner-hermetic fleet design. It therefore neither validates nor contradicts the coordinator decisions in this Blueprint. Agentscope's distinct model is an outer disposable fleet host around an independently identified, denied-egress Docker scenario, with GitHub CI retaining authority.

**Consequences:** A future CodexBar revision may improve a process-testing technique without changing fleet architecture. Any claim about that revision must be repinned and reviewed; moving `main`, maintainer reputation, or an opt-in live probe is not evidence for an Agentscope support row.
