## Capability Summary

Agentscope development may use a self-hosted Crabbox coordinator on Cloudflare Workers to acquire bounded disposable Hetzner Linux workers. The deployment follows the documented Wrangler, Crabbox, Cloudflare, and Hetzner operating paths. It does not require a separate protected launcher, seven credential roles, a one-use mutation-plan service, or a privileged local control installation.

Crabbox supplies disposable outer development capacity. The shared hermetic scenario runner remains the inner test boundary across workstation execution, CI execution, and Crabbox execution. Crabbox is preferred for development and burst capacity when available, workstation execution remains supported, and GitHub-hosted CI remains merge and release authority.

## Architecture Decision Records

### ADR-001: Use the supported upstream Crabbox coordinator

**Decision:** Agentscope self-hosts the Cloudflare Worker and SQLite-backed `FleetDurableObject` from `openclaw/crabbox` tag `v0.46.0`, exact commit [`8ba71f913bbe57285ae29af45ef0d8ec6712477d`](https://github.com/openclaw/crabbox/tree/8ba71f913bbe57285ae29af45ef0d8ec6712477d). Deployment and client commands follow that revision's documented [Cloudflare coordinator](https://github.com/openclaw/crabbox/blob/8ba71f913bbe57285ae29af45ef0d8ec6712477d/docs/infrastructure.md) and [Hetzner provider](https://github.com/openclaw/crabbox/blob/8ba71f913bbe57285ae29af45ef0d8ec6712477d/docs/providers/hetzner.md) paths. Agentscope does not copy or fork the coordinator implementation. A version change is a standalone reviewed Blueprint change before rollout.

**Context:** The upstream coordinator already owns lease serialization, provider calls, active-lease and spend limits, expiry, cleanup retries, and the supported Cloudflare-to-Hetzner lifecycle. Replacing those paths with a second local control plane increases operational failure modes without improving the first working development lane.

**Consequences:** Cloudflare Workers is the coordinator runtime and Hetzner is the only initially enabled provider. Node/PostgreSQL, direct-provider operation, browser login, custom domains, Cloudflare Access, Tailscale, checkpoints, portal artifacts, and other providers are outside the initial path. If the pinned upstream path does not work as documented, operation stops for a reviewed correction or upstream-version change; it does not fall back to a bespoke launcher.

### ADR-002: Deploy with the upstream lock and ordinary Wrangler commands

**Decision:** The operator checks out the pinned source, installs `worker/package-lock.json` with `npm ci --prefix worker`, runs the upstream format, lint, check, test, and build scripts, and deploys the reviewed development profile with the project-local Wrangler resolved by that lock. Cloudflare mutations use the documented Wrangler commands for secret upload, deployment, inspection, and deletion. The deployment profile names one development Worker, its `FLEET` Durable Object binding and migration, its 15-minute trigger, workers.dev exposure, the required secret names, and the bounded non-secret variables; it contains no secret value.

The attended operator uses one supported Node.js release compatible with the pinned project and records the Node, npm, Wrangler, source, lockfile, profile, account, and resulting Worker deployment identities. Moving `latest`, a global Wrangler selected from ambient `PATH`, dashboard-only configuration, and an unreviewed generated profile are not deployment authority. Cloudflare recommends treating Wrangler configuration as the source of truth, and sensitive values use [Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/) rather than plain variables.

**Context:** Wrangler already supplies the supported Cloudflare deployment and secret-management interface. A separate signed-plan grammar, privileged installer, observer, or local mutation executor duplicates that interface and created the failures this decision supersedes.

**Consequences:** Agentscope retains a small reviewed configuration overlay but no coordinator fork. Deployment remains attended and records before/after identities; it does not require a one-use plan envelope, seven enrolled slots, signer roots, or repeated `sudo` prompts.

### ADR-003: Keep credentials ordinary, least-privilege, and out of workloads

**Decision:** One explicitly selected Cloudflare account hosts the development Worker, and one dedicated Hetzner project contains only Crabbox disposable workers. The Cloudflare account may be the repository owner's personal account and may contain unrelated resources; the operator accepts that account-level blast radius and limits every mutation to the exact development Worker. The human operator creates the smallest account-scoped Cloudflare API token that the documented Wrangler deployment requires and a Hetzner project Read & Write token, whose documented authority includes `GET`, `DELETE`, `PUT`, and `POST`. The Cloudflare token is used only for attended deployment and is not stored in the repository. The Hetzner token and one random Crabbox shared token are uploaded as Worker secrets; the shared-token owner and capacity settings are non-secret Worker variables. Browser OAuth and an admin token are omitted until a reviewed use requires them.

The operator stores reusable local credentials in the operating-system secret store. A value may enter a command only through the supported tool's secret-input mechanism or a transient operator-controlled environment and is removed after use. Tokens never enter repository files, chat, command arguments, VM configuration, synchronized source, candidate processes, scenario inputs, logs, or artifacts. The Crabbox guest receives neither Cloudflare deployment authority nor the Hetzner project token.

**Context:** Cloudflare and Hetzner credentials are necessarily broader than one individual Worker or server operation. Limiting each token to one account or dedicated project, keeping deployment attended, and placing provider authority in the coordinator follows the supported broker model without pretending the providers offer narrower permissions than they do.

**Consequences:** Loss or suspected exposure freezes new leases, revokes the affected token, and uses the provider consoles or documented CLIs for attended inventory and cleanup. Ordinary development does not depend on a custom credential vault, role-splitting ceremony, or private digest of secret values.

### ADR-004: Start with one small bounded worker

**Decision:** The first proof and ordinary default use one Hetzner `cx33` server selected explicitly with `--type cx33`, Ubuntu 24.04, a 90-minute hard TTL, a 20-minute idle timeout, and no retained lease or checkpoint. The coordinator initially permits at most two active leases globally, one per owner, USD 25 per month globally, and USD 10 per owner, matching the upstream small-installation guidance. Increasing server type, concurrency, lifetime, budget, provider, or persistence requires an explicit operator change and cost review.

The first proof is one one-shot Crabbox run. It authenticates through the shared-token login path, verifies coordinator and provider readiness with supported doctor/usage commands, runs only a fixed content-free operating-system identity command, and lets the one-shot lifecycle release the lease. It does not sync the repository, hydrate a project toolchain, or claim a hermetic scenario result. A warm lease, `--keep`, desktop, browser, code-server, checkpoint, or class fallback is not part of that proof.

**Context:** The upstream Hetzner provider defaults to the expensive `beast` class, while an explicit `--type` has no capacity fallback. A fixed small type and one-shot run make the first billed action legible and bounded.

**Consequences:** A capacity failure is a failed development attempt, not permission to select a larger server. The operator records the exact server identity, timestamps, and observed cost before allowing broader development use.

### ADR-005: Use the upstream lifecycle and prove terminal cleanup

**Decision:** Crabbox owns brokered server creation, per-lease SSH key handling, readiness, command execution, release, expiry, and coordinator cleanup retries. A successful one-shot proof requires the command to finish, the lease to become terminal, the exact Hetzner server and managed SSH key to be absent, coordinator active-lease and reserved-cost state to return to zero, and the inner hermetic scenario resources to reconcile. The operator independently confirms the dedicated Hetzner project inventory after the run.

If the one-shot path is interrupted or cleanup is uncertain, new acquisition stops. The operator first uses supported Crabbox list, history, stop, usage, and coordinator cleanup behavior, then the dedicated Hetzner project console or API for exact-resource recovery. Cleanup targets only the exact lease/server identities; it never sweeps an unrelated account or infers deletion from a missing local claim. The coordinator remains deployed while it owns a live or uncertain lease.

**Context:** Upstream brokered mode provides alarms and a scheduled reconciliation trigger, but scheduled work is not proof that a billed server is gone.

**Consequences:** A failed cleanup is a visible operational blocker. Recovery may be attended and simple, but terminal evidence still requires agreement between Crabbox state and Hetzner inventory.

### ADR-006: Keep Crabbox outside hermetic and release authority

**Decision:** Crabbox provisions only the disposable outer Linux guest. Before a Crabbox guest may run repository tests, a repo-owned setup path must hydrate the exact Node, pnpm, Docker, and other tool identities required by the unchanged hermetic scenario runner without receiving provider credentials or broadening the scenario's network policy. A receipt component inside the hermetic scenario classifies the result, keeps and removes scenario stdout, stderr, reports, and diagnostics within that inner boundary, and sends only a bounded content-free terminal receipt to the guest-side Crabbox command. The outer guest and coordinator never receive raw scenario output or content-bearing result files. If that hydration and receipt path is absent or cannot be proven, Crabbox remains usable only for the content-free substrate proof in ADR-004 and makes no repository-test claim.

Inside that admitted path, Agentscope runs the exact candidate and manifest with dummy harness credentials, internal model mocks, loopback destination evidence, denied public egress, and bounded Docker resources. Workstation execution, CI execution, and Crabbox execution share that inner contract while retaining different outer orchestration.

GitHub-hosted CI remains merge and release authority. Crabbox results are development and burst evidence only; provider availability, quota, budget, or cleanup delay cannot turn a failed CI check into a pass or block a release that does not require Crabbox.

**Context:** A remote SSH host is useful capacity, not a product-support or isolation boundary.

**Consequences:** The initial one-worker proof makes no repository-test, hermetic-scenario, actual-binary support, release, publication, or provider-service claim. It proves only that the pinned coordinator can acquire, run a fixed content-free command on, and clean one bounded Hetzner worker. A later admitted hydration and receipt wrapper is required before any hermetic development-job claim.

### ADR-007: Retain bounded operational evidence and retire with supported tools

**Decision:** Each run retains a bounded non-secret record containing the pinned Crabbox source and client identity, Worker deployment identity, executor location, exact candidate and manifest identities when applicable, lease and Hetzner server identities, requested limits, start and terminal times, command outcome, cost observation, and inner/outer cleanup result. It excludes tokens, IP addresses, SSH material, synchronized source, raw terminal content, prompts, traces, and harness output.

The pinned upstream coordinator retains ordinary command output, and failed SSH runs create a local failure bundle. Approved substrate commands therefore emit only fixed synthetic content-free output. A later repository-test wrapper must ensure every outer stdout/stderr byte and failure diagnostic is content-free, encode an inner test failure in the receipt rather than exposing raw process output, prove no content-bearing result file crossed into the guest, and delete any local Crabbox failure bundle without sharing or retaining it. If the supported Crabbox invocation cannot keep raw repository-test output out of the guest, coordinator history, and local failure bundles, that invocation is unsupported for Agentscope tests.

Normal idle operation may leave the coordinator deployed with zero active leases. Full retirement first freezes acquisition and proves zero Crabbox leases, zero Hetzner servers and managed keys, and no unresolved run. The operator then removes the Worker through supported Wrangler/Cloudflare operations and verifies its script, trigger, workers.dev exposure, and secrets absent before revoking the coordinator's Cloudflare, Hetzner, and shared tokens. Durable Object storage or class deletion occurs only through an upstream-supported, append-only migration proven compatible with the pinned deployment; when that authority is unavailable, the zero-lease coordinator stays disabled rather than discarding cleanup history. Any provider state that cannot be removed through the supported path remains an explicit incident; architecture does not invent a no-op Worker, custom migration executor, or local retirement signer to relabel it as success.

**Context:** The first goal is a working, supportable development lane, not a second deployment product. Provider consoles and supported CLIs remain adequate attended recovery authority for one owner and one dedicated project.

**Consequences:** Operational evidence is sufficient to diagnose spend and cleanup without becoming another credential or content store. Longer retention and multi-user audit requirements require a later reviewed decision.

### ADR-008: Supersede the protected-launcher bootstrap

**Decision:** The protected launcher, seven-slot credential enrollment, one-use plan ledger, independent observer roles, privileged upgrade ceremony, and generation-2 launcher work are deprecated and are not required or supported prerequisites for Agentscope Crabbox development. Existing repository code and closed pull-request history may remain temporarily for forensic comparison, but they carry no deployment authority and cannot block the documented Wrangler/Crabbox path. Removal or archival is implementation sequencing owned in Beads, not a prerequisite for the first happy-path proof. Previously enrolled launcher credentials are revoked after the replacement path is proven; they are not migrated into or treated as authority for the new setup.

**Context:** The bespoke bootstrap repeatedly failed before the first Worker could be proven, while the upstream-supported deployment and lifecycle already provide the needed small-team behavior.

**Consequences:** Implementation work replaces rather than extends the frozen protected-launcher lane. Any future need for unattended multi-tenant control or stronger mutation separation must start with a new standalone Blueprint; it cannot silently reactivate the superseded launcher.
