## Capability Summary

This Blueprint verifies the complete AgentScope setup flow without ever touching a developer's active AgentScope or harness installation: fresh CLI install, init, hook installation, real harness execution, capture, and destination delivery.

## Architecture Decision Records

### ADR-001: Compose the leaf testing contracts end to end

**Decision:** A real-harness scenario composes, without redefining, the lane boundary from [Test Strategy](/docs/blueprints/testing/test-strategy), filesystem/process boundary from [Container Isolation](/docs/blueprints/testing/integration/container-isolation), network and ledger behavior from [Mock Services](/docs/blueprints/testing/integration/mock-services), authenticated inputs, compatibility catalog, retention, and drift behavior from [Matrix Operations](/docs/blueprints/testing/integration/matrix-operations), workstation/CI/Crabbox gates from [Workstation, CI, and Crabbox Execution](/docs/blueprints/testing/integration/ci-execution), shared execution and evidence behavior from [Harness Execution Verification](/docs/blueprints/testing/harness-execution), and the harness-native lifecycle from that harness's approved Blueprint.

**Context:** Each leaf capability has one authoritative amendment point. Repeating isolation, artifacts, mocks, or lane policy here would create parallel ADRs that can drift.

**Consequences:** This umbrella owns only the complete acceptance boundary: install the exact packed CLI in a fresh scenario, run init and owned hook installation, invoke the real harness against deterministic model mocks, observe destination delivery independently, assert canonical context/redaction, then prove owned cleanup and uninstall. Harness and destination test adapters extend their own seams without changing generic orchestration.

### ADR-002: Keep platform certification distinct from product acceptance

**Decision:** The process fixture certifies generic isolation, immutable inputs, model and destination ledgers, failure handling, concurrency, retention, and cleanup. It is not a real harness and cannot satisfy a harness-support, initialization, hook-installation, capture, or destination-product acceptance criterion.

**Context:** The hermetic substrate is useful before public CLI and harness integrations exist, but fixture-shaped lifecycle markers must not be mistaken for implemented product behavior.

**Consequences:** Only a manifest entry using the real packed CLI, real public commands, a pinned harness binary, and the appropriate first-party adapters end to end can supply product acceptance evidence. The platform fixture remains deterministic certification for the orchestration layer only.

### ADR-003: Keep destination-composition evidence destination-scoped

**Decision:** [CLI Installation ADR-003](/docs/blueprints/operations/cli-installation) is the sole owner of the bounded ordinary-bin configuration profile, including its platform tuple, credential backend, lifecycle operations, and evidence aggregate. This umbrella composes the authenticated result of that profile without restating or extending it and keeps it distinct from actual-harness delivery evidence.

**Context:** Unit contracts and the generic process fixture cannot prove that the self-contained npm artifact composes first-party destinations and their complete local lifecycle. A Reporter accepts only Core's same-process branded redacted trace after a registered harness capture; an external canonical value, fake vendor executable, or hidden certification entry would violate product, brand, or artifact authority.

**Consequences:** The composed profile supplies no complete Local support admission, Reporter/Retriever round-trip, harness, or crash-prefix evidence and promotes no `AC-REP-*`, `AC-RET-*`, or `AC-HAR-*` criterion. Actual-harness delivery, maintenance/upgrade, and package crash-prefix evidence retain their separate acceptance boundaries.
