# Requirements Writing Guide

Write product-wide context as a Product Overview Document. Write a local capability as an FRD with `Overview`, `Terminology`, and identified, independently testable requirements. Requirements are external and user-centered; avoid implementation details. Keep one cohesive capability per requirement and one observable behavior per acceptance criterion.

Use requirements for user-visible product truth, including supported capabilities, compatibility promises, and rules that constrain support claims. Keep release milestones, alpha or version delivery subsets, implementation or merge order, rollout, ownership, dependencies, blockers, and other project sequencing in Beads. A delivery milestone may stage work toward a requirement, but it does not waive or narrow the requirement; revise the requirement separately when the external product promise itself must change.
